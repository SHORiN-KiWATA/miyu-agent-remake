## 量尺

状态：施工 V-1（2026-10-10）。

### 是什么

一个量性能的小程序 `miyu-perf`：照 `23-性能预算.md` 第一节的量法量核心这一边，原始数据和对照预算的表写进 `docs/perf/`。它是工具 crate，不属于任何一层，谁都不许依赖它（`01-架构.md` 第九节规则 5）。

### 在哪

| 文件 | 管什么 |
|---|---|
| `xtask/src/perf.rs` | `cargo xtask perf`：编 release 的 `miyu`、`miyu-sandbox`，再编量尺、跑它 |
| `crates/miyu-perf/src/main.rs` | 照先后量一遍，写结果 |
| `args.rs` | 参数 |
| `budget.rs` | 预算照 23 第二节的表读，判超没超 |
| `fake.rs` | 假模型服务 |
| `sandbox.rs` | 沙盒数据根，拉起、停掉核心 |
| `rpc.rs` | 在连接上说 JSON-RPC，等一轮结束 |
| `memory.rs` | 读进程的内存 |
| `machine.rs` | 量的条件 |
| `measure/startup.rs`、`sessions.rs`、`large.rs`、`append.rs`、`size.rs` | 每一项怎么量 |
| `report.rs`、`report/raw.rs`、`report/rows.rs`、`report/load.rs` | 写原始数据、写表；从原始数据读回来（`--render`） |
| `stats.rs` | 分位数 |

### 对外的样子

`cargo xtask perf [参数]`，参数原样交给量尺，可以不写：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--runs` | 10 | 冷启动量几次 |
| `--sessions` | 10 | 小会话几个 |
| `--events` | 10000 | 大会话说到第几条事件 |
| `--tail` | 30 | 到了以后再说几轮 |
| `--reloads` | 5 | 重启核心再打开大会话几次 |
| `--appends` | 2000 | 追加几条 |
| `--reply-bytes` | 3500 | 假模型每次回多少字节的正文 |
| `--idle-wait` | 200 | 不订阅大会话以后等几秒再量内存 |
| `--out` | `docs/perf` | 结果写到哪 |
| `--render` | 不写 | 不量：照这一份原始数据（`.json`）、照 23 现在的预算重出同名的 `.md`，原始数据不动。只编量尺，不编 `miyu` |

结果：`docs/perf/<日期>-<系统>-<架构>.json`（原始数据）和同名的 `.md`（条件、表）。日期是 UTC。同一天再量一次，盖掉同名的。

预算改了（23 F1：实测后校准），用 `cargo xtask perf --render docs/perf/<那一份>.json` 重出表。

### 怎么走

1. 沙盒在 `target/perf/` 下，每次量之前删掉重建。不放系统的临时目录：那里常是内存盘，同步不算数。
2. 核心的环境照集成测试拉核心的那一套：不拉 models.dev 的目录，缓存目录放进数据根，不用 `$XDG_RUNTIME_DIR`，不走代理。核心空闲一小时才走，量的时候不会自己退出。
3. 系统配置里一家 `perf`（`openai-chat`），地址是假模型服务，模型 `perf/perf-model` 不在目录里：资料里没有窗口，所以没有压缩线，大会话不会自动压。
4. 假模型服务和量尺在同一个进程里，时刻可以直接比。每个 `POST` 回同一段字（正文一块、收尾一块带用量、`[DONE]`），别的请求回空的模型列表。它记下请求头读全的时刻：驱动编好整份请求体才发头，所以这个时刻包含组装和编码，不含请求体在回环上传多久。
5. 每一句话带一个只此一句的记号，量尺照记号认出这一轮的主请求，起标题这些辅助请求跳过。请求编号整个进程里不重复：核心照编号认重发，造会话会交回上一次造的那一个、说话不再开一轮，连接换了、核心重启了都照认。每一次等最多 120 秒，等不到的报是在等什么。
6. 照先后量：
   1. **冷启动**：先空跑一次（第一次起来要建系统账号、索引），再量 `--runs` 次。每次从拉起 `miyu core` 算起，记三个点：写来 `ready`、握完手、造好会话并订阅上（能提交第一轮）。每次量完停掉核心，等它放开数据根的锁。
   2. **热启动、每多一个会话**：造 `--sessions` 个小会话各说一句，重启核心。歇两秒量核心空闲的内存。再一个个新连上、握手、订阅（订阅时核心才载入它），记这一段。都订阅着、各再说一句，歇两秒量内存。
   3. **大会话**：造一个会话，一句一句说，直到说之前的事件数到了 `--events`，再说 `--tail` 轮。每一轮记说出去到模型收到请求、到推来 `turn.ended`。歇两秒量载着它的内存。断开连接，等 `--idle-wait` 秒（会话 actor 空闲 180 秒退出）再量一次。然后重启核心 `--reloads` 次：每次连上、握手、订阅大会话（从头读日志、重放），记这一段；再说一句，记到模型收到请求。最后一次歇两秒量内存。
   4. **追加并同步**：在进程里，大会话日志里的事件从第一条起，一条一条追加进 `target/perf/append/` 下的一份新日志，每条写一次、同步一次，走会话 actor 落盘用的同一个函数。
   5. **二进制**：`miyu`、`miyu-sandbox` 的字节数；拷一份 `strip` 以后再量，没有 `strip` 的平台不写。
7. 内存读 `/proc/<进程号>/smaps_rollup` 的 `Pss`、`Anonymous`、`Rss`，核心和它拉起的子进程各一行，子进程照 `/proc/<进程号>/task/*/children` 找。只有 Linux 上读得到，别的平台写「不量」。
8. 对照预算的表：
   - 预算照 23 第二节的表读，第一格是名字。只写了一个数的照 p50 比，写了分位的照那个分位比；内存照核心进程的 PSS 比。
   - 比的几项：

     | 表里的一行 | 量的是哪一段 | 照 23 的哪一行比 |
     |---|---|---|
     | 热启动：订阅一个没载入的小会话 | 连上、握手、订阅 | 热启动到能提交第一轮 |
     | 热启动：重启核心后打开大会话 | 连上、握手、订阅 | 热启动到能提交第一轮 |
     | 一次请求的投影 | 大会话到了以后的那几轮，说出去到模型收到请求：含 `message.user` 落盘、组装、编码、连接，是投影的上界 | 一次请求的投影（增量，一万条事件的会话） |
     | 从头投影 | 重启、打开大会话以后头一次说到模型收到请求：没有投影缓存，这一次从头算 | 同一个会话从头投影一次 |
     | 追加一条事件并同步 | 每一条的写加同步 | 追加一步的事件并同步 |
     | 核心空闲 | 一个会话都没载入时核心的 PSS | 核心空闲、没有会话载入 |
     | 每多一个活动会话 | 小会话都订阅着时核心 PSS 涨的，除以会话数 | 核心里每多一个活动会话 |

   - 判：没超的「过」，超了的「超」，量不了的「不量」。
   - 23 第二节缺了要比的一行，量尺一开始就报错，不白量。
9. 没有预算的也列出来：冷启动的三个点、大会话有多大、载着它和空闲以后的内存、二进制大小。另有一张「会话长大的一路上」：照说之前的事件数每一千条一档，报说一句到收到请求、一轮的 p50、p95。
10. 条件写机器（CPU 型号、逻辑核数、内存）、系统、内核、rustc、提交（工作区有没提交的改动的标「+改动」）。不写主机名、用户名、路径。
