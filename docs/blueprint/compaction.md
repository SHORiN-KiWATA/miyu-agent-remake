## 压缩

### 是什么

上下文快满时，请她把旧内容写成一份摘要，换掉旧内容，最近的一段原文（尾巴）留着，腾出地方接着干。只在不够用时压，一压就压一大段：每压一次，请求的前缀就重置一次（`09-压缩.md` 第一节）。

压缩不删日志里的任何一条。要看旧内容，她用 `history` 取回（`tools/history.md`）。压缩发生在一个回合里，撤销这一轮，压缩跟着撤掉，上下文回到压缩前的样子（第十一条）。整套做法以 Claude Code 为准（`09-压缩.md`）。

另有一种不请求模型的办法：**裁剪**（trim），把最老的几轮整块移出，由代码写一句说明。它给群聊用，随通讯平台做（第五条）。

### 怎么走

**一、量用量**

1. 用量 = 锚 + 锚以后新进有效历史的内容的本地估算。Claude Code、codex、pi、dsh 都是这个结构。不全靠本地估：旧版整段用 o200k 分词器数，比 DeepSeek 报的系统性少约两成（77 个样本），长会话里一遍要一两秒。
   - **锚**：有效历史里，最近一次压缩那一条之后的 `model.called` 中最近的一条，`result` 是 `ok`、带 `usage`；取供应商报的 `uncached + cache_read + cache_write + output`。每次请求都有，一轮当中也有锚。压缩那一条之前的不算：摘要请求自己那条、尾巴里压缩以前的请求，报的都是压缩前的大小。带 `purpose` 的（回顾这类辅助请求）也不算：它报的是它自己那一次的大小（施工 3-8 四补）。
   - **锚盖住哪些**：锚那次请求有 `messages` 条消息，它的回复是这一次请求的第 `messages` 条（从 0 数）。请求只追加，所以这一次请求的工具面、system、前 `messages + 1` 条，就是锚盖住的；后面的是新增的，本地估。
   - 本地对锚盖住的那些的估算，比供应商报的还大：取估算（照 dsh，宁多勿少）。
   - 整份用本地估算：没有锚；锚的端点、模型和这一次要发的不一样（换过模型，照 dsh）；这一次请求的消息没比锚多（兜底）。
2. 本地估算：一条消息里文字、思考、工具调用的名字和参数、工具结果的文字、驱动的私有数据和认不出的块的原样 JSON，UTF-8 字节加起来除以 4，向上取整（照 codex 的 `APPROX_BYTES_PER_TOKEN = 4`，2026-09-29 项目主人定）；图片照驱动的算法，没有的一张按 2000；文件一个按 2000。工具面照规范的 JSON 字节、system 照字节，都除以 4 向上取整。不另加每块、每条的结构开销。
   - 照 DeepSeek 文档的比例（英文一个字符约 0.3 token、中文约 0.6），中文多估约两成半，英文少估约一成半。只估锚之后那一截，少估的落在余量里；真漏了有被动压缩兜底。
   - 未选：除以 3。中文多估约三分之二，压得偏早。Claude Code、pi 的字符数除以 4 在中文上少算三四倍。
   - 6-3 用 DeepSeek 实测中文、英文、代码、图片各一组，本地估算和供应商报的对比。
3. 压缩以后还没请求过的，整份请求（工具面、system、检查点、之后的内容）都用本地估算。摘要请求的 `model.called` 排在检查点前面，不拿来当锚。

**二、什么时候压**

1. 每次发主请求之前查：回合的第一次请求之前，每一步的工具结果齐了以后，出错再来的也查。再来的请求可能多了半截回复和被打断的那一句；什么都没多的，上一次发之前查过，不会到线。
2. **压缩线** = 窗口 − 输出预留 − 余量。用量超过它就压。算出来不是正数的（窗口不到 33000），当作没有线，不主动压。
   - 输出预留 = min(模型的最大输出, 20000)，余量 13000，和 Claude Code 的「有效窗口减 13000」一样。
   - 摘要请求 = 用量 + 摘要指令 + 输出预留。余量比摘要指令长得多，所以到线时摘要请求一定放得下（`09-压缩.md` Z3）。
   - 一步长得比余量还多的（例如一次读进一个很大的文件）：下一次发请求之前照样到线就压；摘要请求本身放不下，走第三条第 10 条截掉最老的再试；供应商报超长，走被动压缩（第六条）。
3. 设了 `compaction.max_context` 的，压缩线取它和上面那条里小的（随配置那一步）。
4. 模型的资料没报窗口的，不主动压。
5. 自动压缩暂停着的（第十条）：不压；用量加输出预留超过窗口、明知会超长的请求不发：记一条没发出去的 `model.called`（没有 `endpoint`、`model`、`request`，分类 `compaction_paused`，原话 `the request would not fit: <用量> tokens used + <预留> reserved for output > window <窗口>`），这一轮照出错结束；排着队的话她没听到，和摘要请求失败时一样，照排队的规矩接着开下一轮。没超的照发（施工 6-6 上）。

**三、压缩这一步：fork 式**

1. 压缩是这一轮里的一步：回合停在压缩上，发一次摘要请求，收回来写 `context.compacted`，再照常组装、发这一步本来要发的请求。一步至多压一次：压完还在线上的，照发（施工 6-2 下）；发了主请求，下一步又能压。摘要请求说完了，这一步连着出错的次数不清零：重试和主请求合用一个计数。
2. **替代到哪**（`upto`，下面叫 N）：
   - **留尾巴**（2026-09-29 项目主人定，重开 `09-压缩.md` Z4）：从最新的往回数，一组一组地留，留到 16000 token 为止（不超过压缩线的四分之一）。一组是一条人这边的消息（连同跟着它的事实），或者一条助手消息连同它的工具调用和结果；不拆开一组。N 是尾巴前面的那一条。
   - 照投影的先后（`History::ordered`）看，一组从一条人的消息或者一条助手的回复开始，两组之间的别的事件（回合开始、事实、工具结果、模型调用、回合结束）跟着前面那一组。只在切得开的地方切：前面的序号都比后面的小，第 N 条及以前正好是投影的开头一段，摘要请求才是上一次请求的前缀（施工 6-2 下）。请求在路上时来的话，序号比回复小、投影里排在回复后面，那里切不开，这一组并进前面那一组。每条事件照第一条第 2 条的数法估：人的消息、回复、工具结果照内容块，事实照原文，别的算 0。预算 = min(16000, 压缩线的四分之一)；16000 是策略数据（快照里的 `tail`）。

   - 和下面「这一轮要回应的话」合在一起：N 至多是那条边界前面那一条，尾巴只会让 N 往前挪；再照「一组不拆」往前退。
   - **这一轮要回应的话**：以前的回合里的请求（带 `purpose` 的辅助请求不算：她没在里面听到什么，施工 3-8 四补）没看到过、这一轮的回复也没看到过的人的消息，和回报（`job.reported`、`child.reported`，施工 7-8：还没听到的回报压进摘要，她就只看得到摘要转述的一句；子代理的留言、别的会话发来的话本来就是 `message.user`，施工 C-2；空了的通知 `peer.idle` 一样，施工 C-6）；这一轮还没有回复的，加上触发它的那一条。这一轮里认回复不认请求：请求出错、没回复的，她没真看到。以前的回合里请求看到过的，照常压：那一轮已经过去了，摘要请求也才接得上上一次请求的前缀。
   - **边界**：这些话里最早的那条。有边界的，N 至多是边界前面那一条；没有的（回合中途，也没有排着队的新话），N 至多是落了盘的最后一条。
   - N 落在一条回复和它的工具结果之间的，退到这条回复前面（一组不拆）：回合中途排着的新话，序号在这一步的结果前面。
   - 有效历史里第 N 条及以前没有人的消息、回复或工具结果的，不压，照旧发主请求（压了也腾不出地方，还会一直压下去）。N 不比上一次压缩的 `upto` 晚的也是这样：那以前的早就替代掉了。
   - 回合开头（第一次请求之前）：这一轮要回应的话一定在尾巴里，超了预算也留。它们是触发这一轮的那句，连同由上一轮排着队接过来的几句（`kernel/history.md`「拿走什么」认的那几句），和这一轮开头注入的事实。所以这一轮第一次请求的最后一块，照旧是触发它的那句（`08-上下文投影.md` 第七节）。
   - 被动压缩：见第六条。
3. **请求** = 有效历史到第 N 条为止的投影，原样，加一条 user 消息放摘要指令。摘要指令是 `summarize-task.txt`（正文）接 `summarize-end.txt`（最后那句不许调工具，施工 6-8 从正文里拆出来，拼出来和原来一字不差）；手动压缩附了要求的，两份中间夹 `summarize-instructions.txt`（`Additional Instructions:` 那一行）和要求（第七条第 3 条）。这一段是上一次请求的前缀，几乎全部命中缓存。尾巴不进摘要请求，摘要和尾巴不重复；摘要指令里说一句：这之后最近的一段会原样留着。这是 Claude Code「压到某一条为止」那种局部压缩的做法。
4. 用会话自己的驱动、模型、端点。缓存在端点上，换一家就全部落空（旧版撞过）。
5. 工具照样声明，思考的设置照样带，输出上限照会话原来的请求带：前缀要一字不差。不让她调工具：摘要指令开头、末尾写明只许输出文字。不带 `tool_choice: none`：6-3（下）在 DeepSeek 上实测，同一个 9045 token 的带工具请求，带不带都命中 8832，不掉缓存；可是也挡不住，一句「用 read 打开 README.md」带了照样调 `read`。她要是调了工具，照第 7 条。
6. **取摘要**：回复先是 `<analysis>` 草稿，再是 `<summary>` 摘要。只看正文块，思考不要。先去掉草稿：草稿里会顺嘴提到 `<summary>` 这个标签（`Now writing the <summary>.`），从那儿取就把草稿的尾巴带进了摘要（6-3 下真模型两次都这样）。剩下的有 `<summary>` 的，取它到最后一个 `</summary>` 之间的：摘要里引的 HTML 也有 `</summary>`，真收尾的在最后；没有收尾的（输出到了上限）取到末尾。没有 `<summary>` 的，剩下的当摘要。草稿没收尾的，摘要写在它里面的从最后一个 `<summary>` 起留下，没有的到末尾都算草稿。前后空白去掉，取出来是空的，算失败：`model.called` 记成出错，分类 `bad_summary`。
7. 回复里有工具调用：这一次作废，改走隔离式（第四条，施工 6-6 下）。作废的这一次照常记 `model.called`，出错 `bad_summary`，原话写明调了工具、改走隔离式；和截短重试一样，改走哪种记在回合上，落了盘照常走发请求那一步再发（先落盘，后请求）。隔离式一次压缩只改走一次，出错再来的还是隔离式，不算又改走一次（施工 6-6 补）；隔离式也取不出摘要的，算失败。快照里没有 `summarize-system.txt` 的（以前造的），不改走，照失败算，原话只写调了工具。
8. **进度**：摘要请求报发出去时先推一条 `written` 是 0 的 `compaction.progress`，头一收到就能印「正在压缩」；之后收到的正文（草稿加摘要）照字数推；`expected` = 压缩前用量折成的字数，夹在 20000 到 80000 之间（openclaude 的做法）。
9. **不设总超时**：流一直在出字就等着，界面上有进度，人可以打断；卡住不出字的，由 HTTP 的空闲超时管（`http.md`：连接 30 秒、空闲 180 秒，没有总超时，6-3 下核对过）。旧版写死 90 秒，长会话一压就超时。
10. **摘要请求本身超长**（供应商报 `context_too_long`，施工 6-6 中）：
    1. 超了多少：驱动从报错原话里解析（`excess`），照几家常见的说法（「maximum context length is N … resulted in / requested M」「prompt is too long: M tokens > N」），M 减 N；解析不出来的没有。它随「说完了」交给内核（`Input::ModelEnded`），和要等多久一样不进日志。
    2. 截掉哪些：有效历史到第 N 条的投影里，检查点后面的一组一组，从最老的起去掉，只切在切得开的地方（组和切法同第 2 条的留尾巴）。有 `excess` 的，去掉的估算（第一条第 2 条）加起来刚好盖过它；没有的，去掉 20% 的组，向上取整、至少一组。至少留一组；留不下的，这次压缩失败。按组不按轮（2026-09-29 施工 6-6 中定）：一轮任务里可以有几十组工具调用，按轮截，一轮的会话一组都截不掉；Claude Code 截的也是一组一组。
    3. 截过的摘要请求：检查点、留下的几组、摘要指令。留下的第一条是助手的，前面补一条 user：更早的对话为了压缩截掉了（`truncated.txt`）。组装器的 `summarize` 多一个参数：截到第几条，没有是不截。
    4. 截着最多再试 3 次，第 3 次还超长，这次压缩失败（第十条）。每一次都记一条 `model.called`（`compaction`、出错 `context_too_long`），`seen` 照旧是 N。报了超长那一刻不当场重发：截到哪记在回合上，回到准备好，这一批落了盘照常走发请求那一步（先落盘，后请求），环境、权限、会话编号几块事实照查，重读（第九条）照常再交一次，进度照常先推 0 字的。出错再来的（驱动分类可以重试的错，到点再发）照记下的发：截到哪、截了几次、是不是隔离式都不变（施工 6-6 补）。
    5. 截过的，写压缩时 `notes` 最后多一段（`notes-uncovered.txt`）：第几到第几条摘要没看到，原文还在，用 `history` 取回（第八条第 4 条）。
    6. 截过以后前缀变了，这一次不再命中缓存，照常发。
11. **写 `context.compacted`**：`turn` 是这一轮，`by` 是内核，`cause` 是回合的。同时推瞬时的 `compaction.done`（见「对外的样子」）。之后照常组装下一次请求：环境、权限、会话编号几块事实和检查点后面还在的同类比，比不到的注入（`kernel/request.md`「事实」）。
12. 摘要请求照常记一条 `model.called`，`seen` 是 N。

**四、压缩这一步：隔离式（回退）**

- 什么时候用：驱动不能复用前缀的（例如以后借别家 agent CLI 的驱动）；fork 式的回复里她调了工具的。
- 请求（施工 6-6 下）：有效历史到第 N 条的投影，照平常组装的那几条消息原样，最后接摘要指令，和 fork 式一样；只是 system 换成一句极简的（`summarize-system.txt`），工具面是空的。截短重试照第三条第 10 条截。
  - 原来写的是把待压缩的内容压平成一段文字（每段标明角色、工具调用只写名字和参数的键名、图片文件换成占位）。2026-09-29 施工 6-6 下实测开发端点（DeepSeek 的写法）：不带工具面的请求里，照样带着以前的工具调用和结果、思考，收，她只回文字、没有调工具。照原样发就不用另造一套给模型看的标签。哪一家不收没有工具面的工具调用的（Anthropic 的接口要求带着工具定义），由那一家的驱动自己压平，随那个驱动做。
  - 思考照驱动平常的设置，不另关：统一的请求里还没有思考的开关，为这一处加一个不划算（随模型配置那一步再看）。
- 不带只读的读取工具（Claude Code 的回退带着 `Read`）：带了工具，摘要请求就成了一个会调工具的小回合，要多一套派工具、收结果的路；最近的文件压后会重读（第九条）。
- 手动压缩附的要求照样夹在摘要指令里（第七条第 3 条，施工 6-8）。
- 取摘要、进度、超长重试照第三条。

**五、裁剪（trim，随通讯平台）**

1. 切点：从最老的一轮起，一整轮一整轮地移出，移到用量剩压缩线的一半左右为止。不拆开工具调用和结果，不拆开同一条助手消息。
2. 不请求模型。`summary` 是空的，`mode` 是 `trim`，`notes` 是代码写的说明（`trimmed.txt`）。
3. 不重读文件：留下的后一半本来就是原文。
4. 瞬间完成，没有失败，也就没有熔断。
5. 默认用在群聊，各场所可以改（2026-09-29 项目主人定；叫法「裁剪（trim）」也是他定的，和旧版一致）；无人值守的场所压缩失败时也改成裁剪一次（第十条）。

**六、被动压缩**（`trigger` 是 `overflow`）

1. 主请求报上下文超长（驱动的分类 `context_too_long`）：这一步改成先压缩，再重发一次，只重发一次（施工 6-7）。
   - 摘要请求报超长的走第三条第 10 条的截短，不走这里。
   - 暂停着的（第十条）不压，照出错结束。「压完很快又到线」照第十条第 5 条一样算：被动压缩也是一次到线，连着到了次数的不压，写暂停，照出错结束。
   - 压的时机：报超长的那一批落了盘，照常走发请求那一步，先压（`trigger` 是 `overflow`），压完照常组装、重发。一步至多压一次（第三条第 1 条），重发的这一次不再压。
2. 已经收到了输出的（写成了半截回复）不压、不重发，照出错结束这一轮：免得半截回答、重复执行有副作用的操作。
3. 尾巴照第三条第 2 条留，至少留最后一组：最后一条助手消息，连同它的工具调用和结果；最后一组比尾巴的预算还大的，也留（自动压缩不留，这里留：摘要要看的是它以前的，重发时她得看得到自己刚做的）。尾巴里的思考照驱动平时回放历史的规矩带：DeepSeek 带工具时每一轮的思考都要回传，剥掉会报 400（Claude Code 在这里剥掉思考，这里不照它）。有效历史里第 N 条及以前没有能压的，不压，照出错结束。
4. 压完重发还是超长，这一轮照出错结束，算一次失败（第十条）。
5. 真模型上撑爆窗口太贵（开发端点一百万 token），这一条靠执行器替身和随机测试守着（施工 6-7）。

**七、手动压缩**（`trigger` 是 `manual`，施工 6-8）

1. `session.compact`，空闲时才收：有回合在进行的拒绝，`turn_running`；正在改回文件的拒绝，`restoring`。自动压缩暂停着也收（第十条第 6 条）。
2. **替代到哪**：收下命令时就定，照第三条第 2 条，尾巴一样留（2026-09-29 定，照推荐；想从头来，开新会话）。和自动压缩不一样的几处：
   - 「这一轮要回应的话」换成还没有哪次请求看到过的人的消息：以前的回合里的请求（`model.called` 的 `seen`）、回复都没看到过的。例如开了一轮、第一次请求之前就打断了的那一句。
   - 没有这样的话，N 至多是这时落了盘的最后一条：单开的这一轮自己（它的 `turn.started`）不压进去。
   - 尾巴的预算照第三条第 2 条；模型的资料没报窗口、没有压缩线的，就是策略的 `tail`（16000）：没报窗口的不主动压，手动的照样能压。
   - 定出来的 N 照第三条第 2 条是「不压」的那两种（第 N 条及以前没有人的消息、回复、工具结果，或者不比上一次压缩的 `upto` 晚）：自动的照旧发主请求，手动的拒绝，`nothing_to_compact`。策略里没有压缩的（6-2 以前造的快照，连摘要指令都没有）、执行器没交过限额的（算不了尾巴）也是它：只在开发时的旧会话、内核测试里有，不另开原因码。
3. **人附的要求**：去掉前后空白是空的，当没写。有的，摘要指令拼成 `summarize-task.txt`、`summarize-instructions.txt`、要求、`summarize-end.txt`；要求原样放，不转义（是人亲口说的，和 `message.user` 一样），末尾没有换行的补一个。原样记进 `context.compacted` 的 `instructions`。
   - 照 Claude Code（openclaude `getCompactPrompt`）：要求夹在正文和最后那句提醒中间，最后一句还是不许调工具。
   - 以前造的快照里没有拆出来的两份，读成空的：自动压缩拼出来一字不差；附的要求直接接在旧的整份指令后面。
4. **单开一轮**，只做压缩：追加 `turn.started`，没有 `trigger`，`by` 是内核，`cause` 是这个命令，`cwd`、`dirs` 照会话现在的环境写。不注入事实，不换实际生效的权限，不跑回合开始的挂接点：这一轮不请求主模型、不调工具。回应是它的序号，落了盘就回，和 `session.send` 一样不等这一轮做完。
5. 开头那一批落了盘，发摘要请求，名字是 N，照第三条第 3 到 9 条（压后重读照第九条）。`before` 照这时的有效历史组装一次算。不算步数。出了能再来的错，照「出错再来」等着，到点照同一个 N、同样的要求再发。摘要请求报了超长截短再发（第三条第 10 条）、调了工具改走隔离式（第三条第 7 条、第四条）的，要求照样夹在指令里，`model.called` 的 `compaction` 照样是 `manual`。
6. **取到了摘要**：写 `context.compacted`（`trigger` 是 `manual`，带 `instructions`、`notes`、`restored`，不写 `refills`），推 `compaction.done`，接着 `turn.ended`（`completed`），同一批。这一轮不注入事实：下一轮开头照常和检查点后面的比着注入。压缩期间来的消息照排队的规矩排着，同一批接着开下一轮（`kernel/session.md`「排队的消息」）。
7. **没压成**：
   - 出了不再来的错、再来够了、取不出摘要：这一轮 `error`，原因在摘要请求的 `model.called` 里（`compaction` 是 `manual`）。不数进熔断、不写暂停（第十条第 3 条）。
   - 人打断：摘要请求照打断的规矩记 `model.called`（`interrupted`），不写 `context.compacted`，这一轮 `interrupted`。
   - 有计划的重启：这一轮 `restarted`，再起来不接着压：人再要一次就是。没有 `trigger` 的那一轮不接着干，排着的留在日志里，和崩了一样等人开口（`kernel/session.md`「载入和崩溃」）。
8. **不进上下文**：没有 `trigger` 的那一轮，渲染时不记回合开始，它的 `turn.ended` 不出「这一轮没走完」那一句（`kernel/request.md`「组装」）。她没看到过这一轮；写了，失败、打断以后下一轮前面多一句「这一轮出错了」，她会当成是上一轮。摘要请求的 `model.called` 本来就不进上下文。
9. 回合结束的挂接点照常跑（广播，不等）。
10. 手动的不算「压完很快又到线」（第十条第 5 条）：不写 `refills`，之后自动压缩的 `refills` 从头数。成了以后检查点换了，以前的失败、暂停都写在它前面，自动压缩恢复（第十条第 6 条）。

**八、检查点长什么样**

投影里，被替代的那一段换成一条 user 消息，照这个先后；尾巴原样跟在它后面：

1. 包装的开头（`resources/core/checkpoint-open.txt`，已有）。
2. 摘要正文。

**内核和执行器怎么交接**（施工 6-5，照撤销时改回文件那一对的样子：内核不碰磁盘）：

1. 发摘要请求时，窗口够、有候选的，内核在「请求模型」前面先交出「重读」`Action::Reread { seen, paths, limit }`：`seen` 是这次摘要请求的；候选照第 1 条的先后，最多 10 个（挑满 5 个要留余地），路径是效果里换成真实位置以后的；`limit` 是单个的上限折成的字节（5000 × 4）。没有候选、窗口不够的，不交。
2. 执行器照动作的先后做：先在阻塞线程里一个一个读完，再发摘要请求，读的这一会儿不收收件箱。照安全打开，超过 `limit` 的不读完、报太大，读到的存成 blob。交回 `Input::Reread { at, seen, files }`，一个一项，照交出去的先后：读到了（`blob`、原文）、太大、读不到。内核记在这次摘要请求上；不是在路上的那一次的，不理。存了没挑中的 blob 没人引用，等 blob 的回收收走（`07-存储.md` 第五节，还没做）。
3. 取到摘要以后，内核照先后挑：读到了的、估出来不超过 5000 token 的，一个一个加，合计不超过 50000，加上以后整份请求的估算不超过压缩线的一半，挑满 5 个为止。太大的进清单。然后写 `context.compacted`（带 `notes`、`restored`），推 `compaction.done`，接着组装主请求。`restored` 每一项的 `tokens` 是这份原文估出来的。没收到重读结果的（执行器没做），照没有候选写。
4. 摘要请求被打断、要重启的，和以前一样什么都不写：重读的结果跟着这次请求一起丢掉。
5. 重读的原文不进日志，日志里只记 blob。内核在 `History` 里拿着现在这个检查点那几份的原文，组装时照 blob 取。检查点换了、原文不在内存里的时候（载入以后、撤掉了压缩、恢复了压缩，第十一条），内核出「取回原文」`Action::Recall { blobs }`：新检查点 `restored` 里每一份的 blob，照先后；没有重读过文件的不出。执行器照 blob 读出原文，交回 `Input::Recalled { texts }`，做完才收收件箱（`kernel/history.md`「重读的原文」）。读不出来的那一份，渲染时整块不写。
3. 以后有了的也照这里带上：用过的技能（单个 5000、合计 25000 token，最近用过的优先）、计划、待办、没回答的提问（M8 做出来时加）。还在跑的后台命令和子代理不带，交给摘要记（施工 7-8 补，第八条第 4 条）。

**十、失败和熔断**（施工 6-6 上）

1. 一次压缩失败：超长重试 3 次还是超长（6-6 下）；供应商出错（驱动的出错分类照常重试完了）；摘要取出来是空的、调了工具（隔离式做好以前，6-6 下）；被动压缩重发还是超长（6-7）。
2. 失败的那一次：这一轮照出错结束，原因在摘要请求的 `model.called` 里。
3. **怎么从日志认出一次失败**：一轮以 `error` 结束，它最后一条 `model.called` 带着 `compaction`，是 `auto` 或者 `overflow`，结果是 `error`；或者（施工 6-7）最后一条是主请求报 `context_too_long`，而最近一次压缩是这一轮里的被动压缩（压完重发还是超长）。打断、重启、崩了的不算；别的主请求出的错不算；手动压缩失败不算：人就在跟前，他自己看得到。
4. **连续失败 3 次**：有效历史里、最近一次压缩那一条以后写下的这样的回合，数到 3，在这一轮的 `turn.ended` 前面写 `context.compaction_paused`，`reason` 是 `failures`（2026-09-29 项目主人定：停到人处理）。
   - 成功压缩一次，以前的失败都写在它前面，次数自然清零。只看写下的先后，不看在不在检查点后面：失败的那几轮她没真看到的话，照第三条第 2 条留在尾巴里，那几轮的失败照样不算（施工 6-6 上场景测试撞到的）。
5. **内容异常**：到线、切点也定好了，要压之前算这一次是不是「压完很快又到线」：
   - 上一个检查点所在的那一轮算第 1 个回合，这一轮是第 3 个以内的（策略的 `turns`），就是。同一轮里一步接一步地压也照这样算：6-3（下）真模型上窗口设得很小（压缩线 12000），压完她又把刚读过的 1.2 万 token 的文件读回来核对，读完又到线，一轮里压了 9 次还没答。
   - 是的，`refills` 是上一个检查点的加一（没有的算 0），写进这次的 `context.compacted`；不是的不写。`refills` 是写下时的事实，撤销回到前一个检查点时照它原样用。
   - 算出来到了 3（策略的 `refills`）：不压，写 `context.compaction_paused`，`reason` 是 `too_large`，`entry` 是有效历史里检查点后面（尾巴也算）估得最大的那一条（照第一条第 2 条的数法，一样大的取早的），告诉人是哪一条太大（`09-压缩.md` Z9）。回到准备好，落了盘再来，这时已经暂停着了。
6. **暂停着**：有效历史里、最近一次压缩那一条以后写下了 `context.compaction_paused`。
   - 到线不压；明知会超长的请求不发（第二条第 5 条）。
   - 告诉人可以怎么办：手动压缩、换一个模型、开新会话（「给人看的字」）。
   - 暂停着也收手动压缩（第七条）、清空（第十四条）。人手动压缩成功、清空了，检查点换了，暂停在它前面，恢复自动压缩（6-8、6-8 补）。撤掉写着暂停的那一轮，暂停跟着撤掉。
   - 全从有效历史算：载入、重启不另记，和不重启一样。
7. 无人值守的场所（随通讯平台）：不暂停，改成裁剪一次（第五条），同时通知管理员（2026-09-29 项目主人定，照推荐）。

**十一、撤销和压缩**（2026-09-29 项目主人提：压缩也是一次请求，应该能撤销。施工 6-9 定的细节在 `kernel/history.md`「撤掉压缩」「从日志的一段重建」「重读的原文」）

1. 压缩跟着它所在的回合：自动的、被动的，在引起它的那一轮里；手动的、清空的，单开一轮（第七条、第十四条）。`context.compacted` 一定带 `turn`，账本查：不在回合里的压缩没有哪一轮能把它撤掉，它替代掉的回合也就撤不了。
2. 撤销一轮，和它以后的每一轮一起撤，里面的压缩跟着撤掉：有效历史回到那之前最近一次还算数的压缩（一次都没有的，从头），加上它后面没撤掉的。所以撤销能撤掉压缩，撤到压缩以前的回合也行，原因码 `compacted` 不再用。
   - **还算数的压缩**：它所在的那一轮还在有效历史里。账本记着每一次还算数的压缩在哪一轮、替代到哪；撤销拿走的压缩记在那一次撤销上，恢复时放回。
   - 写进一份摘要的回合都在那次压缩以前，撤它们的时候那次压缩也在撤的范围里，没有「摘要里还留着它」的问题（`09-压缩.md` 第九节）。
   - 撤的范围里没有还算数的压缩的，照以前的撤法，不读磁盘。
3. 恢复照旧：下一轮开始之前能恢复，撤掉的压缩跟着回来，不重新请求模型，也不读磁盘：放在一边的就是撤掉的那几轮连同里面的压缩，放回去以后有效历史落到最近的那一次压缩上。
4. **撤掉压缩时内核和执行器怎么交接**（照撤销时改回文件、压完重读的样子：内核不碰磁盘）：
   1. 内核出「读回日志」`Action::ReadBack { from }`：`from` 是撤完以后还算数的最近一次压缩替代到的下一条，一次都没有的从第 1 条。这一会儿来的命令拒绝，`restoring`；会话不算空闲。
   2. 执行器只读地读这个会话的日志，从第 `from` 条到最后一条，交回 `Input::ReadBack { at, from, events }`，读完才收收件箱。读不了的，会话停下（`session/actor.md`）。
   3. 内核拿这一段重建有效历史，记 `turn.reverted`，再落到检查点上；接着照常算改回文件的几步。对不上的（起点不对、没连到最后一条）当过时的不理。
   4. 平时内存里照旧只留最近一次压缩以后的（`07-存储.md` 第七节）。读回来的那一段里撤掉的放在一边，下一轮开始才丢：撤掉的压缩多，放在一边的也多。
5. 载入时先把整份日志过一遍账本，认出哪一次压缩还算数，有效历史从它替代到的下一条起重建（`kernel/session.md`「载入和崩溃」）。
6. 撤掉压缩以后，前一个检查点重新算数：它重读过的文件，内核出 `Recall` 取回原文（第九条「内核和执行器怎么交接」第 5 条）。恢复了压缩的、载入以后的也一样。
7. 撤掉压缩以后，请求回到压缩前的样子：这段前缀刚被摘要请求用过，多半还在供应商的缓存里。用量又在线上，下一次发请求之前照常再压一次（又一次摘要请求）。人可以趁这时换一个窗口大的模型、手动压缩附上要求，或者多撤几轮。
8. 撤的是回合开头就到线压的那一轮：触发它的话照撤销的规矩一起撤（`kernel/history.md`「拿走什么」）。重做这样的一轮（施工 4-7 再补）：照这一条先读回、撤掉压缩，再重发那几句话；新的一轮开头照常到线再压。手动压缩、清空单开的那一轮没有触发，不能重做（`not_redoable`，`kernel/history.md`「重做」）。
9. `miyu undo` 撤掉了压缩的，说一句（「给人看的字」）：撤销的回应里多一格 `compactions`，撤掉了几次；撤掉几次都说同一句（`protocol/undo.md`、`cli/undo.md`）。恢复不说。清空不数在这里，另有 `clears` 和那一句（第十四条第 7 条）。
10. 想回到压缩以前、又想留着后来的几轮：从那里分叉（`03-事件模型.md` 第七节，还没有）。

**十二、压缩期间**

- 压缩是会话自己的事，在这个会话的 actor 里做，不阻塞别的会话（旧版撞过）。
- 压缩期间来的新消息照常落进日志，排在 N 之后，照排队的规矩排着。
- 人打断：压缩取消，什么都不写；这一轮照打断收尾。

**十三、度量**

每次压缩记一行 `INFO`（`log.md`），会话 actor 转推 `compaction.done` 时记（6-3 下）：

```text
INFO  session  <会话> compacted seen=24 trigger=auto before=15465 after=2675 summary_in=14147 summary_cached=2816 summary_out=2666 took_ms=11816
```

- `seen` 哪一次摘要请求；`trigger` 为什么压，照 `compaction.done` 的 `trigger`（`auto`、`manual`，施工 6-8）；`before`、`after` 压前、压后的估算。

- 截过几次、重读了几个文件随 6-6、6-5 加。
- 清空不记这一行：没有摘要请求，不推 `compaction.done`（第十四条）。

**十四、清空**（`trigger` 是 `clear`，施工 6-8 补）

1. `session.clear`，空闲时才收：有回合在进行的拒绝，`turn_running`；正在改回文件的拒绝，`restoring`。自动压缩暂停着也收。
2. **上下文本来就是空的**，拒绝，`nothing_to_clear`：有效历史里没有检查点，或者最近的检查点就是清空的，而且它后面没有人的消息、回复、工具结果、回报。
   - 最近的检查点是一份摘要的（自动、手动、被动压的），后面什么都没有也收：摘要还在上下文里，这时拒绝说「上下文为空」不对。回报也算：它们进上下文（`kernel/request.md`「回报」）。这两条 2026-09-30 施工 6-8 补时定。
   - 事实、回合的开头结尾不算：清了，下一轮开头照样注入、照样有。
3. **单开一轮**，一批三条，`by` 都是内核，`cause` 都是这个命令：
   - `turn.started`：没有 `trigger`，`cwd`、`dirs` 照会话现在的环境写；
   - `context.compacted`：`trigger` 是 `clear`，`upto` 是这一轮开头以前的最后一条（这时追加过的最后一条），`summary` 是空的，没有 `instructions`、`notes`、`restored`、`refills`；
   - `turn.ended`：`completed`。
   不请求模型、不注入事实、不换实际生效的权限、不跑回合开始的挂接点，回合结束的挂接点照常跑（广播，不等）。记在一边的回报跟着清掉，不再由它们另开一轮（`kernel/session.md`「回报」）。一批都落了盘才回应，附上 `turn.started` 的序号。
4. 不推 `compaction.progress`、`compaction.done`，运行日志不记 `compacted` 那一行：没有摘要请求，也就没有压前压后的用量、摘要请求的用量。
5. **渲染**：清空的检查点什么都不出，单开的那一轮也不出（没有 `trigger`，第七条第 8 条）。清空以后的第一次请求只剩工具面、system、那一轮开头注入的环境、权限、会话编号几块事实（检查点后面没有，比不到，照常注入）和触发它的那句（`kernel/request.md`「组装」第 2 条）。
6. **熔断**：没有摘要请求，不会失败，不数；检查点换了，以前的失败、暂停都写在它前面，自动压缩恢复（第十条第 6 条）。清空的不写 `refills`，之后自动压缩的 `refills` 照第十条第 5 条从它数起，和手动的一样。
7. **撤销、恢复**照第十一条：清空那一轮是一轮，撤掉它，检查点跟着撤掉，读回更早的日志，上下文回到清空以前；恢复把它放回来，又是空的。下一轮开始、再压缩以后恢复不了。撤销的回应里另有一格 `clears` 数它，`compactions` 不算它；`miyu undo` 撤掉的几轮里有清空的，说「撤掉了清空，上下文回到了清空以前」，和撤掉了压缩那一句都有的先压缩后清空（`protocol/undo.md`、`cli/undo.md`，2026-09-30 项目主人定）。
8. `history` 照样找得到清空以前的（`tools/history.md`：日志照样留着）；清空的检查点摘要是空的，不算一条。
9. 不做：命令行上的清空命令（`miyu ask` 本来每次都开新会话）；QQ 的 `/reset` 随通讯平台。
