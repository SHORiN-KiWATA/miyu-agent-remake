## 压缩

### 是什么

上下文快满时，请她把旧内容写成一份摘要，换掉旧内容，最近的一段原文（尾巴）留着，腾出地方接着干。只在不够用时压，一压就压一大段：每压一次，请求的前缀就重置一次（`09-压缩.md` 第一节）。

压缩不删日志里的任何一条。要看旧内容，她用 `history` 取回（`tools/history.md`）。压缩发生在一个回合里，撤销这一轮，压缩跟着撤掉，上下文回到压缩前的样子（第十一条）。整套做法以 Claude Code 为准（`09-压缩.md`）。

另有一种不请求模型的办法：**裁剪**（trim），把最老的几轮整块移出，由代码写一句说明。它给群聊用，随通讯平台做（第五条）。

### 怎么走

**一、量用量**

1. 用量 = 锚 + 锚以后新进有效历史的内容的本地估算。Claude Code、codex、pi、dsh 都是这个结构。不全靠本地估：旧版整段用 o200k 分词器数，比 DeepSeek 报的系统性少约两成（77 个样本），长会话里一遍要一两秒。
   - **锚**：有效历史里，最近一次压缩那一条之后的 `model.called` 中最近的一条，`result` 是 `ok`、带 `usage`；取供应商报的 `uncached + cache_read + cache_write + output`。每次请求都有，一轮当中也有锚。压缩那一条之前的不算：摘要请求自己那条、尾巴里压缩以前的请求，报的都是压缩前的大小。
   - **锚盖住哪些**：锚那次请求有 `messages` 条消息，它的回复是这一次请求的第 `messages` 条（从 0 数）。请求只追加，所以这一次请求的工具面、system、前 `messages + 1` 条，就是锚盖住的；后面的是新增的，本地估。
   - 本地对锚盖住的那些的估算，比供应商报的还大：取估算（照 dsh，宁多勿少）。
   - 整份用本地估算：没有锚；锚的端点、模型和这一次要发的不一样（换过模型，照 dsh）；这一次请求的消息没比锚多（兜底）。
2. 本地估算：一条消息里文字、思考、工具调用的名字和参数、工具结果的文字、驱动的私有数据和认不出的块的原样 JSON，UTF-8 字节加起来除以 4，向上取整（照 codex 的 `APPROX_BYTES_PER_TOKEN = 4`，2026-09-29 项目主人定）；图片照驱动的算法，没有的一张按 2000；文件一个按 2000。工具面照规范的 JSON 字节、system 照字节，都除以 4 向上取整。不另加每块、每条的结构开销。
   - 照 DeepSeek 文档的比例（英文一个字符约 0.3 token、中文约 0.6），中文多估约两成半，英文少估约一成半。只估锚之后那一截，少估的落在余量里；真漏了有被动压缩兜底。
   - 未选：除以 3。中文多估约三分之二，压得偏早。Claude Code、pi 的字符数除以 4 在中文上少算三四倍。
   - 6-3 用 DeepSeek 实测中文、英文、代码、图片各一组，本地估算和供应商报的对比。
3. 压缩以后还没请求过的，整份请求（工具面、system、检查点、之后的内容）都用本地估算。摘要请求的 `model.called` 排在检查点前面，不拿来当锚。

**二、什么时候压**

1. 每次发主请求之前查：回合的第一次请求之前，每一步的工具结果齐了以后，出错再来的也查。再来的请求可能多了半截回复和被打断的那一句；什么都没多的，上一次发之前查过，不会到线。
2. **压缩线** = 窗口 − 输出预留 − 余量。用量超过它就压。算出来不是正数的（窗口不到 33000），当作没有线，不主动压。
   - 输出预留 = min(模型的最大输出, 20000)，余量 13000，和 Claude Code 的「有效窗口减 13000」一样。
   - 摘要请求 = 用量 + 摘要指令 + 输出预留。余量比摘要指令长得多，所以到线时摘要请求一定放得下（`09-压缩.md` Z3）。
   - 一步长得比余量还多的（例如一次读进一个很大的文件）：下一次发请求之前照样到线就压；摘要请求本身放不下，走第三条第 10 条截掉最老的再试；供应商报超长，走被动压缩（第六条）。
3. 设了 `compaction.max_context` 的，压缩线取它和上面那条里小的（随配置那一步）。
4. 模型的资料没报窗口的，不主动压。
5. 自动压缩暂停着的（第十条）：不压；用量加输出预留超过窗口、明知会超长的请求不发：记一条没发出去的 `model.called`（没有 `endpoint`、`model`、`request`，分类 `compaction_paused`，原话 `the request would not fit: <用量> tokens used + <预留> reserved for output > window <窗口>`），这一轮照出错结束；排着队的话她没听到，和摘要请求失败时一样，照排队的规矩接着开下一轮。没超的照发（施工 6-6 上）。

**三、压缩这一步：fork 式**

1. 压缩是这一轮里的一步：回合停在压缩上，发一次摘要请求，收回来写 `context.compacted`，再照常组装、发这一步本来要发的请求。一步至多压一次：压完还在线上的，照发（施工 6-2 下）；发了主请求，下一步又能压。摘要请求说完了，这一步连着出错的次数不清零：重试和主请求合用一个计数。
2. **替代到哪**（`upto`，下面叫 N）：
   - **留尾巴**（2026-09-29 项目主人定，重开 `09-压缩.md` Z4）：从最新的往回数，一组一组地留，留到 16000 token 为止（不超过压缩线的四分之一）。一组是一条人这边的消息（连同跟着它的事实），或者一条助手消息连同它的工具调用和结果；不拆开一组。N 是尾巴前面的那一条。
   - 照投影的先后（`History::ordered`）看，一组从一条人的消息或者一条助手的回复开始，两组之间的别的事件（回合开始、事实、工具结果、模型调用、回合结束）跟着前面那一组。只在切得开的地方切：前面的序号都比后面的小，第 N 条及以前正好是投影的开头一段，摘要请求才是上一次请求的前缀（施工 6-2 下）。请求在路上时来的话，序号比回复小、投影里排在回复后面，那里切不开，这一组并进前面那一组。每条事件照第一条第 2 条的数法估：人的消息、回复、工具结果照内容块，事实照原文，别的算 0。预算 = min(16000, 压缩线的四分之一)；16000 是策略数据（快照里的 `tail`）。
   - 最后一组本身就超过尾巴的预算：不留尾巴，N 是日志的最后一条。
   - 和下面「这一轮要回应的话」合在一起：N 至多是那条边界前面那一条，尾巴只会让 N 往前挪；再照「一组不拆」往前退。
   - **这一轮要回应的话**：以前的回合里的请求没看到过、这一轮的回复也没看到过的人的消息；这一轮还没有回复的，加上触发它的那一条。这一轮里认回复不认请求：请求出错、没回复的，她没真看到。以前的回合里请求看到过的，照常压：那一轮已经过去了，摘要请求也才接得上上一次请求的前缀。
   - **边界**：这些话里最早的那条。有边界的，N 至多是边界前面那一条；没有的（回合中途，也没有排着队的新话），N 至多是落了盘的最后一条。
   - N 落在一条回复和它的工具结果之间的，退到这条回复前面（一组不拆）：回合中途排着的新话，序号在这一步的结果前面。
   - 有效历史里第 N 条及以前没有人的消息、回复或工具结果的，不压，照旧发主请求（压了也腾不出地方，还会一直压下去）。N 不比上一次压缩的 `upto` 晚的也是这样：那以前的早就替代掉了。
   - 回合开头（第一次请求之前）：这一轮要回应的话一定在尾巴里，超了预算也留。它们是触发这一轮的那句，连同由上一轮排着队接过来的几句（`kernel/history.md`「拿走什么」认的那几句），和这一轮开头注入的事实。所以这一轮第一次请求的最后一块，照旧是触发它的那句（`08-上下文投影.md` 第七节）。
   - 被动压缩：见第六条。
3. **请求** = 有效历史到第 N 条为止的投影，原样，加一条 user 消息放摘要指令（`summarize-task.txt`）。这一段是上一次请求的前缀，几乎全部命中缓存。尾巴不进摘要请求，摘要和尾巴不重复；摘要指令里说一句：这之后最近的一段会原样留着。这是 Claude Code「压到某一条为止」那种局部压缩的做法。
4. 用会话自己的驱动、模型、端点。缓存在端点上，换一家就全部落空（旧版撞过）。
5. 工具照样声明，思考的设置照样带，输出上限照会话原来的请求带：前缀要一字不差。不让她调工具：摘要指令开头、末尾写明只许输出文字。不带 `tool_choice: none`：6-3（下）在 DeepSeek 上实测，同一个 9045 token 的带工具请求，带不带都命中 8832，不掉缓存；可是也挡不住，一句「用 read 打开 README.md」带了照样调 `read`。她要是调了工具，照第 7 条。
6. **取摘要**：回复先是 `<analysis>` 草稿，再是 `<summary>` 摘要。只看正文块，思考不要。先去掉草稿：草稿里会顺嘴提到 `<summary>` 这个标签（`Now writing the <summary>.`），从那儿取就把草稿的尾巴带进了摘要（6-3 下真模型两次都这样）。剩下的有 `<summary>` 的，取它到最后一个 `</summary>` 之间的：摘要里引的 HTML 也有 `</summary>`，真收尾的在最后；没有收尾的（输出到了上限）取到末尾。没有 `<summary>` 的，剩下的当摘要。草稿没收尾的，摘要写在它里面的从最后一个 `<summary>` 起留下，没有的到末尾都算草稿。前后空白去掉，取出来是空的，算失败：`model.called` 记成出错，分类 `bad_summary`。
7. 回复里有工具调用：这一次作废，改走隔离式（第四条）。隔离式做好以前（6-6），算失败，记法同上。
8. **进度**：摘要请求报发出去时先推一条 `written` 是 0 的 `compaction.progress`，头一收到就能印「正在压缩」；之后收到的正文（草稿加摘要）照字数推；`expected` = 压缩前用量折成的字数，夹在 20000 到 80000 之间（openclaude 的做法）。
9. **不设总超时**：流一直在出字就等着，界面上有进度，人可以打断；卡住不出字的，由 HTTP 的空闲超时管（`http.md`：连接 30 秒、空闲 180 秒，没有总超时，6-3 下核对过）。旧版写死 90 秒，长会话一压就超时。
10. **摘要请求本身超长**（供应商报超长）：
    1. 报错里解析得出超了多少 token 的：检查点留着，从它后面最老的一轮起，一整轮一整轮去掉，去掉的估算加起来刚好盖过超出的量。
    2. 解析不出来的：去掉最老的 20% 的轮，至少一轮。
    3. 至少留一轮。去掉以后第一条是助手的，前面补一行说明：更早的对话为了压缩被截掉了（`truncated.txt`）。
    4. 最多试 3 次。截过的，`notes` 里写明摘要没有覆盖到哪一段（第八条）。
    5. 截过以后前缀变了，这一次不再命中缓存，照常发。
11. **写 `context.compacted`**：`turn` 是这一轮，`by` 是内核，`cause` 是回合的。同时推瞬时的 `compaction.done`（见「对外的样子」）。之后照常组装下一次请求：环境、权限两块事实和检查点后面还在的同类比，比不到的注入（`kernel/request.md`「事实」）。
12. 摘要请求照常记一条 `model.called`，`seen` 是 N。

**四、压缩这一步：隔离式（回退）**

- 什么时候用：驱动不能复用前缀的（例如以后借别家 agent CLI 的驱动）；fork 式的回复里她调了工具的。
- 请求：一句极简的 system（`summarize-system.txt`），不带工具，思考关掉。待压缩的内容（有效历史到第 N 条的投影里的消息）写成一段文字，放进一条 user 消息：每段标明角色；工具调用只写工具名和参数的键名；图片、文件换成占位。最后接摘要指令。
- 不带只读的读取工具（Claude Code 的回退带着 `Read`）：带了工具，摘要请求就成了一个会调工具的小回合，要多一套派工具、收结果的路；最近的文件压后会重读（第九条）。
- 取摘要、进度、超长重试照第三条。

**五、裁剪（trim，随通讯平台）**

1. 切点：从最老的一轮起，一整轮一整轮地移出，移到用量剩压缩线的一半左右为止。不拆开工具调用和结果，不拆开同一条助手消息。
2. 不请求模型。`summary` 是空的，`mode` 是 `trim`，`notes` 是代码写的说明（`trimmed.txt`）。
3. 不重读文件：留下的后一半本来就是原文。
4. 瞬间完成，没有失败，也就没有熔断。
5. 默认用在群聊，各场所可以改（2026-09-29 项目主人定；叫法「裁剪（trim）」也是他定的，和旧版一致）；无人值守的场所压缩失败时也改成裁剪一次（第十条）。

**六、被动压缩**（`trigger` 是 `overflow`）

1. 供应商报上下文超长（驱动的分类 `context_too_long`）：这一步改成先压缩，再重发一次，只重发一次。
2. 已经收到了输出的不压、不重发，照出错结束这一轮：免得半截回答、重复执行有副作用的操作。
3. 尾巴照第三条第 2 条留，至少留最后一组：最后一条助手消息，连同它的工具调用和结果。尾巴里的思考照驱动平时回放历史的规矩带：DeepSeek 带工具时每一轮的思考都要回传，剥掉会报 400（Claude Code 在这里剥掉思考，这里不照它）。
4. 压完重发还是超长，这一轮照出错结束，算一次失败（第十条）。

**七、手动压缩**（`trigger` 是 `manual`）

1. `session.compact`，空闲时才收。
2. 单开一轮，只做压缩：`turn.started` 没有 `trigger`，`by` 是内核，`cause` 是这个命令。不注入事实，不跑回合开始的挂接点。尾巴照第三条第 2 条留，和自动压缩一样（2026-09-29 定，照推荐）；想从头来，开新会话。
3. 人附的要求接在摘要指令后面（`Additional Instructions:` 后面），原样记进 `instructions`。
4. 写完 `context.compacted`，这一轮结束，`completed`；失败的照出错结束，`error`。
5. 人打断：压缩取消，什么都不写，这一轮 `interrupted`。
6. 压缩期间来的消息照排队的规矩排着，这一轮结束以后接着开下一轮（`kernel/session.md`「排队的消息」）。
7. 有计划的重启打断的这一轮，再起来不接着压：人再要一次就是。

**八、检查点长什么样**

投影里，被替代的那一段换成一条 user 消息，照这个先后；尾巴原样跟在它后面：

1. 包装的开头（`resources/core/checkpoint-open.txt`，已有）。
2. 摘要正文。
3. 摘要的收尾（`resources/core/checkpoint-close.txt`：`</summary>`；施工 6-5 把原来一起写在里面的规则那一句挪到了第 6 条，没有第 4、5 条的会话，请求的字节不变）。
4. 代码写的几段（`notes`，施工 6-5）：写的时候照模板拼好，原文存进事件，以后逐字节回放。
   - 读过、改过的文件清单：照被替代的那一段里的效果算（`file.read`、`file.changed`），不照工具名猜，旧版照工具名猜，一个都没认出来。最近的在前，去重，最多 30 个，多的写还有几个（`compaction/notes-files.txt`、`notes-files-more.txt`）。路径在会话现在的工作目录里的写相对的，别的写绝对的。
   - 取回指路：被替代的是第 1 到 N 条，原文还在日志里，用 `history` 按序号、关键词、时间取回（`compaction/notes-retrieve.txt`）。6-4 真模型上她不知道序号，只能从头往下翻。
   - 压前读过、太大没重读的文件，写明要看自己读（`compaction/notes-too-large.txt`）。
   - 摘要请求截过最老的一段的，写明没有覆盖到哪一段（6-6）。
5. 重读的文件（`restored`，施工 6-5）：照挑中的先后，每个一块：`compaction/restored-open.txt`（`<file path="…">`，路径照清单的写法）、原文（照 blob，不转义）、`compaction/restored-close.txt`（`</file>`）。
6. 包装的结尾（`resources/core/checkpoint-end.txt`：规则那一句和 `</conversation-checkpoint>`）。

- 环境和状态（时间、工作目录、权限级别）不在检查点里：压缩后的第一次请求照事实注入的规矩各注入一块，紧跟在检查点后面（第三条第 11 条）。
- 检查点的规则写在包装的结尾，不进 system（6-3 下照 `26-提示词.md` J12 实测定的）：`Carry on from where the summary leaves off, without redoing work it records as done.`，19 个 token，只有压缩过的会话带。
  - 先什么都不加，回合开头压、回合中途压各跑了 8 次（加没加那一句的都算）。她一次都没有复述摘要，也没有停下来问要不要接着做。
  - 可回合中途压完，这一轮的最后一条只有检查点和事实，没有一句话告诉她这时该做什么（回合开头压的，触发这一轮的那句在尾巴里，没有这个问题）。4 次里她都把摘要里记着读完了的文件再读一遍核对（「环境像是重置了，读一遍稳妥些」）；窗口设得很小，文件读回来又到线，有一次一轮压了 5 次。
  - 加上结尾这一句，3 次都照摘要直接答，一轮只压 2 次，输入从 4.5 万到 9.6 万降到 4.3 万左右。
  - 原来备着的 system 规则 `core/checkpoint-rule.txt` 因此不用，施工 6-4 删掉了（2026-09-29 项目主人定）。
- 摘要里会写到摘要指令本身：她把它当成用户的最后一句话，记进「All user messages」，还写「现在这一轮是要摘要」。6-3 下试过两种说法都没用（第 6 节加「不算这一条」、开头加「这一条不是对话的一部分，别写进摘要」），摘要照样写，已经撤掉。它只让她多想几句，没有让她做错事：包装结尾那一句说了接着做什么。压缩质量评测（6-10 以后）再看。
- 只有用户角色的消息才算用户说的话：摘要指令里写明，工具输出、模型回复里写着「User:」的不算。

**九、压后重建**（只在压缩时，裁剪不重建）

1. 最近读过、改过的文件，照日志里效果的先后，最近的优先：
   - 最多 5 个；单个 5000 token，超了不重读，只进清单（第八条）；合计 50000 token，放不下的跳过。
   - 尾巴里已经有完整内容的，跳过：施工 6-5 照「尾巴（第 N 条以后）里读过、改过这个文件的」算，尾巴里有她最近看到的那一版或者改动。只读了一段的也算，宁可少重读一个。
   - 从磁盘重读，照 `fs.md` 的安全打开；读不到的（删了、没权限、不是普通文件、不是 UTF-8）跳过，清单照写。
   - 重读的内容存成 blob，哈希记进 `restored`，重放时逐字节相同。
2. 封顶：重读以后，压完的整份请求（工具面、system、检查点、事实、尾巴）的估算不超过压缩线的一半，放不下的跳过。窗口在 32000 token 以下的不重读，只写清单和取回的办法。

**内核和执行器怎么交接**（施工 6-5，照撤销时改回文件那一对的样子：内核不碰磁盘）：

1. 发摘要请求时，窗口够、有候选的，内核在「请求模型」前面先交出「重读」`Action::Reread { seen, paths, limit }`：`seen` 是这次摘要请求的；候选照第 1 条的先后，最多 10 个（挑满 5 个要留余地），路径是效果里换成真实位置以后的；`limit` 是单个的上限折成的字节（5000 × 4）。没有候选、窗口不够的，不交。
2. 执行器照动作的先后做：先在阻塞线程里一个一个读完，再发摘要请求，读的这一会儿不收收件箱。照安全打开，超过 `limit` 的不读完、报太大，读到的存成 blob。交回 `Input::Reread { at, seen, files }`，一个一项，照交出去的先后：读到了（`blob`、原文）、太大、读不到。内核记在这次摘要请求上；不是在路上的那一次的，不理。存了没挑中的 blob 没人引用，等 blob 的回收收走（`07-存储.md` 第五节，还没做）。
3. 取到摘要以后，内核照先后挑：读到了的、估出来不超过 5000 token 的，一个一个加，合计不超过 50000，加上以后整份请求的估算不超过压缩线的一半，挑满 5 个为止。太大的进清单。然后写 `context.compacted`（带 `notes`、`restored`），推 `compaction.done`，接着组装主请求。`restored` 每一项的 `tokens` 是这份原文估出来的。没收到重读结果的（执行器没做），照没有候选写。
4. 摘要请求被打断、要重启的，和以前一样什么都不写：重读的结果跟着这次请求一起丢掉。
5. 重读的原文不进日志，日志里只记 blob。内核在 `History` 里拿着最近一个检查点那几份的原文，组装时照 blob 取。载入以后，执行器照最近一个检查点的 `restored` 从 blob 读出原文，造会话、载入以后在别的输入之前交一条 `Input::Recalled { texts }`，和交限额一样。读不出来的那一份，渲染时整块不写。
3. 以后有了的也照这里带上：用过的技能（单个 5000、合计 25000 token，最近用过的优先）、计划、待办、还在跑的后台命令和子代理、没回答的提问（M7、M8 做出来时加）。

**十、失败和熔断**（施工 6-6 上）

1. 一次压缩失败：超长重试 3 次还是超长（6-6 下）；供应商出错（驱动的出错分类照常重试完了）；摘要取出来是空的、调了工具（隔离式做好以前，6-6 下）；被动压缩重发还是超长（6-7）。
2. 失败的那一次：这一轮照出错结束，原因在摘要请求的 `model.called` 里。
3. **怎么从日志认出一次失败**：一轮以 `error` 结束，它最后一条 `model.called` 带着 `compaction`，是 `auto` 或者 `overflow`，结果是 `error`。打断、重启、崩了的不算；主请求出的错不算；手动压缩失败不算：人就在跟前，他自己看得到。
4. **连续失败 3 次**：有效历史里、最近一次压缩那一条以后写下的这样的回合，数到 3，在这一轮的 `turn.ended` 前面写 `context.compaction_paused`，`reason` 是 `failures`（2026-09-29 项目主人定：停到人处理）。
   - 成功压缩一次，以前的失败都写在它前面，次数自然清零。只看写下的先后，不看在不在检查点后面：失败的那几轮她没真看到的话，照第三条第 2 条留在尾巴里，那几轮的失败照样不算（施工 6-6 上场景测试撞到的）。
5. **内容异常**：到线、切点也定好了，要压之前算这一次是不是「压完很快又到线」：
   - 上一个检查点所在的那一轮算第 1 个回合，这一轮是第 3 个以内的（策略的 `turns`），就是。同一轮里一步接一步地压也照这样算：6-3（下）真模型上窗口设得很小（压缩线 12000），压完她又把刚读过的 1.2 万 token 的文件读回来核对，读完又到线，一轮里压了 9 次还没答。
   - 是的，`refills` 是上一个检查点的加一（没有的算 0），写进这次的 `context.compacted`；不是的不写。`refills` 是写下时的事实，撤销回到前一个检查点时照它原样用。
   - 算出来到了 3（策略的 `refills`）：不压，写 `context.compaction_paused`，`reason` 是 `too_large`，`entry` 是有效历史里检查点后面（尾巴也算）估得最大的那一条（照第一条第 2 条的数法，一样大的取早的），告诉人是哪一条太大（`09-压缩.md` Z9）。回到准备好，落了盘再来，这时已经暂停着了。
6. **暂停着**：有效历史里、最近一次压缩那一条以后写下了 `context.compaction_paused`。
   - 到线不压；明知会超长的请求不发（第二条第 5 条）。
   - 告诉人可以怎么办：手动压缩、换一个模型、开新会话（「给人看的字」）。
   - 人手动压缩成功，检查点换了，暂停在它前面，恢复自动压缩（6-8）。撤掉写着暂停的那一轮，暂停跟着撤掉。
   - 全从有效历史算：载入、重启不另记，和不重启一样。
7. 无人值守的场所（随通讯平台）：不暂停，改成裁剪一次（第五条），同时通知管理员（2026-09-29 项目主人定，照推荐）。

**十一、撤销和压缩**（2026-09-29 项目主人提：压缩也是一次请求，应该能撤销）

1. 压缩跟着它所在的回合：自动的、被动的，在引起它的那一轮里；手动的，单开一轮（第七条）。
2. 撤销一轮，和它以后的每一轮一起撤，里面的压缩跟着撤掉：有效历史回到那之前最近一次还算数的压缩（一次都没有的，从头），加上它后面没撤掉的。所以撤销能越过压缩，原因码 `compacted` 不再用。
3. 恢复照旧：下一轮开始之前能恢复，撤掉的压缩跟着回来，不重新请求模型。
4. 越过压缩时，内核要用的更早的那一段（被替代的事件、那几轮的效果）不在内存里：内核交给执行器从磁盘读回来，读回来再算，和改回文件一样一来一回，内核照旧不碰 I/O。平时内存里照旧只留最近一次压缩以后的（`07-存储.md` 第七节）。
5. 载入时先看完整份日志里的撤销、恢复，认出哪一次压缩还算数，有效历史从它算起。
6. 撤掉压缩以后，请求回到压缩前的样子：这段前缀刚被摘要请求用过，多半还在供应商的缓存里。用量又在线上，下一次发请求之前照常再压一次（又一次摘要请求）。人可以趁这时换一个窗口大的模型、手动压缩附上要求，或者多撤几轮。
7. 撤的是回合开头就到线压的那一轮：触发它的话照撤销的规矩一起撤（`kernel/history.md`「拿走什么」）。
8. 想回到压缩以前、又想留着后来的几轮：从那里分叉（`03-事件模型.md` 第七节，还没有）。

**十二、压缩期间**

- 压缩是会话自己的事，在这个会话的 actor 里做，不阻塞别的会话（旧版撞过）。
- 压缩期间来的新消息照常落进日志，排在 N 之后，照排队的规矩排着。
- 人打断：压缩取消，什么都不写；这一轮照打断收尾。

**十三、度量**

每次压缩记一行 `INFO`（`log.md`），会话 actor 转推 `compaction.done` 时记（6-3 下）：

```text
INFO  session  <会话> compacted seen=24 trigger=auto before=15465 after=2675 summary_in=14147 summary_cached=2816 summary_out=2666 took_ms=11816
```

- `seen` 哪一次摘要请求；`trigger` 为什么压（现在只有 `auto`）；`before`、`after` 压前、压后的估算。
- `summary_in`、`summary_cached`、`summary_out`、`took_ms`：摘要请求的输入（没命中的、命中的、写进缓存的加起来）、命中、输出、用时，照它的 `model.called`，没有的不写。
- 截过几次、重读了几个文件随 6-6、6-5 加。
