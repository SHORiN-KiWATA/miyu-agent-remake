## 仓库拆分

状态：已定（2026-10-11）。项目主人 2026-10-11 建了 GitHub 组织 `miyu-agent`，定了重制版直接当家（`miyu-agent/miyu`，老 Miyu 留在个人账号、不进组织），终端界面和网页拆成各自的仓库，拆法交给主会话设计。下面都是主会话照推荐定的技术形状。

### 一、拆成哪几个

| 仓库 | 放什么 |
|---|---|
| `miyu-agent/miyu` | 核心、命令行、接入QQ、全部内部 crate、`miyu-client`（第二节）、设计文档、出厂资源（两个界面的清单除外） |
| `miyu-agent/miyu-tui` | 终端界面：现在 `proto/tui-demo` 上的 `tui-demo/`，它的图纸 `tui.md`、清单 `packages/tui/` |
| `miyu-agent/miyu-web` | 网页：`crates/miyu-web`（`miyu-web serve`）、`miyu-webserve` 里 HTTP 那一块、现在 `proto/web-demo` 上的前端，它的图纸、清单 `packages/web/` |

- 带着历史搬：照路径从原来的分支滤出来（`git filter-repo`），提交和作者都在。
- `miyu-webserve` 不单开仓库：它连核心的那一块（`open::Core`、`CoreCommand`，接入QQ 也用）进 `miyu-client`，听端口、给页面、`/ws` 转发那一块只有网页用，随网页走。单开的话它自己要钉核心的版本，网页又要同时钉它和核心，三方对版本只换来一家用。以后真有别人写网页界面要这套底子，再拿出来。
- 拆法照「运行时只走协议」这条已经守住的线：界面和核心之间只有协议（设计 `04-核心协议.md`），代码上借的只是「怎么找到、连上核心」那几样（第二节）。

### 二、界面只依赖 `miyu-client`

核心仓库加一个 crate `miyu-client`：给界面用的那几样都从这里拿，界面不再直接依赖别的内部 crate。它是门面，转出这些（2026-10-11 数过两个界面实际用到的）：

| 一组 | 转出什么 |
|---|---|
| 连核心 | `miyu-ipc` 的 `connect`、`connect_or_start`、`connect_or_start_bare`、`spawn_detached`、`Connection`、`Ready`、`ConnectError`、`StartError`；`miyu-webserve` 的 `open`（照终端的样子连核心、要一次性码） |
| 在哪 | `miyu-store` 的 `DataRoot`、`ResourceRoot`、`Env`、`locale`、`cache_root` |
| 给人看的字 | `miyu-store` 的 `Human` |
| 协议里的类型 | 会话编号这些编号、事件 `Said`、`Template` |
| 自己的清单 | `miyu-config` 读清单（`package::read`）和它的值 |
| 运行日志 | `miyu-log` 装日志 |

1. **门面不搬代码**：`pub use` 转出去，代码留在原来的 crate；界面能用的就是门面上有的，别的够不着。
2. **门面的样子是协议的一部分**：一份测试把门面上的每一样都用一遍（编得过就是在），改了、少了门面上的东西，照改协议的规矩告诉两个头。
3. **层序**：`miyu-client` 登记在传输那一层（`xtask/src/layers.rs` 的分层门禁），只往下引。
4. **先在一个仓库里收紧**：拆之前，`crates/miyu-web`、`tui-demo/`、网页的桥先改成只依赖 `miyu-client`，门禁照旧跑；收紧了再拆，拆的那一步只换依赖的写法。

### 三、版本怎么对

- 界面照 git 依赖钉核心的某一个提交：`miyu-client = { git = "https://github.com/miyu-agent/miyu", rev = "<提交>" }`；核心发版打标签以后钉标签。升级就是界面仓库里改这一行、过 CI。
- 协议照现在的规矩：只加格不改形状；要改形状照握手的协议版本走（`protocol.md`「握手」），老的界面照协议版本被挡在门外，说清楚是哪一边旧。
- 合核心时改了协议、门面的，照现在的做法告诉两个头（提交号、形状），两个头在自己的仓库里升级。

### 四、测试

1. **界面自己的单元测试**不要核心。
2. **终端连真核心的测试**（现在在测试进程里拼一个核心，用 `miyu-session` 的测试夹具、`miyu-core`、`miyu-endpoint`）：拆的时候先照原样，开发依赖照 git 钉同一个提交、打开 `testkit`，不重写；之后改成黑盒：拉起照钉住的提交编出来的真 `miyu`，模型用本机的假模型（照 `miyu-perf` 的假模型：本机 HTTP，照 OpenAI 的样子回），测的就是用户用的那个程序。
3. **协议的样本**（`docs/designs/samples/`）留在核心仓库，界面的 CI 照钉住的提交取。

### 五、CI 和门禁

- 两个界面仓库各自三台 CI：格式、clippy（`-D warnings`）、文档、测试、行数（每个 `.rs` 不超过 500 行，同核心）。层序、登记簿、许可证照需要：界面不发字给模型，没有登记簿；许可证照核心的白名单。
- 核心仓库的 CI 照旧；`miyu-client` 在工作区里，三台都编。

### 六、发版和打包

- 核心仓库加一份 `heads.toml`：两个界面的仓库和要的标签。发版时照它取两个界面的发布产物（三个平台的程序和 `package/` 文件夹），程序放在 `miyu` 旁边，清单放进资源目录的 `packages/tui/`、`packages/web/`：用户拿到的照旧是一个包。
- 两个界面的清单只在各自的仓库里有，核心仓库删掉 `resources/packages/{tui,web}/`；核心里用到它们的测试（约 20 处）改成测试自己放的夹具。
- 软件源做好以后（设计 31 第八节），两个界面也能当包单独升级。

### 七、在途的工作

- 终端：`proto/tui-demo` 上的改动先提交、推上去，照分支的最新提交滤出来；终端的会话以后在新仓库的检出里做，`proto/tui-demo` 和它的几个 `step/tui-*` 分支确认带过去了再删。
- 网页：`crates/miyu-web` 在 main 上，前端在 `proto/web-demo`；网页的会话先把在途的分支合了或推了。演示用的桥 `web-demo/bridge/` 和 `miyu-web serve` 做的是同一件事，留不留、怎么并由网页的会话定。
- 图纸：`tui.md`、`web.md`、`web-ui.md`、`web-module.md`、`webserve.md` 随界面走；核心仓库留协议、设计和别的图纸。施工单是历史，不搬。
- 两个界面仓库各放一份 `AGENTS.md`：照核心的那份留下和界面有关的规矩。

### 八、施工拆分

| 步 | 做什么 | 谁做 |
|---|---|---|
| S-1 | `miyu-client` 门面、门面测试、层序登记；`miyu-webserve` 的 `open` 挪进来 | 主会话 |
| S-2 | 网页、终端、网页的桥改成只依赖 `miyu-client` | 网页、终端各自的会话（主会话审） |
| S-3 | 开 `miyu-tui`：滤出历史、CI、git 依赖钉核心 | 主会话，和终端的会话约好时间 |
| S-4 | 开 `miyu-web`：同上，`miyu-webserve` 的 HTTP 那一块搬过去 | 主会话，和网页的会话约好时间 |
| S-5 | 核心仓库删掉两个界面的代码和清单，测试改夹具；发版照 `heads.toml` 打包 | 主会话 |
| 之后 | 终端连真核心的测试改黑盒 | 终端的会话 |
