## 性能预算（草案）

状态：F1 到 F4 已定（2026-09-25）。其余内容为草案。

「轻量、极速、低占用」是第一条原则（`00-设计理念.md` 第一节），原则里说：没有测量数字的优化不算优化。这一份定下要量什么、怎么量、量出来要达到多少。四位外部读者都指出，前面的文档里数字散在各处，拼不出一张靶子；这一份就是那张靶子。

表里的数都是初值，原型第一次实测之后校准。校准时照实改，记下测到的数字（`README.md` 的约定）。

### 一、怎么量

先定量法，再谈数字。jcode 把「又快又省」当卖点，它的测法有几处坑（第四节），这里一条条避开：

- **启动分三个点量**：
  1. 头的第一帧：真正的界面画出来，不算命令行先打出来的一行字；
  2. 能打字：敲下的字出现在屏幕上；
  3. 能提交第一轮：核心就绪、会话载入完毕，回车就能发出去。

  冷启动（核心没在跑）和热启动（核心已经在跑）分开报。
- **内存按进程分开报**：核心、每个头、每个 worker 各报各的，用 PSS 和私有匿名内存。
  - 空会话要量，钉住的一个大会话也要量。初值：一个 8 MB、三百多条消息的会话。
  - 空闲一段时间以后再量一次：分配器会把释放的内存攒着不还。
- **会话越长越要量**：投影、打开会话、翻历史，都在一万条事件的长会话上量。
- **量一次落盘**：追加一步的事件，加上同步，报 p50 和 p99。
- **量界面**：一帧的准备加输出、按键到上屏，报 p50 和 p95。
- **写清条件，原始数据入库**：写明机器、系统、版本。原始数据跟着代码入库；量尺进 CI 做回归闸门，不是只在发布前跑一次。

### 二、预算

| 项目 | 预算（初值） | 为什么是这个数 |
|---|---|---|
| 冷启动到能打字 | 150 ms | jcode 自己的冷启动预算就是 150 ms；一两百毫秒以内的等待，人不大察觉 |
| 热启动到第一帧、到能打字 | 50 ms | jcode 实测到能打字是 48.7 ms（口径见第四节） |
| 热启动到能提交第一轮 | 200 ms | 核心要载入会话：读投影缓存，再重放尾巴（`07-存储.md` 第七节） |
| 按键到上屏 | p50 5 ms | jcode 实测 3.5 ms |
| 一帧的准备加输出 | p95 16 ms | 六十帧 |
| 在会话树里切到另一个会话 | 一帧之内（p95 16 ms） | 项目主人要「近乎秒切」（2026-09-26）。树里每个会话的视图都订阅着，切过去只是换一份来画（`13-终端界面.md` 第五节） |
| 一次请求的投影（增量，一万条事件的会话） | p95 5 ms | 投影是内核里最热的纯函数（`08-上下文投影.md` 第一节） |
| 同一个会话从头投影一次 | 100 ms | 打开长会话、投影缓存失效时才发生 |
| 追加一步的事件并同步 | p99 20 ms（固态硬盘） | 先落盘后推送，这段延迟人会直接感到（`07-存储.md` S4） |
| 核心空闲、没有会话载入 | 30 MB | 按需运行时，不用就不在；常驻时这是底 |
| 核心里每多一个活动会话 | 5 MB | 会话的 actor 空闲就退出（`07-存储.md` 第七节） |
| 终端界面自己，载着一个大会话 | 20 MB | 头只负责画，显示逻辑在核心（`01-架构.md` D1）。旧版的全屏演示放五条长回复不到 4 MB（`13-终端界面.md` 第九节） |
| 重型 worker | 用完就退，不算常驻 | embedding、识别模型的几百 MB，只在用的时候占（`20-语音.md` 第七节） |

- 超了预算，先查是不是量法的问题，再查是不是设计的问题。确实是设计的问题，按对应文档的重开条件走。

### 三、借来的手段

这些是从 jcode 的代码里看到的做法，已经写进了对应的文档。能找到它自己实测的，写在最后一列：

| 手段 | 写在哪 | jcode 的实测 |
|---|---|---|
| 拉起核心时用一根管道通知就绪，加上拉起锁、清残留的套接字、先 bind 后做重活 | `12-进程形态与分发.md` 第二节 | 内部预算是服务端就绪 80 ms，没有公开结果 |
| 先画后连，连上之前也能打字 | `13-终端界面.md` 第九节 | 到能打字 48.7 ms |
| 同步输出、只改变了的格子、空闲时分档放慢心跳 | `13-终端界面.md` 第九节 | 动画只重画动画那一行以后，少用约 0.26 个核，按键延迟 p50 从 6.6 ms 降到 3.5 ms |
| 折好的行按宽度缓存，只画视口 | `13-终端界面.md` 第九节 | 没有单独的数字 |
| 按段记请求的哈希，有意的改写都登记，没登记的未命中就报警 | `08-上下文投影.md` 第七节 | 没有 |
| 流式输出的空闲超时按思考强度放大，等第一个字时发心跳 | `15-模型与供应商.md` 第五节 | 没有 |
| 连接预热 | `15-模型与供应商.md` 第五节 | 首字快 12% 到 27%（各 10 对，只测了一个模型） |
| 急着插话时，剩下的工具补「已跳过」 | `02-内核.md` 第六节 | 没有 |

还有三条写在这一份里：

- **长驻进程的分配器纪律**：核心和 worker 用系统的分配器。在 glibc 上限制 arena 的个数，空闲一段时间就 trim 一次，把攒着的内存还给系统。jcode 把这一条和别的几项一起做，空闲时的私有匿名内存从 69 MB 降到 38 MB；它换过 jemalloc，默认参数下吃到过 1.4 GB。旧版 Miyu 测过 mimalloc，判了不做（旧版仓库 `docs/plan/low-footprint.md`）。
- **缓存都有两个上限**：条数一个、字节数一个，谁先到按谁算。
- **进程自己记账**：核心定时采样自己的 PSS、私有内存和分配器的统计，写成 JSONL 放在 `state/` 下；涨得快的时候多采一次。回归闸门钉住一个大会话，每次改动都跑（F4）。

### 四、jcode 的量法，哪些不照搬

- 它的「到第一帧 14 ms」，在当前代码里量到的，很可能是界面起来之前命令行先打出的一行字，和别家的「第一帧」不是一回事。所以我们分三个点量（第一节）。
- 它的内存只量了空会话，而且量的是好几个月前的旧版本。它自己的回归闸门拿一个 8 MB 的真实会话量，单个客户端空闲时就有约 38 MB，是 README 里「每个会话约 10 MB」的四倍。
- 它测自己用的是一个干净的临时目录，测别家用的是真实的家目录和配置，两边条件不对等。
- 它的每个会话都有一个完整的界面进程，markdown 渲染和折行都在客户端算，所以每个会话都要多付一份内存。我们的头只负责画，显示逻辑在核心（`01-架构.md` D1）。

### 五、决定

**F1. 预算是策略数据**

- **已定：第二节的数都是初值，原型第一次实测后校准；校准照实改，记下测到的数字。**
- 重开条件：无。

**F2. 量法**

- **已定：启动分三个点，冷热分开；内存按进程分开报，空会话和大会话都量，空闲以后再量一次；长会话上量投影和打开；原始数据入库，量尺进 CI 做回归闸门。**
- 未选：学 jcode，只在发布前量一次空会话。数字好看，但说明不了真实用起来怎样。
- 重开条件：无。

**F3. 分配器**

- **已定：用系统的分配器；glibc 上限制 arena 的个数，空闲时 trim。**
- 未选 A：jemalloc。jcode 用默认参数时吃到过 1.4 GB。
- 未选 B：mimalloc。旧版测过，判了不做。
- 重开条件：实测某个平台上，系统的分配器明显不够用。

**F4. 进程自己记账**

- **已定：核心定时采样自己的内存，写成 JSONL；回归闸门钉住一个大会话，每次改动都跑。**
- 重开条件：采样本身的开销超出预算。

**后续再定**

- 发行构建怎么配（LTO、codegen-units、panic 的策略、strip）：原型阶段按体积和速度实测定
- macOS 和 Windows 上各自怎么量内存
