## 运行日志

核心自己的日志：它起来了没有、在干什么、哪里出了错。排障时先看它，不用先造测具去复现。旧版的痛点就在这里：日志不透明，查一个问题要先造测具，费时费钱（2026-09-26 项目主人：「像内核日志那样拥有完整的事件日志」）。

它和会话日志不是一回事：

- **会话日志**（`07-存储.md` 第三节）是真相源，记会话里发生的每一件事，JSONL，永远留着，回放就靠它。
- **运行日志**是给人看的流水：核心和它的子进程在干什么，一行一条，满了轮换。不是真相源，删了不丢任何东西。

### 一、写到哪

- **核心的**：数据根的 `state/logs/core.log`（`07-存储.md` 第二节的 `state/`）。满 10 MB 换一份，正在写的之外留最近 5 份：`core.log.1` 是上一份，以此类推，最老的是 `core.log.5`，和 logrotate 的 `rotate 5` 一个口径。
- **每个软件一份**（LG4）：扩展、QQ 桥、语音这些子进程，标准错误输出各写进自己的 `state/logs/<软件>.log`，同样轮换。核心的日志里记它们什么时候起、什么时候退、退出码是多少。
- 前台跑的一次性命令（`miyu ask` 这类）照 `22-命令行.md` 的规矩把出错打在标准错误上；它们连着的核心照常记自己的。

### 二、一行怎么写

```text
2026-09-27 21:03:15.284 INFO  core     started version=0.0.0 root=~/.miyu
2026-09-27 21:03:16.002 INFO  session  0199d1e6-3b7a-7c41-8e5d-2f6b4c9f02a3 created persona=engineer venue=local
2026-09-27 21:03:18.410 INFO  session  0199d1e6-3b7a-7c41-8e5d-2f6b4c9f02a3 request seen=6 endpoint=deepseek model=deepseek-flash
2026-09-27 21:03:18.411 DEBUG http     0199d1e6-3b7a-7c41-8e5d-2f6b4c9f02a3 sent host=api.deepseek.com bytes=5120
2026-09-27 21:03:20.104 DEBUG http     0199d1e6-3b7a-7c41-8e5d-2f6b4c9f02a3 ended host=api.deepseek.com status=200 took_ms=1693
2026-09-27 21:03:20.105 INFO  session  0199d1e6-3b7a-7c41-8e5d-2f6b4c9f02a3 ended seen=6 took_ms=1695 in=104 hit=0 out=149
2026-09-27 21:05:02.771 WARN  session  0199d1e6-3b7a-7c41-8e5d-2f6b4c9f02a3 retrying seen=9 attempt=1 limit=5 wait_ms=3000 class=rate_limited
```

- **一行一条的字，像 dmesg**（LG1）：时刻、级别、来源、这件事，后面跟 `键=值`。值里有空格、引号、等号的加双引号。一行里不出现换行和别的控制字符：换行写成 `\n`，ESC 这类写成 `\x1b`，`cat` 日志的时候终端不会把它们当成指令。
- **时刻**：本机时间，到毫秒。核心起来的那一行写上时区（`tz=+09:00`），跨时区看日志的对得上。
- **级别**占 5 格，**来源**占 8 格，都左对齐：`core`、`session`、`http`、软件的名字。会话写全编号，搜得到，不会撞。
- **用时、要等多久**写毫秒的整数，键名带 `_ms`：`took_ms=1695`。不换算单位，好比、好加。
- **缓存为什么没命中，看 `request` 和 `ended` 两行**（2026-09-27 补，施工 3-9 下，项目主人问「怎么从日志查原因」）：`ended` 的 `in`、`hit` 是输入、命中缓存；`request` 在这一次请求的前缀和上一次比变了的时候，多一个 `changed=`，写第一处不同在哪：`tools`、`system`，或者 `message:<第几条，从 0 数起>:<角色>`，例如 `changed=message:0:user`。只是往后接着加的，不写。没写 `changed`、`hit` 还是 0 的，是请求太短、供应商那边没存（DeepSeek 按 128 个 token 一块存，末尾总有一截不存）；写了 `changed` 的，是我们自己的前缀变了，照它说的地方查。
- **字一律英文**（LG1，2026-09-27 项目主人定）：贴进 issue、搜索、别人帮忙看都方便。它是给人看的，不进请求，`26-提示词.md` 管不着它；和界面语言无关，换了界面语言，日志还是一种话。

### 三、级别

照 niri 的口径：

| 级别 | 什么时候用 |
|---|---|
| `ERROR` | 一定是 bug：内核拒了自己造的事件，走到了不该走到的状态。出现了就该修 |
| `WARN` | 坏事，但可能发生：限速、断线重试、子进程异常退出、磁盘快满、配置写错了用默认 |
| `INFO` | 来龙去脉：核心起停，会话开关，每次请求发出去、怎么收场（用时、用量、出错的分类），重试，子进程起停 |
| `DEBUG` | 每一条输入、每一个动作，排障时开 |
| `TRACE` | 更细。只在开发构建里有，发行版编译时去掉 |

- **默认 `INFO`，能配置**（LG2）：配置项 `log.level`，写进配置长期生效（`14-配置.md`）；环境变量 `MIYU_LOG` 只管这一次启动，像内核命令行上的 `loglevel`。软件包的日志默认跟着核心的这一项，可以在自己的配置里单独调。
- 配置里写错了级别：用默认的 `INFO`，记一条 `WARN` 说写错的是哪个值。

### 四、写什么，不写什么

- **不写对话的内容**（LG3）：人说的话、她的回复、思考、工具的参数和结果，一个字都不写。写编号：会话编号、序号（`seen`）、命令编号、调用编号，凭它们去会话日志里翻。
- **不写密钥**：key、令牌、密码永远不写，前几位也不写。配置里的密钥只写名字（`07-存储.md` 第九节）。
- **家目录写成 `~`**：路径里不带用户名。
- 这样一份日志可以直接发给别人看、贴进 issue，不漏对话，不漏 key。

### 五、怎么看

`miyu logs`（`22-命令行.md` 的管理命令表，随 `miyu` 这个程序一起来）：

- 默认打出核心日志的最后 100 行；`-f` 跟着看；`--level warn` 只看这一级和更严重的；`--session <编号>` 只看一个会话；`miyu logs <软件>` 看那个软件的。
- 它读的是文件，核心没起来也能看。

### 六、决定

**LG1. 一行怎么写**

- **已定：一行一条的字，像 dmesg；字一律英文（2026-09-27 项目主人定）。**
- 未选：JSONL。好用脚本处理，人要看得靠 `miyu logs` 转成人话；会话里的事已经在会话日志里了，这里是给人看的流水。
- 未选：跟着界面语言。换了界面语言，前后的日志是两种话，搜索要搜两遍。
- 重开条件：无。

**LG2. 记到哪一级**

- **已定：默认 `INFO`；配置项 `log.level` 长期生效，环境变量 `MIYU_LOG` 管这一次启动，像 grub 配 `loglevel`（2026-09-27 项目主人：「INFO级，但是可以给配置项？就像是我们可以给grub配置loglevel一样？」）。**
- 未选：默认 `DEBUG`。排障更方便，文件长得快，平时用不着。
- 重开条件：实测 `INFO` 查不出常见的问题。

**LG3. 写不写对话的内容**

- **已定：不写，只写编号；密钥永远不写（2026-09-27 项目主人定）。**
- 未选：写前几十个字。对着看方便，可日志一发给别人就漏了对话。
- 重开条件：无。

**LG4. 每个软件的日志**

- **已定：子进程各写各的文件，核心记它们的起停和退出码（2026-09-27 项目主人定）。**
- 未选：都混进核心的一份。只有一个文件好找，可哪个软件刷屏，就把别的挤掉了。
- 重开条件：无。
