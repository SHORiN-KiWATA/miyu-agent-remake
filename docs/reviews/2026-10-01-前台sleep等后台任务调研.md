## 调研：前台 sleep 等后台任务，别家怎么处理（2026-10-01）

### 零、起因和 Miyu 现在的样子

- M7 验收自测第 1 条（`docs/construction/7-11-M7 验收.md`）：她把 `./test.sh` 放到后台（j1），知道结束会自己回报，还是在前台跑了一条 `sleep 26` 去等，再用 `jobs` 读输出。
- 给她看的字里已经有两处说「不用等」：
  - `shell` 放到后台时的回执 `shell/started.txt`：`Started {job} in the background. You will be told when it ends. Read its output with jobs output.`
  - `jobs` 的说明：`… Finished jobs report to you on their own, so there is no need to poll.`
- 她正忙时，回报在「下一步」看到（`docs/blueprint/agents.md` 第三条）。前台 `sleep 26` 那一步不结束，回报就排在它后面。所以这条 sleep 不丢信息，只是白等：后台早跑完了，她还在睡。或者没睡够，再睡一轮。
- 一处要注意的场所：`miyu ask` 不等后台命令（`docs/blueprint/cli/ask.md`「等谁」、`docs/designs/22-命令行.md` 第三节）。她结束这一轮，`miyu ask` 就退出，之后命令跑完只记下、不叫醒她（没人看着的一次性会话）。这种时候她要在这一次里给出结果，前台 sleep 反倒是唯一的路。M7 那一次正好在等一个子代理，会话有人看着，她结束这一轮也会被回报叫醒，只是她不知道。

### 一、各家怎么做

出处一律相对各仓库的根。openclaude 是 Claude Code 的社区分叉（`5cd1133`，v0.31.0，底子是较早的 Claude Code）。真正的 Claude Code 另外核对了本机装的 2.1.280 版二进制（从里面抽出的字符串）和官方文档。

#### 1. Claude Code：说明里写、工具里硬拦、另给一个 Monitor

**硬拦的规则（2.1.280 二进制里的 `validateInput`）**

- 什么时候查：一个服务端下发的特性开关开着（`tengu_amber_sentinel`，默认关），后台任务没被关掉（`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`），这次调用不是 `run_in_background`，三样都满足才查。这次调研所在的会话里，Bash 工具的说明就带着「Foreground `sleep` is blocked」那一句，说明这个开关对这个账号是开的。全量开没开，查不到。
- 拆命令：照 `&&`、`||`、`;`、`|` 切开，只看第一段。第一段去掉空白后，整段要正好是 `sleep <数字>`（正则 `^sleep\s+(\d+(?:\.\d*)?)\s*$`，小数也认）。
- 门槛：秒数小于 25 放行，25 及以上拦下。M7 的 `sleep 26` 在这条规则下正好被拦。
- 拦下时不跑命令，交回出错（`errorCode: 10`），原文：

  ```text
  Blocked: standalone sleep 26. To wait for a condition, use Monitor with an until-loop (e.g. `until <check>; do sleep 2; done`). To wait for a command you started, use run_in_background: true. Do not chain shorter sleeps to work around this block.
  ```

  后面还有别的命令的，开头换成 `Blocked: sleep 26 followed by: <后面那些>.`。
- 串接怎么算：只看第一段。`sleep 20; sleep 20` 第一段 20 秒，放行。`cd x && sleep 30`、`sleep 30s`、`sleep 1m`、`until …; do sleep 5; done` 第一段都不是纯 `sleep N`，也放行。「别拿短的 sleep 串起来绕」只写在说明和报错里，代码不查。
- 例外：小于 25 秒的（限速、节奏），写了 `run_in_background` 的，后台任务整个关掉的，开关没开的。
- PowerShell 工具有同样的一条：第一句（照 `; | & 换行` 切）是 `Start-Sleep N`、`Start-Sleep -Seconds N`、`-s N`、`sleep N`，门槛同一个 25 秒，报错多一句「Monitor runs bash」。
- 另一条相关的：前台命令到时不杀，挪到后台接着跑，但开头是 `sleep` 的不挪（二进制里的名单只有 `sleep`，官方文档 tools-reference「Background commands」写的是「unless the command starts with `sleep`」）。
- 旧版对照：openclaude `src/tools/BashTool/BashTool.tsx:474`（`detectBlockedSleepPattern`）、`:678-684`，门槛是 2 秒、只认整数，报错原文是 `Blocked: … Run blocking commands in the background with run_in_background: true — you'll get a completion notification when done. For streaming events (watching logs, polling APIs), use the Monitor tool. If you genuinely need a delay (rate limiting, deliberate pacing), keep it under 2 seconds.`。PowerShell 那条在 `src/tools/PowerShellTool/PowerShellTool.tsx:275`。也就是说门槛从 2 秒放宽到了 25 秒，为什么改没找到公开说明，changelog 里没写。

**说明里怎么写**

- 2.1.280 完整版 Bash 说明里「Avoid unnecessary `sleep` commands」一组（二进制里的原文）：
  - `Do not sleep between commands that can run immediately — just run them.`
  - `If your command is long running and you would like to be notified when it finishes — use run_in_background. No sleep needed.`
  - `If waiting for a background task you started with run_in_background, you will be notified when it completes — do not poll.`
  - `Long leading sleep commands are blocked. To poll until a condition is met, use Monitor with an until-loop (e.g. until <check>; do sleep 2; done) — you get a notification when the loop exits. Do not chain shorter sleeps to work around the block.`
  - 开关没开时这一句换成 `If you must poll an external process, use a check command (e.g. gh run view) rather than sleeping first.` 和 `If you must sleep, keep the duration short to avoid blocking the user.`
- 精简版说明只有一句：`run_in_background runs the command detached: it keeps running across turns and re-invokes you when it exits. No & needed. Foreground sleep is blocked; use Monitor with an until-loop to wait on a condition.`
- 旧版的同一组在 openclaude `src/tools/BashTool/prompt.ts:283-300`。

**「等某件事」的专门工具**

- Monitor（官方文档 tools-reference「Monitor tool」，2.1.98 加的）：在后台跑一段脚本，标准输出每一行都作为一条通知送给模型，模型照常干活。每个监视都有期限，默认 5 分钟、最多 30 分钟，`-p` 一次性运行里最多 10 分钟，到期给一条通知让它自己决定要不要再开。
  - Monitor 的说明（二进制里）分三种用法：
    - 只要一条通知（「服务起来了告诉我」）的，用 `run_in_background` 加一条条件满足就退出的命令（`until grep -q "Ready in" dev.log; do sleep 0.5; done`），退出时只来一条完成通知。
    - 每出一件事来一条、一直看的，用 Monitor 加不会退出的命令（`tail -f`）。
    - 每出一件事来一条、到某个结局为止的，用 Monitor 加会退出的命令。
  - `-p` 一次性运行里：后台 shell 在最后结果交出后约 5 秒被杀掉。后台子代理、Monitor 会让这次运行一直等着（官方文档 headless「Background tasks at exit」）。所以 `-p` 里想在这一次拿到结果，合法的路是 Monitor。
- TaskOutput（带 `block=true` 能阻塞等一个任务）已经标成过时，说明里叫模型改用 Read 读任务的输出文件（官方文档 tools-reference，openclaude `src/tools/TaskOutputTool/TaskOutputTool.tsx:175`）。
- 另有一个 Sleep 工具，只在主动模式（proactive）里给，说明写「Prefer this over Bash(sleep ...) — it doesn't hold a shell process」（openclaude `src/tools/SleepTool/prompt.ts`）。

**后台任务结束怎么通知**

- 一条 `<task-notification>`，带任务编号、调用编号、输出文件路径、状态（`completed`、`failed`、`killed`）、一句摘要（`Background command "<描述>" completed (exit code 0)`），作为排队的通知送进去，优先级是「下一步」（openclaude `src/tasks/LocalShellTask/LocalShellTask.tsx:105-170`）。这次调研里真撞见了：一条命令超时被挪到后台，跑完以后，这条通知在我下一次调工具之前送到了。
- 还有一个看门的：后台命令 45 秒没有新输出、最后几行像在等人输入，就发一条「appears to be waiting for interactive input」，叫它杀掉重跑、改用管道或非交互参数（同一个文件 `:24-98`）。

#### 2. codex：不拦 sleep，给「会提前返回的等」

- 硬拦：`codex-rs/core/src/tools` 下没找到拦 shell 里 `sleep` 的代码（`d7b07d4`）。
- 说明：较新的模型（`gpt-5.6-*`、`gpt-6-*` 等）的系统提示里有一句：`Avoid performing blocking sleep or wait calls longer than 60 seconds, as they may prevent you from communicating with the user for their duration.`（`codex-rs/models-manager/models.json`）。
- 长命令的形状和别家不同，轮询本身就是设计好的路：
  - `exec_command` 跑到 `yield_time_ms`（默认 10 秒，250 到 30000）还没完，就交回一个会话编号（`codex-rs/core/src/tools/handlers/shell_spec.rs:30-35`）。
  - 之后模型用 `write_stdin` 发空字符去「查」：空的查询至少等 5 秒、默认最多 300 秒，进程退出了当场返回（`shell_spec.rs` 里 `write_stdin` 的参数说明，`codex-rs/core/src/unified_exec/mod.rs:73-78`，`codex-rs/core/src/unified_exec/process_manager.rs:1018-1030` 和 `collect_output_until_deadline`）。
  - 所以 codex 的「等」是一次阻塞的查询，结束了立刻回，不会白等。
- 专门的等待工具：
  - `clock.sleep`（特性开关 `SleepTool`，按模型给）：`Pause execution for a specified duration. The sleep ends early when new input arrives for the active turn. Returns the elapsed wall-clock time.` 最长 12 小时（`codex-rs/core/src/tools/handlers/sleep.rs`，开关在 `codex-rs/core/src/tools/spec_plan.rs:1234`）。`gpt-6-*` 的提示里还鼓励用它：「You can use clock.sleep to wait for external events and conditions to change.」「Prefer working in the current task with clock.sleep between checks over automations.」
  - `wait_agent`（多代理）：`Wait for a mailbox update from any live agent … The wait also ends early when new user input is steered into the active turn.`（`codex-rs/core/src/tools/handlers/multi_agents_spec.rs` 的 `create_wait_agent_tool_v2`）。
- 后台进程结束：没找到主动推给模型的代码。进程退出时只给界面发 `ExecCommandEnd` 事件（`codex-rs/core/src/unified_exec/async_watcher.rs` 的 `spawn_exit_watcher`），模型要靠 `write_stdin` 查。

#### 3. opencode：shell 没有后台，后台子代理的说明和回执里写「别睡、别查」

- `shell` 工具没有放到后台的参数，说明里也没有关于 sleep 的话（`packages/opencode/src/tool/shell/shell.txt`、`prompt.ts`，`696f41bc`）。
- 后台只有子代理（`task` 工具的 `background`，要开实验开关 `OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS`）：
  - 参数说明：`Run the agent in the background. You will be notified when it completes. DO NOT sleep, poll, or proactively check on its progress`。
  - 派出去的回执：`The task is working in the background. You will be notified automatically when it finishes.` `DO NOT sleep, poll for progress, ask the task for status, or duplicate this task's work …` `Work on non-overlapping tasks, or briefly tell the user what you launched and end your response.`（`packages/opencode/src/tool/task.ts:25-61`）。
- 做完了：以一条合成的用户消息（`<task_result>`）送回父会话、开一轮（同一个文件 `:227-265`）。
- 不拦，没有等待工具。

#### 4. pi：没有后台，也就没这件事

- `bash` 工具只有 `command`、`timeout`，没有默认超时，说明里没有 sleep 的话（`packages/coding-agent/src/core/tools/bash.ts:39-40`、`:239`，`5fd446c`）。
- 作者的立场是不做后台 bash，要长跑的用 tmux（Mario Zechner 的博客 [What I learned building an opinionated and minimal coding agent](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)，2025-11-30）。
- 不拦，没有等待工具，没有结束通知。

#### 5. dsh：说明里写「别睡」，同时给一个受控的等

- 常驻 system 的一段（`tool:jobs`，`packages/jobs/tool-jobs/src/index.ts:262-267`，`47f94385`）：

  ```text
  Track every background job id you start. You are notified in-session when a job finishes — do not busy-poll or sleep on one; keep working on independent steps and do not duplicate a running job's work. Before giving a final answer, collect every still-relevant job with job_output (set wait: true only when you are genuinely blocked on it), and job_kill jobs that stopped mattering.
  ```

- 等待：`job_output` 带 `wait: true` 就阻塞到任务结束或到时（默认 30 秒，最多 10 分钟），到时交回 `[status: running]`、任务照跑（同一个文件 `:304-334`）。说明里的「只在真卡住时用」是在压它别滥用。
- 结束通知：一条用户消息 `background job <编号> (<种类>: <标题>) finished <状态>. Read its output with job_output.`。她正忙就排进下一步，闲着就叫醒她，连着叫醒有个次数上限（同一个文件 `:146-160`、`:269-300`）。
- 不拦 bash 里的 sleep（`packages/shell/tool-bash/src` 里没有相关代码）。

### 二、对照

| | 说明里写不等 | 硬拦前台 sleep | 专门的等待 | 结束怎么通知模型 |
|---|---|---|---|---|
| Claude Code 2.1.280 | 写，好几句 | 拦：第一段是 `sleep N`、N≥25 秒（开关控制） | Monitor（每行一条通知，有期限） | `<task-notification>`，下一步送到 |
| codex | 较新模型的提示里「别阻塞超过 60 秒」 | 不拦 | `write_stdin` 空查询、`clock.sleep`、`wait_agent`，都会提前返回 | 不推，靠模型查 |
| opencode | 后台子代理的参数说明和回执里写 | 不拦 | 没有 | 合成一条用户消息开一轮 |
| pi | 没有后台 | 不拦 | 没有 | 没有 |
| dsh | 常驻 system 一段 | 不拦 | `job_output` 带 `wait: true` | 用户消息，忙时下一步、闲时叫醒 |
| Miyu 现在 | 回执、`jobs` 说明各一句 | 不拦 | 没有（2026-09-26 定了不设「等它做完」） | `job.reported`，忙时下一步、闲时叫醒 |

两点观察（推断，没有别家的实测数据）：

- 只靠写字的（opencode、dsh）都写得很重，大写的 DO NOT、常驻 system。Miyu 已经写了两处短句，M7 里 DeepSeek 照样睡。
- 两家给了「会提前返回的等」（codex、dsh）。Claude Code 拦了 sleep，同时给了 Monitor 这个出口。拦和出口是一对：只拦不给路，模型会改写成别的形状去等。

### 三、Miyu 的几条路

**A. 不管**

- 好处：不动代码，不加字。
- 坏处：白等照旧。后台早跑完了她还在睡，没睡够的再睡一轮，多一次请求。
- 伤害不大：回报不丢，只是慢。

**B. 只加字**

- 最便宜的放法是回执 `shell/started.txt` 末尾加一句（例如 `Do not sleep to wait for it.`，估计十来个 token，只在放到后台那一次出现，不常驻，合 J12）。
- 坏处：她已经看过两句同义的，照样睡。加第三句管不管用，要实测才知道。Claude Code 是字和拦一起上的。

**C. 在 `shell` 里硬拦（照 Claude Code）**

- 拦什么：前台（没写 `run_in_background`）、第一段整段是 `sleep N`（bash、zsh），或者 `Start-Sleep N`、`Start-Sleep -Seconds N`、`sleep N`（PowerShell），N 不小于门槛的，不跑，交回出错。切段照 `&&`、`||`、`;`、`|`、换行。小于门槛的、第一段不是纯 sleep 的（`until …; do sleep 2; done` 这类有条件的等）放行。
- 报错的草稿（英文短句，一句一个意思，没量 token，估计 30 个左右）：

  ```text
  Not run: sleep {seconds} in the foreground. Background jobs report to you when they end. If you need a result now, run that command in the foreground instead.
  ```

  最后一句给她一条在所有场所都走得通的路：要在这一轮拿结果，就别放后台，前台跑、放宽 `timeout`（最多 10 分钟）。它也正好接住 `miyu ask` 那种场所。
- 好处：结果确定。常驻的字一个不加，只在撞上时出一句，本身就是「按需出现」。前缀不变。代码小：一个切段加一个正则，和 Claude Code 的检查一样浅。
- 坏处：她可能改写成 `sleep 20; sleep 20`、`timeout /t 30`、`python -c "import time; time.sleep(30)"` 绕过去，Claude Code 也只在字面上说别这样。要实测她被拦之后怎么做。`miyu ask` 里她放了后台又想当场交结果时，只能照报错改成前台跑，或者结束这一轮（结果等 `miyu ask -c`）。

**D. 加一个等待（比如 `jobs` 加 `wait`：等到某个任务报回来或者到时，别的回报、人插话也提前回）**

- 好处：合法的等有了出口，结束了立刻回，不白等。codex、dsh 都有。
- 坏处：和 2026-09-26 项目主人定的「不设等它做完」相反（`docs/designs/02-内核.md` 第七节：模型多半会白白地等，注意事项又白占 token）。工具面常驻多几十个 token，每次请求都背着。dsh 要另写「只在真卡住时用」来压着它。

### 四、推荐

**推荐 C：在 `shell` 里硬拦前台的长 sleep，门槛 25 秒，只看第一段，照 Claude Code 现在的规则。原来的两句不动，不加常驻的字，不加等待工具。**

- 理由：Miyu 已经试过「只写字」，不管用。硬拦不占常驻 token，合 J12。回报机制本来就把「等」这件事接住了，缺的只是让她别自己睡。
- 施工前先照 J12 实测：拦下以后她做什么（结束一轮、改成前台跑、还是改写成连着的短 sleep 绕过去），量出报错这句多少 token，登记。改写绕过的比例高的话，再考虑把开头连着的几段 sleep 加起来算。
- `miyu ask` 场所照拦，报错里的最后一句指路（前台跑）。要不要让 `miyu ask` 等后台命令，是另一件事，见下面第 3 题。

### 五、要项目主人拍板的

1. **前台 sleep 等后台任务怎么处理**
   - A 不管。
   - B 只在放到后台的回执里再加一句。
   - **C 在 `shell` 里硬拦，报错指路（推荐）。**
2. **拦的门槛**
   - **25 秒，照 Claude Code 现在的（推荐）：M7 的 `sleep 26` 拦得住，限速、等端口这类短等放行。**
   - 2 秒，照 Claude Code 早先的：几乎所有 sleep 都拦，误伤多。
   - 10 秒：折中，没有别家的依据。
3. **`miyu ask` 一次性会话里，她放了后台又想当场交结果**
   - **照样拦，报错叫她改在前台跑（推荐）：和别的场所一套规则，`miyu ask` 退出后后台命令只记下的规矩不变。**
   - `miyu ask` 里不拦：她睡够了当场交结果，但白等照旧。
   - `miyu ask` 也等这一次放到后台的命令：一直开着的服务会让它退不出去，要另想怎么认「服务」。

### 六、没查到、不确定的

- Claude Code 的开关 `tengu_amber_sentinel` 对哪些人开：服务端下发，只知道这次调研所在的账号是开着的。
- Claude Code 门槛从 2 秒改成 25 秒的原因：changelog 和文档里都没写。
- 2.1.280 里切段的函数（压缩后叫 `Ul`）是不是和 openclaude 的 `splitCommand_DEPRECATED` 一样按 `&& || ; |` 切：照名字、用法推断，没有逐行对。
- codex 在 app-server 这一层有没有另外把后台进程结束告诉模型：只查了 core 的 unified exec 和提示词，没查全。
- DeepSeek（`deepseek-v4.1-flash`）在 Miyu 里被拦以后怎么做、加字管不管用：都没实测。报错那句的 token 数没量。
