## 调研：dsh 的软件快速装卸、即插即用（2026-09-30）

项目主人让记一笔（2026-09-30）：软件的快速装卸、即插即用，去看 dsh（DeepSeek 的 harness）的论文和源码。这份是调研记录，只记，不改设计的决定。真要做的时候（装卸软件包那一段，M8 以后），从第四节的三道题拍板起，再照第三节写进设计。

依据：dsh 的源码和文档（下面的路径相对 dsh 仓库的根，写成 `dsh/…`）；dsh 的 README 指向的论文 *A Programming Paradigm for Spatiotemporal Composability*（Yifan Shi、Wei Zhang、Tianyi Cui，北大、DeepSeek-AI，arXiv 2608.25512，2026-08-26，92 页）。论文细读了引言、5.2、第 6 节和结论，第 3、4 节的形式化只看了算法。

### 一、dsh 怎么做

1. **一切都是插件**，连主循环也是，没有特权内核（`dsh/docs/architecture.zh.md`）。插件树由几层补丁叠出来：组合包的、这套配置的、家目录的。装第三方插件是在配置目录里 `pnpm add` 再往补丁里加一行；补丁文件一直被监听，改了当场按新内容重组，不用重启。
2. **注册是可逆的副作用**（插件框架 cordis 的核心规则，`docs/cordis-primer.zh.md`）：监听、子插件、服务、工具注册都把撤回函数挂在调用它的插件上，卸载时倒序撤回，插件作者不写卸载代码；框架管不到的资源（定时器、连接）包进 `ctx.effect()`。卸载要等真正停稳（子进程等它退出）。
3. **热装、热卸**：配置里一行写 `disabled: true` 就卸掉、行留着，改回来它和等它的插件都重新加载。改配置时按每行的 `id` 比对，只动变了的行，按变的字段选扰动最小的做法（卸载、整行重挂、原地重启），失败就回到旧的。改源码的热重载是一次交易，要么全换要么全回滚。
4. **依赖**：必需依赖用 `inject` 声明，服务没到齐插件停在「等依赖」，不报错也不跑一半，配置里的先后无所谓；提供者被卸载或替换，依赖方跟着卸载，回来再自动加载。可选依赖用的时候看有没有。缺依赖默认不出声，它自己承认是坑，启动器补了一道报缺的检查。
5. **配置改了**：先校验，再重启插件，插件可以否决或者改成原地更新；每个设置项标 `applies: live | restart`；改坏的配置节保留上一次好的值。
6. **能力接缝**：一项能力分声明接口、实现接口、使用接口（给模型的工具）三个角色。例如几个搜索后端注册到同一个接缝上，给模型的工具名归 `tool-web`，换后端工具面不变。
7. **装卸和缓存前缀**：终端版每一步现组装工具面，文档写明注册、卸载「可能从第一个变动的 schema token 起让缓存失效」，变了整份记进日志。网页版严格：会话钉在它加入时的那一代组合上，已经开跑的会话不换组合，只有空会话能换。一次模型请求钉住当时的适配器，热重载不串。技能目录变了在历史末尾追加一份替换目录，不改写前缀。MCP 断线时上一批工具留着、调用报错。
8. **它自己承认的坑**：被换下的旧一代组合永不回收（没记还有几个会话在用）；让模型自己写插件并运行的功能沙箱「不是安全边界」，默认不带。

### 二、论文的论点

- 把动态组合拆成两维：**时间上可组合**（组件移除时，它对共享环境做的修改完整、安全地撤回）和**空间上可组合**（组件声明依赖，运行时在依赖出现、消失、换实现时自动起停它）。
- 对现状的批评：VSCode 装得上卸不干净，下载量前 100 的扩展里 87 个含代码、卸载要重启扩展宿主；靠重启进程、容器编排凑合，丢掉进程里的状态。
- 对 agent harness：以后的 harness 会一边服务一边改自己的组件，没有这两样，每次自改都要重启、打断在跑的任务。结论里把「自进化 harness」列为以后要验证的方向，不是已经验证的结论。
- 加载器靠稳定的 id 增量对账，最终状态只取决于最终配置；卸载先让依赖它的卸完再撤它自己；只有系统独占、能恢复的位置才撤得回，数据发出去了只能补偿；多提供者可以独占绑定，也可以经代理中转（换后端使用方看不到），滚动升级等旧的手上没有在跑的请求再卸；依赖声明本身就是能力申请，可以在加载时审批；依赖成环能静态查出来。唯一的案例是 Koishi，作者自己说只是「存在性和采用情况」的结果，没有定量对比。

### 三、对照 Miyu

**已经是这个方向的**：模块是一份清单加一次注册，没有后门（`05-内核接口.md` 第一节、I1）；会话从快照取策略、工具面会话内字节恒定，和 dsh 网页版的按会话钉住同一个思路，更严（`25-工具加载.md`、`03-事件模型.md`）；故障模块的工具留在目录里（05 I6）；崩溃退避重启、次数有上限（05 第九节）；配置项标明生效时机（`14-配置.md`）；按职能替换（`12-进程形态与分发.md` R8）；权限在清单里声明、安装时人批准（05 I5）。

**值得借的**：
1. 注册都能撤回、由内核负责：模块登记的东西（工具、命令、挂接点、事件种类、页面、订阅、定时器、子进程）都记在它的注册凭据上，停用、卸载、升级时倒序撤回，子进程等退出才算撤完。Rust 里就是丢掉凭据全部撤回。门禁：装上再卸掉，各张表和目录快照逐字节回到装之前。
2. 「等依赖」状态：依赖分必需和可选，必需的没有提供者就停在等依赖、不跑一半；提供者回来自动接着起，换实现跟着重起；安装时查成环；`miyu doctor` 列出在等依赖的和它缺什么。
3. 按变了什么选扰动最小的做法、失败回滚：配置生效时机加一档「只重启这个模块」（外部扩展重起进程、MCP 断开重连）；升级是一次交易，起不来就回旧版本；改坏的配置节保留上一次好的值。
4. 停用、升级那一刻在跑的调用，认它开始时的提供者；停之前先不派新调用、等在跑的结束（有上限），到点的照打断收拾。
5. 工具面归使用方、后端藏在后面：替换分「换后端」（工具面一个字节不变，不动前缀）和「换工具」（照 K3 下一轮生效），能做成换后端的优先。
6. 安装界面写明装上以后工具面多多少 token、正在进行的会话会改写一次前缀（dsh 每个包的 README 要写对模型、token、缓存的影响，有门禁查）。

**不适合的**：每一步都允许增删工具、只在文档里写缓存影响（和工具面字节恒定冲突）；源码级热重载（编进核心的 Rust 模块做不到，也不必，能热换的是外部进程）；模型自己写插件并运行（和安装时人批准冲突）；扁平的全局服务名、缺依赖不出声；可执行的配置表达式；钉住旧一代却不做引用计数。

### 四、做的时候要拍板的（附推荐）

1. **运行中卸载、停用一个软件，已经用过它的会话怎么办**：推荐这个会话里它照旧留在工具面，调用时报「已卸载」，等会话压缩或结束才拿掉（和 05 I6 同一个道理，不多掉一次缓存）；另一种是照 K3 下一轮就拿掉，掉一次缓存。
2. **新装的软件，已有的预设自动打开吗**：推荐安装时问一句在哪些预设里打开，默认勾上当前在用的。
3. **技能、知识库列表变了**：推荐像 dsh 和旧版 Miyu 那样在末尾追加一份替换列表，不改写 system（会话中途新建技能时，不然每建一个就要重算一次前缀）；另一种是保持 `26-提示词.md` 现在的写法（列在稳定区，走 K3）。
