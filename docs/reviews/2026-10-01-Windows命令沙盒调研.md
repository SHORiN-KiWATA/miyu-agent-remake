## 调研：Windows 上的命令沙盒，别家怎么做（2026-10-01）

### 零、Miyu 卡在哪

- 设计（`docs/designs/11-权限与沙盒.md` 第六节 A3）照 codex：专用的沙盒用户、访问控制、每个会话一个受限令牌（带成员自己的限制 SID）、命令跑在单独的桌面上、给沙盒用户登记 git 的 `safe.directory`，装的时候要一次管理员权限。5-8 已经把「装」做完了（`miyu sandbox setup`，建 `miyu-sandbox` 用户，密码 DPAPI 加密存进数据根）。
- 5-9 虚拟机实验（`docs/construction/5-9-Windows：跑.md`）：读写那一层都通了（工作区能写、家目录能读、数据根读写都拒、git 经环境变量登记 `safe.directory` 后照常、每条命令多约 80 毫秒）。
- 卡住的是单独的桌面：
  - 在你登录的桌面会话里：跟你共用当前桌面能跑，另开一个桌面被系统拒绝。
  - SSH 这类没有桌面的会话里：正好反过来。
- 于是 5-9 暂停，Windows 上沙盒用不了，工作区这一级每步问人。

### 一、codex：两套后端，桌面照开，SSH 下一样坏

codex 的 Windows 沙盒在 `codex-rs/windows-sandbox-rs`（`d7b07d4`，2026-09-25）。级别有三个：`Disabled`、`RestrictedToken`（不提升，代码里叫 legacy）、`Elevated`（`codex-rs/protocol/src/config_types.rs:297`）。另有一个可选的 MXC 后端。

| 项 | 不提升（RestrictedToken） | 提升（Elevated） |
|---|---|---|
| 以谁的身份跑 | 你自己，令牌收紧 | 专用的沙盒用户 `CodexSandboxOffline`、`CodexSandboxOnline`，属于一个本地组（`codex-rs/windows-sandbox-rs/src/setup.rs:53-54`，`setup_provisioning/sandbox_users.rs`） |
| 怎么起 | 直接 `CreateProcessAsUserW`，受限令牌 | 两跳：父进程用 `CreateProcessWithLogonW` 以沙盒用户起一个 `codex-command-runner`，runner 再用受限令牌起命令（`src/elevated/runner_client.rs`，`src/bin/command_runner/win.rs` 开头的说明） |
| 令牌 | `CreateRestrictedToken`，标志 `DISABLE_MAX_PRIVILEGE \| LUA_TOKEN \| WRITE_RESTRICTED`，限制 SID 是一组「能力 SID」加登录 SID 加 Everyone（提升的那一套再加沙盒用户自己的 SID）（`src/token.rs` 的 `create_token_with_caps_from`） | 同左 |
| 文件 | 给工作区等可写的地方加访问控制，授给能力 SID。`WRITE_RESTRICTED` 只在「写」的时候查限制 SID，所以只管得住写，管不住读，要限制读的直接拒绝跑（`codex-rs/sandboxing/src/windows.rs` 里那段注释） | 读写都靠给沙盒用户设的访问控制，能限制读 |
| 网络 | 只靠环境变量那一层（官方文档：environment-level offline controls） | 防火墙规则加 WFP 过滤，按离线那个沙盒用户过滤出站（`src/setup_provisioning/firewall.rs:35-49`，`src/wfp.rs:79-84`） |
| 管理员 | 不要 | 装的时候要（建用户、组、防火墙、登录权限）。另有一个 Windows 服务（`codex-rs/windows-sandbox-service`），经命名管道认出是谁，替它做要提升的装配和卸载时的清理，主要给桌面版（MSIX 包）用 |
| 桌面 | 一律另开（配置项 `windows.sandbox_private_desktop` 已删：「legacy Windows sandboxes always use a private desktop」，`codex-rs/config/src/strict_config.rs:271`） | 一律另开 |
| git | 没登记 `safe.directory` | 经 `GIT_CONFIG_COUNT` 这组环境变量登记 `safe.directory`（`src/sandbox_utils.rs:36`） |

**桌面怎么开（`src/desktop.rs`）**

- 名字 `CodexSandboxDesktop-<随机 32 位十六进制>`，建在调用者当前的窗口站上（`CreateDesktopW`）。
- 提升的那一套：父进程（你）建桌面时就给好访问控制：你的用户 SID 全权，沙盒用户 SID「参与者」权限（全权去掉改 DACL、改属主、删除）。代码注释说，`CreateProcessWithLogonW` 会把调用者的登录 SID 盖进新进程的令牌，所以管理权只给你的用户 SID，不给登录 SID。
- 同一个沙盒用户、同一套权限的命令共用一个桌面，缓存在进程里，不随每条命令建、拆。
- 起 runner 时 `lpDesktop` 留空，runner 继承你的 `WinSta0\Default`。runner 起命令时 `lpDesktop` 写 `Winsta0\CodexSandboxDesktop-…`：**窗口站的名字写死成 `Winsta0`**（`desktop.rs:217`、`:253`）。
- `src/process.rs:124-128` 的注释：受限令牌起的进程不设 `lpDesktop`，PowerShell 之类会在 DLL 初始化时失败（`STATUS_DLL_INIT_FAILED`）。

**SSH 下 codex 也没解决**

- [openai/codex#30839](https://github.com/openai/codex/issues/30839)：同一台机器、同一个用户、同一个项目，本地和远程桌面都好，SSH 进去就报「timed out after 15000ms connecting runner pipe-in」。
- [openai/codex#37722](https://github.com/openai/codex/issues/37722)（报告人给的根因）：SSH 会话在 Session 0，窗口站是 `Service-0x0-<LUID>$`。`CreateProcessWithLogonW` 起的 runner 在这个继承来的窗口站和桌面上没有授权，初始化失败（`0xC0000142`）。报告人提议起 runner 前给沙盒用户在这个窗口站、桌面上临时加一条。两个都还开着，没有维护者的修复。
- 所以 codex 是**绕开**了这一关：它只保证本地和远程桌面（交互会话）能用，SSH 下整个沙盒起不来。

**MXC**（`codex-rs/mxc-sandbox/README.md`）

- 直接调微软 MXC 的 `BaseContainerRunner`，不建用户、不改访问控制、不要管理员。要有「进程安全环境」（PSEC）才用，不走 MXC 里 AppContainer 加访问控制的退路。
- 默认关着：`windows.sandbox = "mxc"` 是写死用它，`features.prefer_mxc` 默认关。
- 界面这一层：「Win32k calls and desktop handles remain available for PowerShell startup; clipboard, input-injection, and desktop/system-control restrictions remain.」也就是 MXC 自己管住剪贴板、模拟输入，不靠另开桌面。
- 代价：前台进程退出时 MXC 把剩下的子孙进程都杀掉，放到后台的服务活不下来。
- 微软自己的文档（[microsoft/mxc os-version-support](https://github.com/microsoft/mxc/blob/main/docs/process-container/os-version-support.md)）：进程容器的产品下限是 Windows 11 24H2（26100），原生的 PSEC 那一层要 25H2 起。

**codex 的设计文档**：`docs/` 里只剩一页指向官网（`docs/sandbox.md`）。早先有过 `docs/windows_sandbox_security.md`（2025-11，2026-01 删掉换成链接），当时写着冒烟测试 41 项过 37 项，其中「只读模式下 `Start-Process 'https://…'` 能打开主机的浏览器」列为已知失败。现在的冒烟脚本里这一项还标着「KNOWN FAIL until GUI escape fixed」（`codex-rs/windows-sandbox-rs/sandbox_smoketests.py:914`）。官网的说明页（[Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox)）讲了提升和不提升的差别、装的时候要管理员、两种都默认另开桌面。

### 二、Claude Code：文档说不支持，二进制里已经有一套在灰度

- 官方文档（[sandboxing](https://code.claude.com/docs/en/sandboxing)）：沙盒支持 macOS、Linux、WSL2，「Native Windows is not supported」，Windows 上请在 WSL2 里跑。企业策略要求沙盒而 Windows 上用不了时，直接拒绝执行命令（2.1.280 二进制里的原话：「Enterprise policy requires sandboxing, but the sandbox is unavailable on Windows … Shell command execution is blocked by policy.」）。
- 但 2.1.280 二进制里已经有一套 Windows 沙盒，由特性开关控制（「the Windows sandbox is not active on this session (feature gate off)」），用的是 Anthropic 开源的 sandbox-runtime 里的 `srt-win.exe`：`/sandbox install` 弹一次 UAC，建一个 `srt-sandbox` 用户，装按这个用户 SID 过滤的 WFP，还带 git 的 `safe.directory`。

### 三、Anthropic sandbox-runtime 的 srt-win：桌面这一关的正解

仓库 [anthropics/sandbox-runtime](https://github.com/anthropics/sandbox-runtime)（Apache-2.0，`e87c1096`，2026-09-30），Windows 部分在 `vendor/srt-win-src/`（Rust），README 标着 alpha。它的形状和 Miyu 的设计几乎一样：专用用户、装一次要管理员、文件靠给这个用户加访问控制。

**身份和装**（README「Windows (alpha)」）

- 一次提升的 `windows-install`：建 `srt-sandbox` 用户和一个组，随机密码 DPAPI 加密存在 `HKLM\SOFTWARE\sandbox-runtime`，装 WFP 过滤。能重跑，重跑换密码。
- 每条命令不要管理员。
- 以另一个用户的身份跑，顺带堵住「借别的进程起进程」这一类逃逸（任务计划、BITS、以交互用户身份跑的 COM）：借出来的进程还是这个用户，照样被管着。

**两跳**（`src/logon.rs`、`src/launch.rs`）

- 你这边（它叫 broker）用 `CreateProcessWithLogonW` 以 `srt-sandbox` 起 runner（带 `LOGON_WITH_PROFILE`，沙盒用户有自己的 profile、临时目录）。
- runner 用自己的令牌做一个收紧的令牌，起真正的命令，挂在作业对象里（`KILL_ON_JOB_CLOSE`）。

**桌面怎么过**（`src/winsta.rs` 开头的长注释，关键几处都注明「verified by probe」）

1. 你这边在**自己当前的窗口站**上开一个新桌面，名字 `srt-sb-<pid>-<随机数>`。窗口站的名字是读出来的（`GetProcessWindowStation` 加 `UOI_NAME`），交互会话里是 `WinSta0`，服务、SSH 这类会话里是 `Service-0x0-<登录编号>$`，不写死。读不出来就报错，不猜 `WinSta0`。
2. 新桌面建的时候就明写访问控制：你、`srt-sandbox`、SYSTEM 三个全权。不写的话默认的访问控制只认你，沙盒用户进不来。
3. **给 `srt-sandbox` 在当前窗口站上加一条授权**（`0x2037F`：窗口站的全部使用权加读访问控制，不给改 DACL、改属主、删除）。原因写得很清楚：`lpDesktop` 不为空时，seclogon **不再**替新登录自动加窗口站的授权，runner 挂不上窗口站，子进程 DLL 初始化失败。这一条加了就不撤：它在这个登录会话的对象上，注销就没了。几个并行的命令共用一个窗口站，先结束的撤掉会弄死别人的。
4. 把「窗口站\桌面」这个路径作为 `CreateProcessWithLogonW` 的 `lpDesktop` 传下去，runner 直接落在新桌面上，真正的命令继承它（`lpDesktop` 留空）。
5. runner 查自己在不在 `Default` 桌面上，在的话拒绝跑（fail closed）：说明前面建桌面失败了，命令会和你共用桌面、能装低层键盘钩子记你的按键。
6. 另给 `srt-sandbox` 在这个会话的 `BaseNamedObjects` 目录上加建对象、建子目录的权（msys2、cygwin 的程序要，Git for Windows 带的 bash 这类就是）。

不另开窗口站：非管理员在交互会话里建不了窗口站（`CreateWindowStationW` 拒绝）。另开窗口站多给的那一点（剪贴板、全局原子表分开）改由作业对象的界面限制补上。

**作业对象的界面限制**（`src/job.rs`）：不许读写剪贴板、不许用全局原子、不许碰作业外面进程的窗口句柄、不许改系统参数和显示设置、不许切桌面、不许关机注销。

**令牌**（`src/token.rs` 开头的说明）

- 把令牌里**所有登录 SID 改成只用于拒绝**，Administrators 也是。理由：seclogon 把你的交互登录 SID 盖进了 runner 的令牌，同一会话里你的每个进程默认都给登录 SID 读内存的权（`VM_READ`）。不去掉，沙盒里的命令能读你浏览器、终端、宿主程序的内存。
- 不用限制 SID（没有 RestrictingSids）：它说那样会弄坏 Schannel、LSA 的 RPC，也就是 HTTPS、git 走系统 TLS 这类。
- 完整性级别照普通用户（Medium），特权只留 `SeChangeNotifyPrivilege`。
- 访问控制、WFP 都只认沙盒用户的 SID，不认登录 SID（`src/logon.rs` 开头）。

**测试**：它的 CI 在 GitHub 托管的 Windows 机器上跑（x64、arm64，这些机器以管理员身份跑、UAC 关着，建用户、装 WFP 都不用另外提升），装、执行、访问控制、杀进程树、桌面隔离都有冒烟脚本。桌面那一项（`ci/smoke-exec.ps1` 的 R12）查子进程确实在 `srt-sb-*` 桌面上（`.github/workflows/integration-tests.yml`）。

**它写明的限制**（README「Known limitations」，挑和 Miyu 有关的）：装在你个人目录下的工具（nvm、Scoop、`pip install --user`、`%LOCALAPPDATA%\Programs`）沙盒用户打不开，要么机器级安装、要么把路径加进可读。Miyu 已经定了「家目录整个可读」，这一条对 Miyu 不成问题。

### 四、别家一两句

- **dsh**（`packages/sandbox/sandbox-windows-acl/README.md`，`47f94385`）：不建用户，不要管理员。把你自己的令牌复制成 `WRITE_RESTRICTED` 的，限制 SID 是工作区 SID、临时目录 SID、登录 SID、Everyone。只管写，自己标成「部分收紧」（Everyone 能写的地方、硬链接都挡不住）。读、网络、看进程都不管。桌面不隔离：受限令牌下另开控制台的子进程初始化就死（`0xC0000142`），只好共用。它的设计记录说拒了 MXC（要 24H2 起、读任意路径要大面积改主机的访问控制）和 AppContainer（读不了任意路径）。
- **opencode**（`696f41bc`）：没有命令沙盒。
- **pi**（`5fd446c`）：核心没有。示例扩展 `packages/coding-agent/examples/extensions/sandbox/` 套 Anthropic 的 sandbox-runtime，注释里只写了 macOS、Linux。
- **Windows Sandbox（系统自带的）**：一次性的轻量虚拟机，每次开都是干净的系统，主机上装的软件里面没有。只有专业版、企业版、教育版有，家庭版没有，同时只能开一个（[微软文档](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/)）。拿来跑开发命令太重，也用不了你装好的工具链。
- **Sandboxie**：靠内核驱动把文件、注册表重定向到一个沙盒目录。要装驱动，不适合随 Miyu 发。
- **AppContainer**：不要管理员，但只能读授了权的路径，dsh 和 Miyu 以前都因为开发工具在里面能不能跑没把握没选（A3 未选 B）。
- **MXC**：见上面 codex 那一节。原生那一层要 Windows 11 25H2 起。

### 五、「单独的桌面」这一关

**Miyu 实验里的两种现象，照 srt-win 的注释都讲得通**（推断：实验程序没进仓库，没法逐行对）

- 交互会话里另开桌面被拒：`CreateProcessWithLogonW` 的 `lpDesktop` 一旦指定，系统就不替沙盒用户加窗口站的授权（微软文档 [CreateProcessWithLogonW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createprocesswithlogonw) 的 `lpStartupInfo` 一节：「The application must add permission for the specified user account to the specified window station and desktop, even for WinSta0\Default.」）。新桌面默认的访问控制也只认建它的人。两样缺一样，新进程就挂不上。
- 交互会话里共用能跑：`lpDesktop` 留空时，新进程带着你的登录 SID，`WinSta0` 和 `Default` 本来就认这个登录 SID。
- SSH 里共用不行：窗口站换成了 `Service-0x0-…$`，沙盒用户在它上面没有授权（和 codex#37722 的根因一样）。
- SSH 里另开能跑：推测实验程序在当前窗口站上建桌面、明写了访问控制。没有实验程序，不确定。

**三家的做法**

- codex：只在交互会话里另开，窗口站写死 `Winsta0`。runner 先落在 `Default` 上靠登录 SID 挂住窗口站，命令再去新桌面。SSH 下不通，issue 还开着。
- dsh：不隔离桌面。
- srt-win：两种会话一套路子。在当前窗口站上开新桌面、明写访问控制、给沙盒用户在当前窗口站上加一条授权，路径读出来不写死。runner 不在 `Default` 上才跑。

**srt-win 的路子在 SSH 会话里一定行吗：没有直接证据。** 它的代码按「当前窗口站」写，注释里点了 `Service-0x0-…$` 这个名字，CI 在 GitHub 的 Windows 机器上验过桌面隔离。但没看到专门的 SSH 测试。它给窗口站加授权靠的是「你对自己的窗口站有改 DACL 的权」，服务会话里你有没有这个权，要在虚拟机里试。

**真要不通时还有一条退路**（推断）：SSH、服务这类会话本来就和你登录的桌面分属不同的会话，窗口消息、模拟按键、截屏跨不了会话，剪贴板也是按窗口站分的。「单独的桌面」要防的「给你的窗口发按键、读你的屏幕」，在这种会话里已经被会话隔离挡住了。这时共用继承来的桌面（只要照 codex#37722 的提法给沙盒用户在这个窗口站、桌面上加授权），加上作业对象的界面限制，风险很小。这是安全上的取舍，列在第八节第 3 题。

### 六、照 srt-win 做，Miyu 要改什么

Miyu 现在的形状（`docs/blueprint/sandbox.md`）：核心经助手 `miyu-sandbox run` 起命令，Windows 上助手起子进程、等它。正好对得上两跳：核心是 broker，助手是 runner。

1. **起助手**：核心用 `CreateProcessWithLogonW` 以 `miyu-sandbox` 起助手（密码从 5-8 的记录里解出来），`lpDesktop` 是下面第 2 条的「窗口站\桌面」。要不要 `LOGON_WITH_PROFILE`（沙盒用户自己的临时目录、注册表）照 srt-win 定。
2. **桌面**：核心在当前窗口站上开一个新桌面，访问控制明写本人、沙盒用户、SYSTEM。窗口站名字读出来，不写死 `WinSta0`。桌面的句柄核心拿到命令结束再放。几条命令共用还是每条一个，codex 共用、srt-win 每条一个，按实验定。
3. **窗口站授权**：核心给沙盒用户在当前窗口站上加一条 `0x2037F`，幂等，不撤。
4. **命名对象目录**：给沙盒用户在会话的 `BaseNamedObjects` 上加建对象、建子目录的权（Git for Windows 带的 bash、ssh 这类要）。
5. **令牌**：助手用自己的令牌做收紧的令牌，登录 SID 和 Administrators 改成只用于拒绝，特权只留 `SeChangeNotifyPrivilege`。登录 SID 这一条对 Miyu 尤其要紧：核心的进程在同一个会话里，内存里有本机令牌，不去掉的话沙盒里的命令读得到核心的内存，`11-权限与沙盒.md` A6「沙盒冒充不了本人」就不成立了。
6. **成员隔离的限制 SID 要重新核对**：A3 写的是每个成员一个限制 SID。srt-win 说带限制 SID 的令牌会弄坏 Schannel、LSA 的 RPC。codex 用的是 `WRITE_RESTRICTED`（限制 SID 只在写的时候查），能用，但限制 SID 就只管写，成员之间「读」的隔离要靠访问控制另外做。这是技术题，照「技术题按推荐定、留痕」处理即可：推荐照 codex 用 `WRITE_RESTRICTED`，读的隔离照访问控制，实验时把 HTTPS、git 走系统 TLS 一起验。
7. **作业对象**：加上 srt-win 那一组界面限制，外加随核心停而杀掉整棵树（Miyu 已经有看门的，对一下两者怎么共存）。
8. **fail closed**：助手起来先查自己在不在 `Default` 桌面上，在的话不跑，照「收紧不成」退出 125（`sandbox.md` 助手的退出码）。
9. **git**：照实验和 codex，经 `GIT_CONFIG_COUNT` 这组环境变量登记 `safe.directory`。
10. **网络不用做**：Miyu 定了沙盒不管网络（A5），WFP、防火墙这一大块整个省掉。srt-win、codex 的代码量里这部分占不少。
11. 5-8「还没有的」里记着的照旧：`remove` 先停掉以沙盒用户身份在跑的进程，`miyu doctor` 读装好的记录。

**管理员权限**：和现在的设计一样，只在装的时候要一次（5-8 已做）。每条命令不要：建桌面、给窗口站和命名对象目录加授权，srt-win 都是用你自己的权做的（它在交互会话里探过）。服务、SSH 会话里你有没有这些权，待实验。

**工夫**：参照体量，srt-win 的 Rust 源码约 45 万字节（注释很多），其中和 Miyu 有关的几块（桌面和窗口站、两跳、令牌、作业对象）约 9 万字节。codex 的 `windows-sandbox-rs/src` 约 100 万字节。Miyu 不做网络、装的那一步已经有了，估计是「一次一两天的虚拟机小实验，加上和 5-8 差不多大的两三张施工单」。这是估计，没有逐项拆。

### 七、推荐

- **照 srt-win（Anthropic sandbox-runtime 的 Windows 部分）的做法，不照 codex。** 两家身份、装法一样，但 srt-win 过桌面这一关的办法两种会话一套，codex 写死 `Winsta0`、SSH 下起不来。srt-win 也是 Apache-2.0，注释把每个坑的原因和验证写清楚了，能直接当图纸的参考。
- **管理员只在装的时候要一次**，现在的 5-8 不用改。
- **什么时候接着做**：先在一个空档做一次虚拟机小实验（一次性程序，不进仓库），只验第六节第 1 到 5 条，在本地登录、远程桌面、SSH 三种会话里各跑 cmd、PowerShell、git、cargo，外加 HTTPS。实验过了，5-9 排在 M8（终端界面）之后、对外说支持 Windows 之前。理由：项目主人平时用 Linux、macOS，Windows 上现在每步问人也能用，不挡任何一个里程碑。CI 能照 srt-win 在 GitHub 的 Windows 机器上跑装、起命令、桌面这几项冒烟（那里是管理员、UAC 关着），交互桌面和 SSH 两种会话还得靠虚拟机。

### 八、要项目主人拍板的

1. **Windows 沙盒照哪家的做法**
   - **照 srt-win：专用用户，桌面在当前窗口站上另开、给沙盒用户加窗口站授权（推荐）。**
   - 照 codex：同样的专用用户，桌面写死 `WinSta0`，SSH 下不支持沙盒。
   - 先不做，等 MXC：不要管理员，但要 Windows 11 25H2 起，codex 也还默认关着。
2. **什么时候接着做**
   - **先在空档做一两天虚拟机小实验验桌面这一关，5-9 排在 M8 之后（推荐）。**
   - 实验和 5-9 现在就接着做。
   - 等有 Windows 用户的真实需求再说，Windows 上一直每步问人。
3. **实验里 SSH、服务这类没有桌面的会话，另开桌面还是不通时**
   - **共用继承来的桌面、给沙盒用户在上面加授权，加上作业对象的界面限制：这种会话和你登录的桌面本来就隔着会话，发按键、截屏跨不过去（推荐）。**
   - 这种会话里算沙盒用不了，每步问人。

### 九、没查到、不确定的

- srt-win 的路子在 SSH、服务会话里行不行：代码按当前窗口站写，CI 验过桌面隔离，但没看到专门的 SSH 测试。服务会话里你有没有权给窗口站、命名对象目录改授权，没有证据。
- Miyu 实验里交互会话「另开被拒」的真正原因：实验程序没进仓库，第五节的解释是照 srt-win 的注释和微软文档推的。
- GitHub 托管的 Windows 机器上跑的是交互会话还是服务会话：没查。srt-win 的桌面冒烟在那里是过的。
- codex 提升的那一套，命令令牌里登录 SID 是开着的：它能不能读同会话里你的进程内存，没核实，只是 srt-win 专门堵了这一条。
- codex 冒烟里「打开浏览器」那一项现在是不是还失败：脚本里还标着已知失败，没跑过。
- 工夫是照代码体量估的，没有逐项拆。
