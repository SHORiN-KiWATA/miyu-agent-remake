## 施工单 4-1：工具接口和工具面

状态：施工中。

### 目的

工具有了接口和目录：每件工具报出自己的名字、给模型看的说明、参数格式和访问类别，核心起来时登记进工具目录。造会话时，照目录把工具面存进策略快照：会话里每次请求的 tools 数组都照它发，逐字节不变；载入时照快照重建。内核照快照拿到每件工具的访问类别和参数格式，查调用、修正参数都照它。

### 不做什么

- 执行工具、执行中的输出、叫停：4-2。
- 显示名、摘要：4-5。
- 默认超时：M4 的几件各自管自己（`shell` 有自己的超时，4-8），要统一的超时，等有工具用得上再加。
- 存根、按组加载、改描述：M4 全是全量（施工方案第三节）。
- 按预设挑哪些工具：预设那一步。
- 老会话换成新目录的工具面（`02-内核.md` K3）：以后随扩展的安装、升级做。

### 我定的

- **4-1、4-2 换个先后**：原来先做执行、再做工具面。可执行要测，会话的策略里先得有工具：内核照策略里的工具规则查调用，策略里没有的一律回「没有这件工具」，走不到执行。所以先让工具面进快照，下一步测执行时策略里就有了。
- **接口放在第 3 层的新 crate `miyu-tool`**：工具是执行器（01 第九节），第 3 层的基础系统（4-4）照它实现，第 4 层的会话照它执行。第 2 层的策略快照不依赖它：造会话时，会话把规格换成内核的类型（名字、说明、参数格式、访问类别）交进去。
- **规格先有四格**：名字、说明、参数格式、访问类别。说明和参数格式原样进 tools 数组，一个字节不改（05 第七节：参数格式原样照抄）。
- **登记时就查**，查不过的核心起不来，报是哪一件、哪一条：
  - 重名的：工具名是模型认的，两件同名，她调的是哪一件说不清。
  - 名字不合写法的：各家供应商对函数名的限制都是英文字母、数字、`_`、`-`，1 到 64 个字符。不合的，每次请求都会被供应商拒收。
  - 参数格式不是 `{"type":"object",…}` 的：理由相同，供应商只收对象。
  - 说明写得好不好（英文、不超过三句）不在这里查：出厂的工具各自有测试守着，改描述那一步另有检查（`25-工具加载.md` 第五节）。
- **快照里的工具面照名字排**，和组装器排的一样，交进来的先后不影响字节。每件记名字、说明、参数格式、访问类别四格，照这个先后。
- **没有工具的快照，字节和以前一样**：工具面这一格空的不写。M3 造的会话，快照照旧读得回来，哈希不变。
- **读回来的快照也查重名**：从磁盘读回来的快照里有两件同名的，造策略时报错，不载入。
- **目录这一步是空的**：核心起来时一件工具都不登记，`miyu ask` 发的请求和现在一样，没有 `tools`。4-4 起把基础系统登记进来。
- **登记完就冻结**：核心跑着的时候目录不变。现在没有预设，目录里的全开。

### 验收

1. `step/4-1-tool-face` 分支的 CI：三台机器全绿，长跑也绿。
2. `cargo test`：
   - 工具目录：照名字排，和登记的先后无关；重名的、名字里有空格或中文的、长过 64 个字符的、参数格式不是对象的，都登记不上，报是哪一件、哪一条。
   - 快照：有工具的快照，读回来一样，工具面照名字排，每件四格照先后；没有工具的，字节里没有这一格，和 M3 造的一样（照一份 M3 的快照字节比）；造出的策略里，组装器拿到工具面，内核拿到每件工具的访问类别和参数格式；读回来有重名的，报错。
   - 会话：造会话时交进两件假工具（登记的先后倒过来），请求里的 tools 照名字排；载入以后再请求，tools 和 system 逐字节一样；空目录造的会话，请求里没有 tools。
3. 故意改坏一些地方，全部有测试变红。清单施工时列，照实记。
4. `cargo xtask check` 七项全过；推之前本机用交叉 clippy 查 Windows、macOS。

### 风险

- **快照的字节变了**：新加的一格空着的时候不写，M3 的会话照旧载入得了；测试照一份 M3 的快照字节比。
- **说明、参数格式被重新写了一遍**：重新序列化会改字节。存原样的 JSON（`RawJson`），测试比字节。
