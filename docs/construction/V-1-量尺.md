## 施工单 V-1：量尺

状态：施工中（设计 `30-插件框架.md` 第十二节第三阶段，2026-10-10 主会话排；量法照 `23-性能预算.md` 第一节；技术细节主会话定）。

### 目的

第三阶段要照 23 的预算查一遍性能，先得有一把尺。这一步照 23 第一节的量法量核心这一边，原始数据入库，打一张对照预算的表。V-2 照这张表一项项查、修；V-3 让它进 CI。

### 这一步做什么

1. 工具 crate `miyu-perf`：不属于任何一层，谁都不许依赖（登记在 `01-架构.md` 第九节规则 5）。量的是 release 构建出来的真 `miyu`：
   - 自带一个本机回环上的假模型服务，照 openai-chat 的写法，每个请求都回同一段字，记下每个请求的头什么时候到。
   - 数据根是沙盒，放在 `target/perf/` 下。不放系统的临时目录：那里常是内存盘，同步不算数。
   - 模型的资料不写窗口：没有压缩线，大会话不会自动压。
2. 量这几样：

   | 项 | 怎么量 | 对照 23 第二节 |
   |---|---|---|
   | 冷启动 | 拉起 `miyu core` 到它写来 `ready`；再连上、握手、造一个会话、订阅它，就是能提交第一轮。先空跑一次建好数据根，再量 N 次，报 p50、p95 | 冷启动到能打字 150 ms：头停着，只量核心这一截 |
   | 热启动 | 核心在跑：连上、握手、订阅一个没载入的小会话，N 个会话各一次 | 热启动到能提交第一轮 200 ms |
   | 核心空闲 | 起来以后不开会话，量 PSS、私有匿名内存 | 30 MB |
   | 每多一个会话 | 十个会话各说一句、都订阅着，涨的除以十 | 5 MB |
   | 大会话 | 真说出来的一个会话，到一万条事件；载着它的内存；不订阅了、等会话 actor 空闲退出以后再量一次 | 23 第一节要量，第二节没单列 |
   | 一次请求的投影 | 大会话上说一句，到假服务收到请求头：含落盘、组装、编码、连接，是投影的上界；会话长大的一路上每一轮都记 | p95 5 ms |
   | 从头投影 | 重启核心，订阅大会话（从头读日志、重放），再说一句到收到请求 | 100 ms |
   | 追加并同步 | 在进程里：大会话的事件一条一条追加进一份新日志，每条同步一次，报 p50、p99 | p99 20 ms |
   | 二进制 | `miyu`、`miyu-sandbox` 的大小，和 strip 以后的 | 没有预算，记下 |

3. 内存按进程分开报：核心和它拉起的子进程各一行。
4. 结果放 `docs/perf/`：
   - `<日期>-<系统>-<架构>.json` 是原始数据：每一次量的毫秒数、字节数；
   - 同名的 `.md` 写条件和对照预算的表。
   - 条件写机器（CPU 型号、核数、内存）、系统、内核、rustc、提交；不写主机名、用户名、路径。
5. `cargo xtask perf`：先单独编 `cargo build --release -p miyu -p miyu-sandbox`，测试用的开关不混进去；再编 `miyu-perf`，跑它。

### 施工时定的

- 请求编号整个进程里不重复。核心照编号认重发：造会话交回上一次造的那一个，说话不再开一轮；连接换了、核心重启了都照认。试跑时撞过一次，每个连接从 1 数起，大会话第一句就等不到请求。
- 预算照 23 第二节的表读，不抄进代码。F1 说预算是策略数据，校准时改那张表，量尺跟着比；表里缺了要比的一行，量尺一开始就报错。
- 模型名不在目录里，资料没有窗口：大会话不会被自动压缩。
- 这次量的二进制是 main `0d47545a` 的代码。表里提交写的「+改动」是量尺自己还没提交的文件，`miyu` 依赖的 crate 一个都没动。
- 量完以后预算改了（23 F5，2026-10-10 项目主人定：人整段等着的，上限 60 ms，照 p95 比）：冷启动到能打字、热启动到能提交第一轮、从头投影三行改成 p95 60 ms。量尺多了 `--render`：照入库的原始数据、照现在的预算重出表，不用再量一遍。这一份的表就是照它重出的，原始数据没动。

### 量到的

2026-10-10 在一台 Linux 笔记本上量（`docs/perf/2026-10-10-linux-x86_64.md`）。

超了预算的四处，交 V-2：

1. 一次请求的投影：一万条事件时 p95 24.8 ms，预算 5 ms。每多一千条事件约多 2 ms，像是每次请求整段重算（`08-上下文投影.md` 第一节说投影是增量算的）。V-2 先拆开看时间花在哪一段。
2. 热启动到能提交第一轮：重启核心后打开大会话 p50 95.8 ms、p95 107 ms，预算 p95 60 ms。订阅时从头读日志、重放；07 第七节设计的投影缓存还没做。小会话 p95 2.7 ms，过。
3. 核心空闲：PSS 31.8 MB，预算 30 MB；匿名 17.2 MB。
4. 载着一万条事件（日志 9.7 MB）的会话，核心占 111 MB，匿名 90 MB。不订阅了、等 200 秒（会话 actor 空闲退出）以后一点没降；重启再打开、说一句以后是 127 MB。23 第三节的分配器纪律（glibc 上限 arena、空闲时 trim）还没做。23 第二节没单列这一项，算发现。

过了的：

- 热启动：订阅没载入的小会话 p95 2.7 ms。
- 从头投影：p95 36.4 ms。
- 追加一条并同步：p99 2.4 ms。
- 每多一个活动会话：0.97 MB。

没有预算的：冷启动到 `ready` p50 22.7 ms，到能提交第一轮（核心这一截）p50 55.9 ms、p95 58.5 ms，头还没算进去，离 60 ms 只剩一点；二进制 `miyu` 46.5 MB，strip 以后 34.7 MB。
