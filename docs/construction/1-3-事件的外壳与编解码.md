## 施工单 1-3：事件的外壳与编解码

状态：已拍板（2026-09-26），施工中。

### 目的

一条事件能写成一行 JSON，也能从一行 JSON 读回来。认识的种类读成对应的类型，不认识的原样留着。这一步先用 `message.user` 打通，其余种类在 1-4 到 1-6 一种种加。

### 图纸

`03-事件模型.md` 第二节「外壳的写法」，这一步新画的：字段顺序、可选字段、`kind` 的写法、认识和不认识的种类怎么读，附两个样子。顺手把那一节事件示例里的调用编号改成了现在的写法（`"c1"` 改成 `"call_44_1"`）。

### 做什么

| 文件 | 装什么 |
|---|---|
| `crates/miyu-kernel/src/event.rs` | 事件的外壳、按种类读 `body`、写成一行和从一行读回 |
| `crates/miyu-kernel/src/event/message.rs` | `message.user` 的 `body` |
| `crates/miyu-kernel/src/id.rs` | 事件种类的名字 |
| 施工图 | 1-3 那张图纸 |

测试照前两步：图纸上的两行读写一字不差，而且第一行认得出是 `message.user`；每条规则各有一个坏例子。

### 不做什么

- 别的种类：1-4 到 1-6。
- 一行一行地存进文件：3-2 做存储的时候再做。这一步只管一条事件和一行文字之间的转换。
- 内存里的日志：1-7。

### 我定的

- **可选字段写成 `null` 也当没有**：我们自己写的时候没有就不写，从不写 `null`。严格起来就得给每个可选字段单写一段读法，挡的是一件不会发生的事，不值得。
- **认识的种类 `body` 坏了就报错，不当成不认识的**：当成不认识会把坏数据悄悄藏起来。报错里写明是哪一种的 `body`。
- **内存里的事件不带原文**：原文在日志文件里（03 第八节第 5 条），要原文的地方从文件取，内存里只放读好的类型。
- **`message.user` 这一步只有 `blocks`**：别的字段（群里谁说的、是不是冲她来的）等用到的那一步再加，格式演进的规则允许加字段。
