## 施工单 6-7：被动压缩

状态：施工中。

### 目的

本地估算偏小（例如图片算少了）、主请求被供应商报上下文超长时，不再直接出错结束：先压一次，再重发。

### 蓝图改哪几节

- `compaction.md` 第六条写实（已随这张施工单改）：主请求报 `context_too_long`、一个字都没收到、这一步还没压过的，落了盘先压（`trigger` 是 `overflow`）再重发一次；暂停着的不压；「压完很快又到线」照样算，到了次数写暂停、照出错结束；尾巴至少留最后一组，最后一组比预算大也留；没有能压的照出错结束；收到过输出的不压不重发。第十条第 3 条：压完重发还是超长，照一次失败算。
- `kernel/session.md` 收回复第 7 条（已改）。
- 为什么最后一组大也留：自动压缩到线时，最后一组太大就不留尾巴，压进摘要；被动压缩是重发，她得看得到自己刚做的那一步，不然重发的请求里只剩摘要，接不上。

### 不做什么

- 摘要请求自己超长：6-6（中）的截短，不走这里。
- 本地估算怎么调准：看实测再说，这一步只兜底。
- 真模型上撑爆窗口：开发端点一百万 token，太贵；执行器替身、随机测试守着。

### 验收

1. 测试：主请求报超长先压再重发、压的是 `overflow`、`model.called` 的 `compaction` 是 `overflow`；收到过半截的不压；重发还超长照出错结束、算一次失败（连着 3 次照样暂停）；一步只压一次；暂停着不压；快满到了次数写暂停；尾巴至少留最后一组、大的也留；没有能压的照出错结束；随机测试里主请求报超长和别的交错。每一条退回改之前的代码会报红。
2. 请求形状探针、组装样本：没报超长的字节不变。
3. 手写的变异全被逮住；`cargo xtask check` 全过；三台机器的 CI 全绿。

### 风险

- 最后一组本身就撑爆窗口的（一次读进一个巨大的文件）：留下它，重发照样超长，照失败算，连着失败暂停，告诉人。和 Claude Code 一样。
- 报超长的判定靠驱动的分类：各家的说法漏了的，照别的错结束，不压。
