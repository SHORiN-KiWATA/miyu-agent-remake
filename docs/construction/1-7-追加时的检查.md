## 施工单 1-7：追加时的检查

状态：已拍板（2026-09-26），施工中。

### 目的

每往一个会话的日志里追加一条事件，就先查一遍规矩：序号连续、回合一个接一个、每个结果对得上调用、压缩只前进、撤销不越过压缩。坏的事件进不了日志。以后 M2 的回合状态机追加时走这里，从磁盘载入日志也走这里。

查规矩只用一本小账，事件本身不留在内存里（2026-09-26 项目主人提醒：日志全放进内存会一直膨胀）。

### 图纸

- `02-内核.md` 第九节「日志追加时查的规矩」，这一步新画的：九条规矩和各自的出处；只查日志自己能判断的；账本里记哪几样；不认识的种类查什么。
- `07-存储.md` 第七节补一条：活动的会话在内存里只留账本和最近一次压缩以后的事件。
- 1-4、1-5、1-6 留给这一步的几条检查，都在这张表里。

### 做什么

| 文件 | 装什么 |
|---|---|
| `crates/miyu-kernel/src/ledger.rs` | 日志的账本：下一条该是几号；追加一条事件时查九条规矩，查过了就记下这一条带来的变化 |
| `crates/miyu-kernel/src/ledger/tests.rs` | 一段合规的会话从头追加到尾，打断、压缩、撤销都走一遍；每条规矩一个违反的例子：被拦下、报错说清、账本不变 |
| `crates/miyu-kernel/src/lib.rs` | 登记新模块 |
| 施工图 | 1-7 那一张图纸 |

### 不做什么

- 留住事件本身：投影要用的最近一次压缩以后那一段，1-9 做有效历史时留；更早的只在磁盘上，3-2 写日志文件。
- 截掉不完整的尾巴：3-2。
- 崩溃以后给没走完的回合补「中断」：2-8。
- 撤销正在进行的回合、同一个回合撤两次该怎么办：图纸没画到，2-8 做撤销命令时定。
- 一步里的几条事件要么全进、要么全不进：先一条条查。违反规矩只会是内核自己的 bug，或者坏了的日志文件，两种都要停下来查，用不着回滚。

### 要拍板的

没有。这一步全是技术细节，照图纸来。

### 我定的

- **追加前就查，违反的不追加**：日志只增不改，坏事件进去了就删不掉，后面的投影、状态都会跟着错。所以在门口拦。
- **账本只记查规矩要用的几样**：下一条的序号、有没有会话创建、正在进行的回合和它还没有结果的调用、最近一次压缩到哪、那以后开过的回合。还没有结果的调用只会在正在进行的回合里；压缩以前开过的回合不能再撤，压一次就能从账本里丢掉。所以账本不随日志变长。
- **查结果只看还在等结果的调用**：对不上的，不管是根本没有这个调用、还是它已经有了结果，都拦下，报错一句说清。这样不用回头翻那条消息，账本里也不存全部调用的清单。
- **序号由追加的一方给，账本只查对不对**：账本告诉你下一条该是几号。从磁盘载入时事件本来就带着序号，这样新写的和载入的走同一条路，规矩只有一套。
- **用 `BTreeSet`**：纯逻辑的层不许用 `HashMap`（`01-架构.md` 第九节）。
- **不查时间的先后**：时钟可能往回拨，例如对时。查了反而会让一个好好的会话写不进去。
- **报错写中文**：给查问题的人看，写明第几条、违反了哪一条规矩。和编号、时间的报错一样，不原样转给模型。
- **以后加的规矩，不能让已经写下的日志读不进来**：日志一直留着，老日志要永远读得懂（`03-事件模型.md` 第八节）。所以新规矩只能加在从来都成立的事上，例如新加的种类。

### 风险

- 规矩写错了，会把好好的日志拦在外面，会话载入不了。防：测试里那段合规的会话把九条规矩都走一遍，每条规矩还有一个违反的例子。
- 回合状态机（M2）以后可能写出这张表没想到的先后，例如撤销正在进行的回合。防：到时先改图纸上的这张表，再改代码。
