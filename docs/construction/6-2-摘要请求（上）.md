### 已定（我定的技术细节）

**什么时候查、查什么**

- 在 `advance()` 的「准备好」里：先组装主请求，算用量（`estimate::usage`）和压缩线（`estimate::line`）。用量超过线，先压；没超，照旧发。
- 要算得出线，得有两样：
  - 策略里有压缩的数：`Policy.compaction`；
  - 执行器交来的模型限额：新输入 `Input::Limits { model, window, max_output }`。
- 缺一样，就不主动压：没交限额的、没报窗口的、策略里没有压缩的。
- `Limits` 执行器在造会话、载入以后交一次，换了模型再交；6-2 只有替身交，真执行器随 6-3。
- 图片、文件的估算用策略里的数（`estimate::Flat`，出厂各 2000）；DeepSeek 的图片算法随 6-3。

**替代到哪（N）**

「这一轮要回应的话」是：以前的回合里的请求没看到过、这一轮的回复也没看到过的人的消息；这一轮还没有回复的，加上触发它的那一条。

- 这一轮里认回复，不认请求：请求出错、没回复的，她没真看到。
- 以前的回合里请求看到过的，照常压：那一轮已经过去了，摘要请求也才接得上上一次请求的前缀。
- 「边界」是这些话里最早的那条。有边界，N 是边界前面那一条：这一轮的触发、排着队接过来的、开头注入的事实，都留在尾巴里。
- 没有边界（回合中途，也没有排着队的新话），N 是落了盘的最后一条。
- 一组不拆：N 落在一条回复和它的工具结果之间的，退到这条回复前面。回合中途排着的新话，序号在这一步的结果前面。
- 有效历史里第 N 条及以前没有人的消息、回复或工具结果的，不压，照旧发主请求（压了也腾不出地方，还会一直压下去）。N 不比上一次压缩的 `upto` 晚的也是这样：那以前的早就替代掉了。

**摘要请求**

- 组装接口多两个方法：
  - `Assembler::summarize(&History, upto) -> Request`：请求到第 N 条为止，最后是摘要指令；
  - `Assembler::summary(&[Block]) -> Option<String>`：从回复里取出摘要。
- 默认的组装器，`summarize` 分三步：
  1. 用 `History::until(N)` 截出有效历史的前一段，只留第 N 条及以前的，检查点照留；
  2. 照平常组装；
  3. 摘要指令接在后面：最后一条是 user 的，指令并进这一条，做它的最后一块；不是的，另起一条 user。
- `continuation` 是假：最后是人这边的指令，不接着写。
- 第 N 条及以前，就是第 N 条刚写下时的有效历史，所以请求是上一次请求的前缀延伸。
- 指令的字在 `resources/core/compaction/summarize-task.txt`，照 Claude Code 的「压到某一条为止」那一版改写，用自己的话，写成英文。进快照的 `core` 和组装器的 `Texts`，量 token、进登记簿。
- **取摘要**（`summary`）：
  - 只看正文块，思考不要。
  - 有 `<summary>` 的，取它和 `</summary>` 之间的；没有收尾的，取到末尾。
  - 没有 `<summary>` 的，去掉 `<analysis>…</analysis>` 那一段，剩下的当摘要。
  - 前后空白去掉，是空的就算没取到。

**请求在路上**

- 摘要请求也是一次 `Stage::Asking(Call)`，`Call` 多一格 `compaction`，记三样：N、`expected`、已经收到的字数。
  - 打断、有计划的重启、`RequestSent`、增量，照旧走同一条路。
  - 名字 `seen` 是 N，发的动作还是 `Action::CallModel`。
- 不算步数（`requests` 不加）。
- 重试次数和这一步的主请求合用一个计数。等着再来时不标「下一次是重试」：再来的是摘要请求，它后面那一次主请求照常算一步。
- 增量不推 `model.delta`，改推瞬时事件 `compaction.progress { seen, written, expected }`：
  - 正文块每来一段，推一条；
  - `written` 是到这时收到的正文字数，草稿加摘要，照 Unicode 字符数；
  - `expected` = 压缩前的用量，夹在 20000 到 80000 之间（openclaude 的做法：输出约是输入的四分之一，一个 token 约四个字符）。

**说完了**

- **取到了摘要**：
  1. 记一条 `model.called`，`seen` 是 N、`result` 是 `ok`，不写 `message.assistant`；
  2. 写 `context.compacted { upto: N, summary, trigger: auto }`，`by` 是内核，`cause` 是回合的；
  3. 环境、权限两块事实和压缩以后的有效历史比，比不到的注入；
  4. 回到「准备好」，这一批落了盘，再照常组装主请求。
- **说完了，但取不到摘要，或者回复里调了工具**：`model.called` 记成出错，分类是新加的 `bad_summary`（内核查出来的）。这一轮以出错结束，不重试。回复里调了工具的，6-6 改成隔离式。
- **可以重试的错**：照 3-5 的规矩等着再来。到点回到「准备好」，再查一次，再发一次摘要请求。
- **不能重试的错**：这一轮以出错结束。
- **打断**：记一条被打断的 `model.called`，不写 `context.compacted`，这一轮照打断收尾。
- **有计划的重启**：照请求在路上时的规矩收尾。

**别的**

- 指纹：摘要请求也记进「上一次请求」。压完的第一次主请求，`model.called` 里会有 `first_difference`，前缀重置看得见。
- 锚：摘要请求的 `model.called` 排在检查点前面，出错的不是 `ok`，都当不了锚（6-1 的挑法不用改）。
- 快照：`Snapshot.compaction` 装四个数（输出预留的上限 20000、余量 13000、图片 2000、文件 2000）；摘要指令装在 `core.compaction.summarize_task`。以前造的快照里没有这两格，读成「没有压缩」：那些会话不主动压。

1. **内核的单元测试**：
   - 查不查：到线才压、正好在线上不压、没交限额的不压、没有窗口的不压、策略里没有压缩的不压、出错再来的也查。
   - N 怎么取：
     - 回合开头，触发那句和开头注入的事实在检查点后面；

   - 摘要请求：是有效历史到第 N 条的投影加指令；指令并进最后一条 user、或者另起一条；`seen` 是 N；不算步数。

**施工中改的**（都改进了蓝图）：

- **「这一轮要回应的话」**：原来是「还没有哪条回复看到过的人的消息」。随机日志碰出来：上一轮请求出错、没回复的，那句话留在尾巴里，N 退到上一次请求看到的以前，摘要请求就接不上上一次的前缀。改成：以前的回合里请求看到过的照常压；这一轮里认回复不认请求，这一轮还没有回复的，触发它的那一条也留着。
- **一组不拆提前到这一步**：随机日志碰出来：回合中途排着的新话，序号在回复和它的工具结果之间，N 落在中间，摘要请求里有调用没结果、压完的请求里有结果没调用。改成 N 落在回复和它的结果之间的，退到这条回复前面。
- **渲染**：排在检查点前面的 `model.called` 不算这一轮请求过。不然回合开头压完再注入的事实会排到触发的那句后面，第一次主请求的最后一块就不是触发它的那句了。
- **摘要请求的名字可能重名**：回合开头的摘要请求出错再来，N 不变；看到第 N 条的那次主请求以后排着新话的，N 就是它的名字。内核只认在路上的那一次，过时的回报对不上阶段就不理；执行器要保证叫停的请求不再送回报，6-3 查。
- 两份测试文件过了 500 行，拆出 `session/tests/listing.rs`、`session/tests/random/compacting.rs`。

这一步真执行器还不交限额，给她看的东西没变，不用真模型自测；真模型的摘要请求随 6-3 实测。
