## 施工单 1-9：有效历史（上）

状态：已完成（2026-09-26 项目主人验收通过）。

### 目的

投影要用的那一段历史能在内存里维护了：从最近一次压缩算起，去掉撤销掉的回合。账本查过的事件交给它，它只留还要发给模型的那些。压缩一次就丢掉更早的，撤销一次就丢掉撤掉的，所以占的内存随上下文窗口走，不随日志走（`07-存储.md` 第七节）。

### 图纸

- `03-事件模型.md` 第七节「有效历史」，这一步新画的：从最近一次压缩算起、检查点排最前、更早的检查点不再出现；撤销去掉哪些事件；`turn.reverted` 本身不留；内存里只留这一段。
- 撤销时，触发那一轮的消息算不算在里面，是这一步要你定的（「要拍板的」第 1 条）。图纸先照推荐写了。

### 做什么

| 文件 | 装什么 |
|---|---|
| `crates/miyu-kernel/src/history.rs` | 有效历史：最近一次的检查点，加上它之后还有效的事件，照日志的先后。追加一条事件时，压缩就换检查点、丢掉更早的；撤销就丢掉撤掉的回合 |
| `crates/miyu-kernel/src/history/tests.rs` | 没压缩过时全都在；压缩一次、再压一次；被动压缩保下来的尾巴排在检查点后面；撤销去掉那一轮连同人发的触发消息，回报触发的留着触发的那条 |
| `crates/miyu-kernel/src/lib.rs` | 登记新模块 |
| 施工图 | 1-9 那一张图纸 |

### 不做什么

- 按每次请求实际看到的范围切段、工具结果按调用顺序排、群里的闲话等到下一回合开始：1-10 有效历史（下）。
- 哪种事件渲染成什么：1-12 组装请求。有效历史只管哪些事件还算数，不管怎么渲染。
- 分叉出来的会话，投影里带上原会话的那一段：做分叉的那一步再加。
- 回合中途插进来的人的消息带不带这一轮的 `turn`：2-6 定。带的话，撤销这一轮时它也跟着撤。

### 要拍板的

1. **撤销一轮时，触发这一轮的那条消息算不算在里面？** 推荐：人发来的消息算，别处来的不算。
   - 定了：照推荐（2026-09-26 项目主人：「可以。按照你的推荐」）。「人发来的」落到图纸上是 `by` 为账号的 `message.user`：群里别人说的话、另一个会话发来的消息都算别处来的，留着。
   - 人发来的那条一起撤：撤了就跟没说过一样，模型看不到它。以后头可以把原话放回输入框，让人改了再发（Claude Code 的「回到这条消息之前」就是这样）。
   - 子代理的回报、后台命令结束这类触发不撤：它们是别处发生的事实，撤掉这一轮，事实照样在，下一轮她还看得到。
   - 另一种：只撤这一轮自己的事件，人发的那条留着。下一次请求里，她会看到一条没回答的消息，多半会重新回答一遍，效果像「重试」。

### 我定的

- **检查点单独放，排在最前**：日志里检查点这条事件排在被动压缩保下来的尾巴之后，投影里却要排在最前面（`03-事件模型.md` 第七节的图）。所以单独留着，不和别的事件混在一起。
- **只认最近一次的检查点**：新摘要是从带着旧检查点的那次投影里写出来的，旧的已经包在里面。换上新检查点时，旧的和序号在新 `upto` 之前的事件一起丢掉。
- **撤掉的直接丢**：投影从此不再要它们，界面翻历史读的是磁盘上的日志。留在内存里只会白占地方。
- **找触发消息靠 `turn.started`**：被撤回合的 `turn.started` 写着 `trigger`，照它找到那一条；它是 `by` 为账号的 `message.user`，就一起丢。
- **`turn.reverted` 用过就丢**：它不进上下文，要做的事已经做完了。
- **只收账本查过的事件**：有效历史不再重复查规矩，查规矩只在账本里（1-7）。

### 验收

1. `step/1-9-history` 分支的 CI：三台机器全绿。
2. `cargo test -p miyu-kernel history::`：压缩、再压缩、被动压缩的尾巴、撤销的几种情况都有测试。
3. 读 `03-事件模型.md` 第七节「有效历史」。

### 风险

- 撤销的规矩定了以后，头（M8）的「撤销到这里」要照它做：撤到某条人发的消息，就是撤销从它触发的那一轮起的所有回合。防：M8 画界面时照这张图纸对一遍。
- 以后加的事件种类要是也「属于某一轮」却不带 `turn`，撤销时就会漏掉。防：新种类在它的图纸里写明带不带 `turn`；账本的规矩（1-7）已经要求只在回合里发生的种类必须带。
