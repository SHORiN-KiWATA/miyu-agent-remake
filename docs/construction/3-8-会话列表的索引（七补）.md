## 施工单 3-8（七补）：会话列表的索引

状态：已完成（2026-10-01，终端界面实测转来，项目主人觉得 `/sessions` 开得慢；同日施工完，验收结果见末尾）。

### 目的

现在 `session.list` 每列一次，都把每个会话的日志整份读一遍，算标题、置顶；C-3 加的工作目录、最近一次动静也是照日志算的。她的 `sessions` 工具走的是同一个函数。项目主人的测试家目录有 234 个会话、日志共 13 MB，`session.list` 每次约 1 秒（终端界面连测三次：1.06、1.00、0.94 秒）。

存储设计早就定了怎么做：`07-存储.md` 的 S3 写着会话列表用 SQLite 做派生索引，放在账号的 `index/` 下，随时可以删掉重建；「核心启动时不载入任何会话，只读会话列表索引」。这一步把它做出来，协议形状不变，只是快。

### 蓝图改哪几节

- `store.md`（或新的一页 `store/index.md`，照最简单的放）：
  - 会话列表的索引 `home/<账号>/index/sessions.db`，SQLite，派生的。
  - 每个会话一行：编号、属主、父会话、是不是一次性的、标题、置顶、工作目录、造的时刻、最近一次动静。
  - 另记这一行照到日志的哪里（最后一段、字节数）。
- 会话写日志时，同一批事件落了盘以后顺手更新它那一行（`session/actor.md`）：
  - `session.created` 插一行；
  - 改标题、置顶的改那几格；
  - 每一批都更新最近一次动静，`turn.started` 带的 `cwd` 更新工作目录。
  - 删会话删那一行。
  - 更新失败只记一行 `WARN`，不影响会话：索引是派生的，下一条会补上。
- 列会话（`protocol.md`「`session.list`」、`cross-session.md` 第一条、`miyu-endpoint` 的 `list.rs` 的 `scan`）改成读索引。
  - 忙不忙照旧从会话表的内存里拿，不进索引。
  - 某一行照到的位置和日志现在的长度对不上的（崩在更新之前、手动动过日志），只读多出来的那一截补上。
  - 日志比记的短、段对不上的，这一个会话整份重读。
- 索引文件没有、读不了、坏了、版本不对：删掉，照日志重建，记一行 `WARN`。重建期间列会话照旧整份扫，不卡住。
- SQLite 用 `rusqlite` 的 `bundled`，自己带 SQLite 的源码编，三个平台一样。先过许可证门禁（SQLite 是公有领域），写进 `licenses.md`。分层照 `01-架构.md` 第九节，放存储那一层。
- `protocol.md`「还没有的」、`cross-session.md` 第一条第 10 款：去掉「每列一次都整份读」。

### 不做什么

- `history` 的全文索引：随记忆、知识库（`07-存储.md` 第七节）。
- 用量总表的索引：随 M8 的 8-15。
- 会话列表流 `sessions.changed`：M9。

### 验收

1. 测试（先写，退回改之前的代码要红）：
   - 造会话、说话、改标题、置顶、删会话以后，索引那一行对。
   - 列会话读索引，结果和整份扫的一字不差：同一批会话两种算法比。
   - 崩在更新之前，照日志补上；手动截短过日志的，整份重读。
   - 索引没有、坏了、版本不对，都照日志重建。
   - 更新失败不影响会话。
2. 量：造一个 250 个会话、日志共十几兆的测试家目录，比改前、改后的 `session.list` 耗时，看倍率；写进验收结果。量尺类的测试标 `#[ignore]`。
3. 手写变异 15 个左右，挑关键的，全被逮住；`CARGO_BUILD_JOBS=5 cargo xtask check` 八项全过；三台机器的 CI 和长跑全绿。
4. 给模型看的字：没有，请求形状探针零变化。
5. 合了告诉两个头：形状不变，附实测耗时。

### 风险

- 新的 C 依赖：`bundled` 在 Windows、macOS 的 CI 上要先编通。编不通照 S3 的重开条件停下来问主会话。
- 和 8-3 同时做：8-3 碰配置、端点的 `config/`、命令行，这一步碰存储、会话表、`list.rs`。冲突多半在 `protocol.md`、`Cargo.lock`，主会话合并时解。

### 验收结果（2026-10-01）

1. **测试**（先写；存储、会话、端点的是新接口，改之前编不过；`tests/index.rs` 改之前连索引的文件都没有）：整个工作区 2446 个全过。
   - `crates/miyu-store/src/index/tests.rs` 八个：新建的是空的、下次照旧、目录 0700；一批批盖上（属主、一次性、工作目录、标题、置顶、最近一次动静、照到哪，造的时刻不变；只改标题的置顶照旧，只改置顶的标题照旧）；没有这一行、照到的不是这一批之前的不动；写回只填空的、只换照到的没变过的；删行；乱写的文件、版本不对的删掉重建成空的；读不懂的一行报错、`reset` 以后是空的。
   - `crates/miyu-store/src/log/tests/marked.rs` 七个：从头读照到的就是写的一方记的；只读多出来的；接着读后面的段；载入以后照旧知道写在哪一段；末尾的半行不算、一个字节不动；比记的短了、不在一行开头、记的那一段没了交回空的；序号接不上报坏了。
   - `crates/miyu-endpoint/src/list/tests/indexed.rs` 五个：同一批各种各样的会话（没记过工作目录、改名置顶又去掉标题、两段、末尾半行、日志坏了、第一条不对、空目录、一次性的子会话），没有索引、照日志填、照索引读、再读一次，列出来一字不差，只要一次性的也一样；日志坏了的不写进索引。索引没看见的几条（半行写完、再加两条，另一个换了段）补上、写回；截短了的、换成更长一份位置落在一行中间的、记的那一段删了的整份重读、写回。没有、乱写、版本不对的起来时换成空的，照日志填好。用着用着读出坏了的，这一次照样列得对，重建好。
   - `crates/miyu-endpoint/tests/index.rs`：造会话就有那一行；说一轮、改标题置顶以后和日志对得上、照到日志的末尾；删会话删掉那一行。`tests/index_log.rs`：`INFO session index created`、`WARN session index rebuilt`、`WARN session index not read`，读出坏了的照样列得对。
   - `crates/miyu-session/tests/index_log.rs`：每落一批那一行照到日志的末尾；表没了（另开连接 `DROP TABLE`），更新失败只记一行带会话编号的 `WARN session index not updated`，会话照常说完下一轮。
   - 原来的测试都照旧过：`list/tests.rs` 照新的 `Row` 改了写法，期望没变；会话的测试场地多开一份索引，造的、载入的会话都往里写。
2. **量**（`crates/miyu-endpoint/src/list/tests/speed.rs`，标 `#[ignore]`）：250 个会话、日志共 12,956,750 字节。整份读就是改之前的读法（`scan` 不给索引，和改之前同一套：读第一条、再整份读）。

   | | release | debug |
   |---|---|---|
   | 整份读（改之前） | 53–55 毫秒 | 600–632 毫秒 |
   | 照日志填索引的那一次 | 59 毫秒 | 621 毫秒 |
   | 之后照索引读 | 0.9–1.4 毫秒 | 2.6–2.8 毫秒 |
   | 十个会话各多写了五条 | 1.2 毫秒 | 4.0 毫秒 |

   倍率约 50 倍（release）、220 倍（debug）。
3. **变异**：手写 18 个，全逮住（都是测试红）。第一轮活下来三个，补了测试再跑是红的：置顶没写的当成取消（补了只改标题、只改置顶的两批）；载入时段名记成第一段（补了载入以后的位置）；「日志比记的短」那一句检查是多余的（记的位置前面一个字节读不到，照样对不上），删掉了，换成「段对不上时接着读」。清单：盖的时候不查照到的位置、不挪照到的位置；写回时覆盖已有的行、不比字节数；版本不对当成对的；打开失败不删文件；不盖工作目录；置顶没写的当取消；不查在不在一行开头；段对不上接着读；换段时不记新段的名字；载入时段名记成第一段；列会话直接信那一行不补；补好的不写回；整份重读的不换掉旧行；读出坏了不重建；会话落盘不更新索引；删会话不删行。
4. `CARGO_BUILD_JOBS=5 cargo xtask check` 八项全过（许可证一项过了 `rusqlite` 带进来的几个包）。给模型看的字没有，请求形状探针的存档一个字节没变。

**施工中定的**（施工单没写到，按推荐定，写进了 `store/index.md`）：
- 蓝图新开一页 `store/index.md`，`store.md` 只加指向它的几处。
- 一行照到哪里记三样：段（第一条的序号）、这一段的字节数、下一条的序号；接着读时查记的位置前面一个字节是不是 `\n`、序号接不接得上。
- 会话落盘以后只盖照到的正好是这一批之前的那一行，对不上的不动，等列会话补；列会话写回也只换照到的没变过的那一行。所以不会有位置对、内容少了几条的一行。施工单写「下一条会补上」，实际是下一次列会话补上。
- 照日志重建不另起后台任务：打开时坏了的换成一份空的，列会话时没有那一行的整份读、读完写进去，重建期间就是原来的读法。
- 日志坏了的会话不写进索引：照坏的那一段以前算的结果只在这一次用，下次还整份读，和原来一字不差。
- 列会话照放会话的目录走：删会话没删掉的行不碍事，不清。
- 一个核心一个连接、一直开着；WAL 加 `synchronous = NORMAL`；打开时跑 `quick_check`；时刻存毫秒。
- 写盘的阻塞线程带上会话的 span：那边记的 `session index not updated` 有会话编号。
- `miyu-session` 的 `open.rs` 加了 `index` 一格放不下，造不成、载入不了的几种挪进 `open/error.rs`。
- 端点里两个自己造核心的单元测试（`sessions/tests.rs`、`sessions/delete/tests.rs`）末尾删临时目录改成删不掉就留着：Windows 上核心开着索引的文件，删不掉（第一次推的 CI 在 Windows 上因此红了两个）。

**和施工单对不上的**：索引文件原来没有的记 `INFO session index created`，不记 `WARN`：新装的数据根第一次起来就会这样，不是出了问题。读不了、坏了、版本不对的照施工单记 `WARN session index rebuilt`。`cross-session.md` 说慢了随索引换的那一款是第 11 款（施工单写的第 10 款）；`tools/sessions.md` 第 9 条、「还没有的」也照着改了。
