## 施工单 3-3：blob

状态：施工中。

### 目的

图片、文件、超长的工具输出、策略快照这些大内容有了落脚处：按内容哈希存成单独的文件，一个账号一份。先写临时文件、同步、再改名，磁盘上不会有写了一半的 blob；读的时候核对哈希。「先落 blob，再写引用它的事件」（`07-存储.md` 第四节）从这一步起有了真的做法。

### 图纸

- `07-存储.md` 第五节「blob」已经画了：路径、SHA-256、按账号分开不去重（S5）、策略快照也是 blob、回收的规矩。这一步补的：
  - 文件名是去掉 `sha256:` 的 64 位十六进制：Windows 的文件名里不许有冒号。
  - 写：临时文件在 `blobs/tmp/` 里；已经有了的不重写，只刷修改时间，回收的宽限期按它算。
  - 读：核对哈希，对不上报错，不自动修。
- 第四节「各平台的坑」补一条：新建文件、新建目录以后，也要同步所在的目录。
- 已经画了的：内容哈希的写法，`sha256:` 加 64 位小写十六进制（`03-事件模型.md` 第二节），内核里是 `ContentHash`。

### 做什么

| 文件 | 装什么 |
|---|---|
| `crates/miyu-store/src/blob.rs` | 一个账号的 blob：存（临时文件、同步、改名、同步目录；已经有了的刷修改时间）、取（核对哈希）、路径 |
| `crates/miyu-store/src/durable.rs` | 落盘的两件小事，从 `root.rs`、`log.rs` 挪过来合成一处：同步目录；建目录，新建的每一层都同步它的上一层 |
| `crates/miyu-store/src/root.rs` | 一个账号的 blob 目录 `home/<账号>/blobs/`；写完标记同步数据根 |
| `crates/miyu-store/src/log.rs` | 新会话的目录照 `durable.rs` 的建法建 |
| `crates/miyu-kernel/src/id.rs` | `ContentHash::hex`：去掉 `sha256:` 的那 64 位 |
| 测试 | 见「验收」第 2 条 |
| 施工图 | 3-3 那一张 |

### 不做什么

- 回收：删会话那一步再做，连同 `tmp/` 里的残留。宽限期多长到时候定。
- 边读边存的上传（头只传一个文件路径、很大的文件）：到 `blob.put` 那一步（3-8 以后）。现在只收一块已经在内存里的内容。
- 执行器接上「存 blob」：3-7 会话 actor。
- 在请求里把引用换成字节：3-4 驱动的编码。

### 我定的

- **已经有了的不重写，只把修改时间刷成现在**：内容一样，名字就一样，重写没有意义。刷修改时间是给回收用的：宽限期按修改时间算，刚又传了一遍、还没被引用的，不该被当成旧的删掉。git 存对象也是这样（freshen）。
- **临时文件放在 `blobs/tmp/`，名字是进程号加一个计数**，只许新建。撞上崩溃留下的同名文件，就换下一个名字。都放在一个目录里，回收的时候好找。
- **改名失败、可目标已经有了，算成功**：两个会话同时存同一张图，后改名的那个在 Windows 上可能失败。内容是一样的，删掉自己的临时文件就行。
- **读的时候核对哈希**：blob 也是真相，读出来不对就报错（写明是哪一个），不悄悄用，也不删。多算一遍 SHA-256，比一次网络请求快得多；实测慢了再说。
- **新建目录同步上一层，顺手补上以前漏的两处**：07 第四节以前只说了改名以后同步目录，新建的目录、新建的文件也一样，上一层不同步，断电以后这一项可能没了。
  - 3-1 写完标记没同步数据根：断电以后可能标记没了、骨架还在，下次就认不出自己的数据根。
  - 3-2 新建的会话目录没同步 `sessions/`。
  - 这一步把「同步目录」「建目录」挪进 `durable.rs` 一处，三处都用它。
- **同步文件用 `sync_data`**：和会话日志一样，数据和读得出数据要的文件长度。
- **`ContentHash::hex` 放在内核里**：`sha256:` 这个写法只有 `id.rs` 知道。

### 验收

1. `step/3-3-blob` 分支的 CI：三台机器全绿，长跑也绿。
2. `cargo test`：
   - 存了再取，一字不差，带 `\0`、`\r\n` 的二进制也一样；名字是内容的 SHA-256；路径是 `home/<账号>/blobs/<前两位>/<64 位>`，没有冒号。
   - 同一份内容存两遍：只有一个文件；第二遍把修改时间刷成了现在。
   - 存完，`tmp/` 是空的。
   - 崩溃留下的：`tmp/` 里有一个写了一半的临时文件，取这份内容的哈希报「没有」；再存一遍，取得到完整的。撞名的临时文件跳过去。
   - 改名时目标已经有了：算成功，临时文件删掉。
   - 读出来和名字对不上：报错，写明是哪一个，文件不动。没有这个 blob：报「没有」。
   - 两个账号存同一份内容：各存一份。
   - 建目录：一层一层建出来，Unix 上权限 0700；该是目录的地方是个文件，报错。
3. 故意改坏几处，测试变红：文件名留着 `sha256:`、前两位取错、不分前两位的目录、读的时候不核对、已经有了的不刷修改时间、改名写成拷贝、撞名不换名字、改名失败不看目标、两个账号共用一个目录、没有的报成读写出错、建目录不建中间的层。一共 11 处。
   - 不同步（去掉 `sync_data`、去掉同步目录）、不经临时文件直接写到最终的名字：测试里没法断电，测不出来。靠第四节写明的做法，和代码读一遍。
4. `cargo xtask check` 七项全过。

### 风险

- **Windows 上文件开着不能改名、不能删**：临时文件写完先关上，再改名；测试里开着的句柄用完就关。
- **修改时间的精度三个平台不一样**：测试先把修改时间设到很久以前，存第二遍以后看它是不是回到了现在附近，不比精确的值。
- **Windows 上改名的目标已经有了**：标准库的 `rename` 会替换它；万一失败，照上面「算成功」处理。
