## 施工单 3-4：OpenAI 兼容接口的编码（上）

状态：施工中。

### 目的

统一的请求（`08-上下文投影.md` 第二节）编码成 OpenAI 兼容对话接口的请求字节：纯函数，同样的输入字节一定一样，每一种写法都有固定的样本。探针的每一次请求另存一份编码以后的字节；随机日志在线上这一层也查前缀延伸：缓存命中看的是真发出去的字节。解码、出错分类和驱动的接口是下一半。

### 图纸

- `05-内核接口.md` 第七节「驱动的规格」：驱动是纯粹的翻译器，每家的请求字节用固定样本检查。这一步补了「OpenAI 兼容的对话接口怎么编码」那张表：顶层字段和先后、各种消息怎么写、工具面、图片和文件、不用缓存标记；供应商之间不一样的三个开关。
- `26-提示词.md` 第八节：驱动的几句占位随核心附带，放在 `resources/core/drivers/`。
- 已经画了的：统一的请求（`08-上下文投影.md` 第二节，内核的 `Request`）；思考块连同私有数据原样带着，发哪些由驱动定（08 第四节）；图片和文件是 blob 的引用，到编码时才换成字节（08 第二节）；模型能收哪些输入是模型资料（`15-模型与供应商.md` 第三节），查不到时驱动按保守的默认：当作不能看图。
- 调研：opencode v2（`packages/ai/src/protocols/openai-chat.ts`）、pi-mono（`packages/ai/src/api/openai-completions.ts`），旧版只当旁证。codex 已经删掉了这类接口，只剩 Responses。

### 不做什么

- 解码、出错分类、驱动的接口（trait）：3-4（下）。
- 哪个供应商用哪一套开关、模型资料从哪来：配置和模型资料的那几步。这一步只有开关本身和默认值。
- 思考强度的参数：各家写法不一样（pi 收了 11 种），做思考强度时再加。
- 到了步数上限只设 `tool_choice: "none"`：做步数上限的那一步。
- OpenRouter 的 `reasoning_details`、Gemini 的思考签名、Mistral 只收 9 位的调用编号、工具结果后面要先跟一条 assistant 的供应商：接到它们的时候再做。
- 供应商专门的请求头（会话亲和、opencode Zen 的会话头）：3-5 执行器。
- 支持 `cache_control` 的网关用上缓存标记：以后。

### 我定的

- **新 crate `miyu-drivers`**：驱动的编码解码在第 2 层（01 第九节的表早就写了），一个 crate 装各家驱动，一家一个模块。
- **base64 自己写，不加白名单**：只要编码这一半，照 RFC 4648，用它第十节的七个测试值查。
- **图片、文件的字节由执行器先取出来交进来**：驱动收一个只读的端口，不碰文件。驱动另给一个函数，列出这份请求要用哪些 blob，执行器照着取。少了一个，编码报错，写明是哪一个。
- **编码交回请求字节，外加每条消息在字节里的位置**：随机日志拿它查线上的前缀延伸，以后按段记哈希也用得上（08 第七节）。
- **user 消息的拼法**：全是文字的拼成一个字符串，相邻两块之间补一个换行，前一块已经以换行结尾的不补。事实块本来就以换行结尾，照原样接上；两句话合进一条消息时（上一次请求没等到回复），中间有换行，不粘在一起。只接不改，前缀照样延伸。
- **assistant 的正文直接接上**：这类接口的 `content` 本来就是一整段，解码时才按先后切成块，照原样拼回去就是模型当时说的。没有正文、只有工具调用的写 `null`，都没有的写空串（opencode 的做法）。
- **工具调用的编号**：用供应商自己的，在私有数据 `{"id":"…"}` 里（3-4 下解码时照这个写）；没有，或者是别家驱动的，用内核分的 `call_<序号>_<第几个>`。tool 消息的 `tool_call_id` 照同一次调用写的来。
- **参数原文照抄，不是合法 JSON 的写成 `{}`**：原文照抄，模型说过的字一个不改；空的、坏的（被截断的）写成 `{}`，vLLM、Ollama 这类本机服务渲染历史时要把参数解析出来，坏的会让整个请求失败。两家参考都这样兜底，但它们连合法的也重新序列化，我们不。
- **工具结果里的图挪到后面**：这类接口的 tool 消息只收文字（两家参考都这样挪）。一串 tool 消息之后插一条 user 消息：先一句说明，再按先后放图。只有图、没有字的那条 tool 消息，写一句「图在下面」。模型不能看图的，不挪，就地换成占位。
- **三个开关，跟着供应商定、会话里不变**：
  - 输出上限写 `max_tokens` 还是 `max_completion_tokens`，默认 `max_tokens`：OpenAI 官方走 Responses 驱动，这类接口的供应商多数只认它。
  - 思考回不回传、写进哪个字段、没有思考时要不要发空串，默认不回传。DeepSeek 要每条 assistant 都带 `reasoning_content`（opencode 的注释），它那一套是「写进 `reasoning_content`，没有就发空串」。
  - 要不要在流里报用量（`stream_options.include_usage`），默认报：两家参考都发。
- **模型能收哪些输入不是开关，是模型资料**：图片、PDF 能不能收，跟着一次调用传进来，默认都不收（15 第三节，驱动的保守默认）。
- **占位的几句是资源，英文**：放在 `resources/core/drivers/`，驱动收一份读好的，检查里面的占位符（和 `ToolTexts` 一样）。
- **探针的线上存档用 DeepSeek 那一套**：模型名 `deepseek-v4`，输出上限 8192，每条 assistant 都带 `reasoning_content`。第一次真对话最可能接的就是它。

### 验收

1. `step/3-4a-encode` 分支的 CI：三台机器全绿，长跑也绿。
2. `cargo test`：

### 风险

- **有的供应商只收字符串的 `content`**：全是文字的消息一律发字符串，这是最常见的写法；只有带图、带文件时才分段。
- **有的供应商遇到不认识的字段就拒收**：只发最少的几个字段。
- **DeepSeek 的开关没配对会被拒**：默认不回传思考；DeepSeek 的思考加工具调用，要每条 assistant 都带 `reasoning_content`。哪个供应商用哪一套到配置那一步定，3-9 真对话时实测。
- **键的顺序**：线上的格式全用结构体，字段照声明的先后；不经过 `serde_json::Value` 的映射；参数格式、私有数据原样照抄。依赖里哪个 crate 打开了 serde_json 的 `preserve_order`，也影响不到我们。
