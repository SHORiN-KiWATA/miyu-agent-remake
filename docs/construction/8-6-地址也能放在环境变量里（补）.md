## 施工单 8-6（补）：地址也能放在环境变量里

状态：已完成（2026-10-01，图纸 `docs/blueprint/config.md`、`models.md` 已改；验收结果见最后一节）。

### 目的

8-6 以后，`providers.<id>.base_url` 只收地址本身，只有密钥类型的项认 `{ env = … }`。所以端点地址一定会写进数据根的 `system/config.toml`：`cargo xtask dev-home` 就是这么写的，`config.get` 会回它，设置页的「模型」页、`model.list` 也会明文显示。项目主人的规矩：本机端点地址和 key 一样，只放在拉起核心的命令的环境变量里，不进任何文件（「Claude Code 都可以设置」）。

改成：
- `base_url` 也认 `{ env = "变量名" }`，和 key 同一种写法、同一个取法：照核心起来时的环境取，没设、设成空的报 `env_not_set` 警告。
- `config.get`、设置页、`model.list` 显示引用（`{ env = "…" }`），不显示地址。
- `cargo xtask dev-home` 写 `base_url = { env = "MIYU_DEV_BASE_URL" }`，不写地址本身。开发自测回到「地址和 key 只在命令里」：`MIYU_DEV_BASE_URL=… DEEPSEEK_API_KEY=… MIYU_HOME=… miyu …`。

### 蓝图改哪几节

- `config.md`：
  - 类型表「网址」那一行：多认 `{ env = … }`，照「密钥」那一行的读法和查法（TOML、JSON、人敲的三种），引用取不到的照第九条报 `env_not_set`。
  - 「施工时定的」记一条：哪几种类型能写环境变量引用。这一步只给网址，别的类型要用时再加，不为以后写代码。
  - 第九条第 719、720 行一带：环境变量的引用不只密钥用。
- `models.md`：`[providers.<编号>]` 那张表 `base_url` 一行写上能写引用；`model.list` 的 `providers` 里 `base_url` 照配置写的样子交（引用就交引用）；第十条「开发怎么测」第 2 条照新的写法改。
- `config.md`、`models.md` 的「样子」里 dev-home 写出来的那份配置跟着改。

### 不做什么

- 别的类型认环境变量引用：用到再加。
- 「带 env 的项」那种整项被环境变量压过（`log.level` 的 `MIYU_LOG`、8-7 的 `MIYU_CATALOG_UPDATE`）：不用这种，地址是每家供应商一个，压过的写法认不出是哪一家。

### 验收

1. 测试（先写，退回改之前的代码要红）：
   - `base_url = { env = "X" }`：设了照它连（假服务器）；没设、设成空的报 `env_not_set`，这一家没有地址，当场报 `no_model`。
   - `config.get`、`model.list` 回引用，不回地址：整份回应里搜不到地址。
   - `config.set` 能写进引用；人敲的 `{ env = "X" }` 认得出。
   - `xtask dev-home` 写出来的配置里没有地址，只有引用；照它起来的核心连得上假服务器。
2. 真模型（主会话合并前做）：照新的 dev-home 造数据根，数据根里搜不到地址和 key，`miyu ask` 说一句、调一次工具。
3. 手写变异 15 个左右，挑关键的（回应里漏出地址的那种一定要有），全被逮住；`CARGO_BUILD_JOBS=5 cargo xtask check` 八项全过；三台机器的 CI 和长跑全绿。
4. 给模型看的字：没有，请求形状探针零变化。
5. 合了告诉两个头：`base_url` 可能是引用，设置页照引用显示；dev-home 的配置里不再有地址。网页那边等这一步合进来再升级项目主人的演示核心。

### 风险

- 碰 `miyu-config` 的类型、`miyu-models` 的解析、`model.list`：排在 8-7 后面，免得和它撞。

- 施工时定的（要点，细节写进了 `config.md`、`models.md` 的「施工时定的」8-6b 那张表）：
  - 网址认引用照 `Kind` 整体认（和「密钥」类型一样不按字段开关），不是只给 `base_url` 单开一种类型：清单里凡是 `kind: url` 的字段都能写 `{ env = … }`，用不上引用能力的字段（`models.catalog.url`，公开资源地址）读进 `String`/`Option<String>` 时把 `Value::Secret` 当空字处理，不读成乱码的 TOML 字节。

  - **测试逮住的真 bug（不在施工单预期内）**：`crates/miyu-endpoint/src/models.rs` 的 `snapshot()` 只收集每家供应商 `keys` 列表里的引用，不收 `base_url`。按原样实现时，`model.list` 带 `refresh: true`（或后台重拉）要连一个地址是 `{ env = … }` 的供应商，会因为取不到密钥而报错，等于这条路从一开始就是坏的。写 `fetching_the_provider_list_resolves_an_env_based_address` 测试时当场撞见（先红后修），补上 `base_url` 是 `Address::Env` 时也进 `snapshot.secrets`。施工单第二条验收标准「设了照它连」原本只想着 `route.rs` 发请求这一条路，`route/lists.rs` 拉列表是另一条独立的路，两条都要经 `resolve_base_url`、两条都要有能拿到值的 `secret` 闭包。
  - `Kind::Url` 的 Schema、参考文件改动波及了 `models.catalog.url`（也是 `kind: url`，但不需要引用能力）：它的 Schema 也多了 `oneOf`、说明文字也多了「或 `{ env = … }`」一句。技术上它确实能写 `{ env = … }`（`Kind::check` 不挡），但 `CatalogSettings::url` 是 `String` 不是 `Address`，写了引用会被 `String` 的 `Setting` 读成空字（不是解出来的地址），不会连错地方、也不会泄漏什么，只是这一项目前用不上这条路。施工单没预料到这一层联动，施工员判断：按 Kind 整体认（照「密钥」的先例）比只给 `base_url` 单开一种类型更省代码、更一致，代价是这一处文案多说了一句暂时用不上的话，记在这里留痕。
  - 施工单没明确「{ env = … } 的 wrong_type 报错要不要提一句能写 { env = … }」：施工员定的是不改，`config/expected/url` 的报错原样复用（照密钥的样子，用 `one_of` 接「网址的写法」和「{ env = "…" }」两句），wrong_type、bad_format 都共用这一句「期望」，和密钥类型的先例一致。
  - 施工单没有的新测试文件：`crates/miyu-config/src/named_kinds_tests.rs`（门禁的「行数」要求所致，见上）。
- 协议形状（合了告诉两个头）：没有新方法、新推送。`config.get`、`model.list` 里 `providers.<id>.base_url`（及 `config.get` 的 `providers.<id>.base_url` 键）的值形状多了一种可能：原来恒是字符串（地址本身），现在可能是 `{"env": "<变量名>"}`（配置里写了 `{ env = … }` 的那一家）。`model.list` 的 `base_url` 字段同理。两个头如果直接把 `base_url` 当字符串显示，遇到引用形状要能认出 `{"env": …}` 这种对象、照「来自环境变量 <名字>」这样的话显示，不能假设它永远是字符串。
