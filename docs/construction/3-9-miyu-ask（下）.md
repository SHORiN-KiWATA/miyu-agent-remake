`miyu ask "…"` 的先后：

1. 找数据根，建骨架。核心没在跑、自己也没设 `DEEPSEEK_API_KEY` 的，说「没有可用的模型」，退出码 5，不拉起。
2. 连上核心（没在跑就拉起，施工 3-9 上），握手。
3. 会话：`--session` 的用它；`--continue` 的问核心上一次 `miyu ask` 开的是哪个；都没写的，造一个一次性的新会话。
4. 订阅这个会话，发这一句。
5. 认出这一句开的那一轮，边收边打：思考灰色印在标准错误上，回答印在标准输出上。
6. 这一轮结束：标准错误上印一行用量；照结束的原因给退出码。

### 我定的

- **新 crate `miyu-cli`**：第 5 层（头），装命令行的头；主程序只把 `miyu ask` 交给它。给人看的话也挪过来，主程序和它共用一份。
- **一次性标记记在 `session.created` 里**：`"oneshot": true`，不是一次性的不写，旧的日志、样本不用改。
- **`session.list`**：参数 `oneshot`（只要一次性的）、`limit`（最多几个），交回 `sessions: [{session, oneshot}]`，从新到旧。会话编号是 UUIDv7，照编号排就是照造的先后。读每个会话日志的第一条，只读不写，不碰正在写的最后一段。以后有了会话列表流、索引再换。
- **`--continue` 接的是最新的那个一次性会话**：`miyu ask` 开的会话都是一次性的；用 `--session` 接着说的不改变「最新」。一个都没有的，说「还没有 miyu ask 开过的会话」，退出码 1。
- **认出自己那一轮**：`turn.started` 的 `cause` 是自己发的那条命令；之后照回合编号收。
- **回答、思考**：`model.delta` 里 `start` 是 `reasoning` 的那一块是思考，`text` 的是回答；工具调用这一步不打。回答说完补一个换行。思考和回答之间空一行。终端里（标准错误是终端、没设 `NO_COLOR`）思考是灰色；不是终端的照样印，不上色。
- **用量那一行**：这一轮每次请求的用量加起来：输入 = 没命中 + 命中 + 写进缓存，命中率 = 命中 ÷ 输入。例如 `· 输入 1,830 · 命中缓存 1,792（98%）· 输出 12`；英文 `· input 1,830 · cache hit 1,792 (98%) · output 12`。供应商没报用量的，这一行不印。
- **退出码**：走完了 0；被打断 3；出错 1；出错是「没有可用的模型」（没发出去、认证失败）的 5。出错时标准错误上说清是哪一类、原话。
- **Ctrl+C**：第一次打断这一轮（排着的退回），等它收尾，退出码 3；第二次不等，直接退出，退出码 3。
- **`--format json`**：标准输出最后印一行 `{"session":…,"turns":[{"text":…,"usage":{"input":…,"cache_read":…,"cache_write":…,"output":…}}]}`，出错的再带 `"error":{"class":…,"message":…}`；标准错误上不印思考、不印用量，只印出错。
- **测试**：`miyu-cli` 的对话部分交进来连接和两个写的地方，测试在进程里起核心（剧本模型），照样走一遍，看写出来的字和退出码；主程序的测试跑真的进程，测不用拉起核心就能判的几样（没有 key、参数不对）。
- **命令编号带随机前缀**（施工中查出的 bug）：请求的编号就是命令的编号，同一个编号只生效一次（给断线重发的）。原先每条连接都从 `ask-1` 数起，第二次 `miyu ask --continue` 说的那一句和第一次那句同号，被内核当成了重发，什么都没发生，头一直等。现在每条连接取 8 个随机字节当前缀：`ask-<16 位十六进制>-<序号>`。
- **剧本模型会先想再答**（`Play::Thinks`）：测思考、回答分两条通道要它。
- **读会话日志的第一条不能用 `SessionLog::open`**：它会截掉最后一段末尾的半行，会话正在写的那一行就没了。另写一个只读的，只读第一段开头那一行。
- **说明跟着界面语言**：`clap` 的说明写死在代码里，运行时照界面语言换掉 `miyu ask` 的那几句。
- **核心那一层的报错还是中文**：连不上、拉不起核心这些原因是下层 crate 写的，界面语言那一步一起挪。
- **运行日志的 `request` 那一行带上「前缀变在哪」**（2026-09-27 项目主人定，真机验收时加的）：项目主人问「不是应该有内核日志吗？你怎么从内核日志查查原因」。运行日志在 `INFO` 就记了每次请求的输入、命中、输出，却答不了「命中 0 是不是我们的前缀变了」，那一格只在会话的事件日志里。现在内核把第一处不同也交给执行器（`CallModel` 带着 `changed`，和记进 `model.called` 的是同一份），前缀变了的那一次请求多写一个 `changed=`（`tools`、`system`、`message:<第几条>:<角色>`），只是接着加的不写（`28-运行日志.md` 第二节）。
