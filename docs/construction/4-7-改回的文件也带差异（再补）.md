## 施工单 4-7（再补）：改回的文件也带差异

状态：已完成（2026-10-02，项目主人要的，终端界面的会话转来；技术细节主会话定）。

### 目的

撤销、重做把文件改回去时，头要列出每个文件，每个文件的差异能点开看。现在 `session.revert`、`session.unrevert` 回应里的 `files` 只有没动的（`changed`：之后又被改过）才带 `diff`。项目主人 2026-10-02 要：改回了的也带，看得到这次撤销把这个文件改成了什么样。

要做的（技术细节主会话定）：
- `outcome` 是 `restored`、`action` 是 `write` 的那一项也带 `diff`：改回以前磁盘上的内容，对改回以后的内容。规矩和现在一样：上下各 3 行，最多 20 行，多的记进 `more`；太大的、不是文字的不带。`write` 写回之前文件不存在（撤销删掉了新建的文件）的，照「原来是空的」算；改回以后不存在的同理。
- `trash`、`untrash` 两种只是挪位置，内容没变：不带 `diff`。`restored` 里「现在已经是要改成的样子」（本来就一样，没写）的也不带。
- 每个带 `diff` 的项（`restored`、`changed` 都算）多两格：`added`、`removed`，加了几行、删了几行，照整份差异数，不照截断以后的 20 行。
- `session.unrevert`（重做）照同样的规矩：带的是重做又改回去的那一份差异。

### 蓝图改哪几节

- `docs/blueprint/protocol/undo.md`：`files` 那张表（`diff` 的说明、多 `added`、`removed`）、例子。
- `kernel/history.md`、`fs.md` 里讲撤销怎么核对、怎么改回、怎么出差异的那几段（`grep -n 'diff\|差异' <页>` 定位），跟着改。
- 先例：现在给 `changed` 出差异的代码（`grep -rn 'more' crates/miyu-session/src/undo* crates/miyu-endpoint/src/undo*`）和它的测试；命令行 `miyu undo` 印差异的那一处（`crates/miyu-cli/src/undo/print.rs`，看要不要跟着印改回了的差异：照现在的样子印，施工时定、写明）。

### 不做什么

- 改两个演示：合了主会话通知它们的会话。终端界面已经在照现有的格做文件列表，等这一步合了再接差异。
- 撤销、重做的别的行为：不动。

**施工时定的**（技术细节照推荐定）：

- `restored`、`action` 是 `write` 的差异两边都从账号的 blob 取，不读磁盘——这时磁盘上已经是改回以后的样子了，读磁盘反而多一次 IO、还可能因为撤销之后又被人碰过而读到第三种内容，和「改回以前对改回以后」这句话的意思不符。`changed` 的差异仍旧一边是 blob、一边是磁盘（没变，因为 `changed` 本来就是「磁盘上现在的内容和该有的不一样」）。
- 「现在已经是要改成的样子，没写」不靠额外的标记去认：撤销、恢复要改回的两边内容（`changed.before`、`changed.after`）在日志里已经写死了，不管这一次是真的写了还是发现已经一样所以没写，两边拿来做差异的输入都是同一对值；真的没变时，统一格式的差异天然是空字符串，`diff()` 返回 `None`，`File.diff` 也就是 `None`，不用额外去问执行器「到底写了没有」。
- 命令行 `miyu undo`/`miyu restore` 不用改代码：`crates/miyu-cli/src/undo/print.rs` 的 `file_lines()` 本来就是看 `file["diff"]` 空不空来决定印不印差异块，不看 `outcome` 是 `changed` 还是 `restored`，新加的 `restored` 差异自动被印出来，`diff_then`/`diff_now` 两行字（「她改完的」/「撤销以后的」、「现在」）的意思对 `restored` 的两边内容同样说得通。只在 `print.rs` 顶部补了一句说明，没动逻辑。
- `File` 结构改成 `diff: Option<Diff>` 加 `#[serde(flatten)]`，而不是继续在 `File` 里平铺 `diff`/`more`/`added`/`removed` 四个各自 `skip_serializing_if` 的字段：这样「有没有差异」只有一处判断（`Diff` 整个是不是 `None`），`added`/`removed` 不用再单独操心「没有 `diff` 时要不要写」，`more` 保留自己的 `is_zero` 单独判断（施工单明确要「是 0 的不写」，`added`/`removed` 没有这条，所以哪怕是 0 也照常写出来）。

**和施工单对不上的**：

- 施工单「蓝图改哪几节」提到 `kernel/history.md`、`fs.md` 要跟着改：`grep -n 'diff\|差异' docs/blueprint/kernel/history.md docs/blueprint/fs.md` 两份都没有命中，这两页没有讲撤销怎么出差异的内容，没有改动。
- 施工单「先例」提到命令行印差异那一处「看要不要跟着印改回了的差异」要「施工时定、写明」：定了「不用跟着改，照旧打印逻辑自动覆盖新情况」，写进了上面「施工时定的」第三条，以及 `crates/miyu-cli/src/undo/print.rs` 顶部新加的一句注释；没有改动 `docs/blueprint/cli/undo.md`、`cli/redo.md`（施工单「蓝图改哪几节」没有列这两页，这两页目前只提「之后又被改过的」会印差异，没写 `restored` 也会印，留给以后真的要改这两页时一起处理，不在这一步范围内）。
- 施工单没有预料到 `crates/miyu-cli/tests/undo.rs` 这个真实核心、真实套接字的端到端测试会被这一步波及：它原来断言撤销、恢复各只印一行（`· 改回 a.txt\n`），施工后这两处都真的改了内容，自然带着差异块，第一次整套 `cargo xtask check` 的「测试」门就是在这里报红的，照实际新输出改了期望字符串（已记在上面「测试」第一条）。
