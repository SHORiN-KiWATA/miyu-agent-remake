## 施工单 4-2：执行工具的端口

状态：施工中。

### 目的

会话真的去执行工具了。内核说「执行工具」，会话照工具名在工具目录里找到那一件，在这一轮的工作目录里跑；执行中的输出一段段推给头，跑完的结果交回内核落盘；内核说「停下工具」，在跑的当场停掉。几件只读的调用一起跑，互不等待。快照里有、这个核心的目录里却没有的工具（核心升级拿掉了），报「现在用不了」；工具自己出了 bug 崩了，报「出了内部错误，可能做了一部分」，会话照常往下走。

这一步还没有真的工具（第一批在 4-4），测试用几件假工具走完整轮。执行前的链先一律放行，权限策略是下一步（4-3）。

### 做什么

| 文件 | 装什么 |
|---|---|
| `crates/miyu-tool/` | `Tool` 多一样执行：交进参数和工作目录、一个推执行中输出的口子，交回结局（内容块、出没出错） |
| `crates/miyu-session/src/tools.rs`（新） | 执行工具的端口：照名字在目录里找，一件一个任务地跑，量用时；叫停就掐掉那个任务；目录里没有的、崩了的，照资源里的那两句交回出错的结果 |
| `crates/miyu-session/` | actor 把「执行工具」「停下工具」交给端口，回报变成内核的输入；「过执行前的链」先一律放行；载入时也交进工具目录；测试剧本能让她调工具 |
| `crates/miyu-policy/` | 快照里随核心附带的字多两句：现在用不了、崩了 |
| `crates/miyu-store/` | 资源目录读这两份 |
| `resources/core/tool-results/unavailable.txt`、`crashed.txt`（新） | 那两句 |
| `crates/miyu-endpoint/` | 载入会话时交进核心的工具目录 |
| `docs/designs/05、26、28` | 见上 |

### 不做什么

- 权限策略：执行前的链先一律放行，4-3 接上。
- 提问（工具执行中问人，「把回答交给工具」）：4-9。
- 真的工具：4-4 起。
- 默认超时：见 4-1「不做什么」。
- 会话、身份、沙盒范围交给工具：用到它们的那一步再加（路径边界在 4-3）。

### 我定的

- **交给工具的先只有两样**：修正过的参数（一个 JSON 对象的原文）和这一轮的工作目录。05 第六节列的另几样（调用编号、会话、身份、沙盒范围、截止时间）这一步的工具用不上，用到时再加。
- **工具交回的**：给模型看的内容块，和出没出错。用时由端口量：从开始跑到跑完。
- **叫停就是不要了**：端口掐掉跑这件工具的任务，工具的 future 被丢掉，它手里的东西随之收拾（例如 4-8 的命令，整组杀掉）。不另给工具一个取消信号：Rust 的异步本来就是丢掉即取消，少一样要工具自觉照办的约定。掐掉以后什么都不再报，内核本来也不理了。
- **一件一个任务**：内核一起派的只读调用各跑各的，不排队。
- **目录里没有的**：快照是造会话时冻结的，核心升级拿掉了一件工具，老会话里的模型照样会调它。这时不派，当场交回一条出错的结果：`The tool "{name}" is not available right now.`，运行日志记一条 `WARN`。这是 05 第九节「暂时不可用」在第一版里唯一的来由。
- **工具崩了**（panic）：是工具的 bug。交回一条出错的结果：`The tool "{name}" stopped because of an internal error. It may have been partly done.`，运行日志记一条 `ERROR`；会话照常往下走，不跟着停。这句要说「可能做了一部分」：崩在半路的工具可能已经改了东西。
- **这两句放在快照里**：跟内核替工具写的那几句放在一处（`resources/core/tool-results/`），造会话时进快照，会话 actor 从快照里拿，和驱动的占位一样。快照里没有这两句的（施工 4-2 以前造的会话），读成空的：那时的会话没有工具，用不到它们。
- **执行前的链先一律放行**：内核每个调用都先问链，链不回话调用就一直等着。4-3 把权限策略接进来之前，端口当场回放行。
- **执行中的输出**：一段段推给头（瞬时的 `tool.progress`），不落盘。
- **运行日志**（28）：开始跑记 `running call=<调用编号> tool=<名字>`，跑完记 `ran call=<调用编号> took_ms=<毫秒>`，出错的多写 `error=true`；叫停了记 `stopped call=<调用编号> took_ms=<毫秒>`。参数一个字都不记：参数是对话内容（28 第四节）。
- **actor.rs 快满 500 行了**：记运行日志的几个小函数挪进 `lines.rs`，执行工具的事都在 `tools.rs`。
- **测试剧本能让她调工具**：一次回复里调几件，每件写名字和参数原文，照驱动真实的先后出增量。

### 验收

1. `step/4-2-run-tools` 分支的 CI：三台机器全绿，长跑也绿。
2. `cargo test`（用假工具）：
   - 调一件工具：在这一轮的工作目录里跑，结果落盘成 `tool.result`（成功、带用时），下一次请求里有它，她接着说完；工具出错的，结果是出错。
   - 执行中的输出：头先看到一段段 `tool.progress`，再看到结果；日志里没有它们。
   - 两件只读的一起跑：两件互相等着对方开始才往下走，一起派的才走得完。
   - 打断：在跑的那件被掐掉（它的 future 被丢掉了），结果是内核补的「跑到一半被打断」；之后不再有它的输出和结果。
   - 目录里没有：造会话时有这件、载入时的目录里没有，调它得到「现在用不了」，运行日志有一条 `WARN`；目录里换了说明的，载入的老会话照样发当时的工具面。
   - 工具崩了：结果是「出了内部错误」，运行日志有一条 `ERROR`，会话照常请求下一次。
   - 运行日志：`running`、`ran`、`stopped` 几行照上面的写法，参数的字一个都不出现。
3. 故意改坏一些地方，全部有测试变红。清单施工时列，照实记。
4. `cargo xtask check` 七项全过；推之前本机用交叉 clippy 查 Windows、macOS。

### 风险

- **掐掉任务以后还有回报**：工具在被掐掉之前推的输出还在路上。内核本来就不理过时的，端口也只认还在跑的调用。
- **崩了的工具连带会话**：工具在自己的任务里跑，panic 只让那个任务结束，端口从任务的结局认出来，会话不受牵连。
