## 施工单 6-6（中）：截短重试

状态：已完成（2026-09-29：摘要请求超长截掉最老的几组再发，最多 3 次，截过的写明摘要没看到哪一段；变异全逮住；CI 全绿）。

### 目的

摘要请求自己超长（供应商报 `context_too_long`）时，不再当场算一次压缩失败：截掉检查点后面最老的几组，最多截着再试 3 次；截过的，检查点里写明摘要没看到哪一段、怎么取回。

### 蓝图改哪几节

- `compaction.md` 第三条第 10 条写实（原来写的「一整轮一整轮去掉」改成一组一组，理由见下）：
  1. 驱动从报错原话里解析超了多少 token（`excess`）：「maximum context length is N … resulted in / requested M」「prompt is too long: M tokens > N」这几家常见的说法，M 减 N；解析不出来的没有。它随「说完了」交给内核（`Input::ModelEnded` 多一格），和 `wait_ms` 一样不进日志。
  2. 截掉哪些：有效历史到第 N 条的投影里，检查点后面的一组一组（和留尾巴同一种组：一条人这边的消息，或者一条助手消息连同它的工具调用和结果），从最老的起去掉，只切在切得开的地方。有 `excess` 的，去掉的估算加起来刚好盖过它；没有的，去掉 20% 的组，向上取整、至少一组。至少留一组，留不下的这次压缩失败。
  3. 截过的摘要请求：检查点、留下的几组、摘要指令；留下的第一条是助手的，前面补一条 user：`truncated.txt`。组装器的 `summarize` 多一个参数：截到第几条（没有是不截）。
  4. 截着最多再试 3 次，第 3 次还超长，这次压缩失败（第十条）。每一次都记 `model.called`（`compaction: auto`，出错 `context_too_long`）。截到哪记在回合上，落了盘照常走发请求那一步再发；重读（6-5）照常再做一次；进度照常每次从 0 推。
  5. 截过的，写压缩时 `notes` 最后多一段 `notes-uncovered.txt`：第几到第几条摘要没看到，用 `history` 取回。
  6. 截过以后前缀变了，这一次不再命中缓存，照常发。
- 为什么按组不按轮：一轮任务里可以有几十组工具调用，摘要请求超长多半是一轮里读了很大的东西；按轮截，一轮的会话一组都截不掉。Claude Code 截的也是一组一组（API 一来一回）。
- `kernel/session.md`：`ModelEnded` 多 `excess`；收回复第 7 条：摘要请求 `context_too_long` 先截着再试。`kernel/request.md`（组装）、`drivers/` 讲出错分类的那一页、`session/actor.md`（回报多一格）。
- 「样子」「给人看的字」：`truncated.txt`、`notes-uncovered.txt` 量 token、进 `26-提示词.md` 第十节登记簿和 `prompts.md`。

### 不做什么

- 摘要请求调了工具改走隔离式、`summarize-system.txt`：6-6（下）。
- 主请求报超长先压再重发（被动压缩）：6-7。
- 真模型上撑爆窗口：开发端点的真窗口是一百万 token，撑爆一次太贵；驱动的解析照几家报错的原话样本测，重试的路在执行器替身和随机测试里测。

### 验收

1. 测试：驱动照几家原话解析出 `excess`、解析不出来的没有；截多少（盖过 `excess`、20% 向上取整、至少一组、至少留一组、只切在切得开的地方）；截过的请求照检查点、留下的几组、指令拼，第一条是助手的补 `truncated.txt`；再试 3 次还超长算一次失败、连着 3 次失败照样暂停；截过的写 `notes-uncovered.txt`；重读不重做；随机测试里摘要请求超长和别的交错。每一条退回改之前的代码会报红。
2. 请求形状探针、组装样本：没截过的字节不变。
3. 登记簿对得上；手写的变异全被逮住；`cargo xtask check` 全过；三台机器的 CI 全绿。

### 风险

- 超长的多半是最新的那一组（一次读进一个很大的文件），截老的截不到它：三次都超长，照失败算，连着失败照样暂停，暂停时告诉人哪一条太大。和 Claude Code 一样。
- 各家原话五花八门，解析不出来的走 20%：多截几次，不会少截到不够。

### 验收结果（2026-09-29）

1. **测试**：
   - 驱动：OpenAI、DeepSeek、Anthropic 三种原话解析出超了多少（DeepSeek 的 requested 算上了输出、Anthropic 的带千分位），没超的、说不出数的、别的写法没有；分类的测试里超长的带着、413 没有原话的没有、限速的原话里有两个数也不解析。
   - 内核场景（`session/tests/scenario/shorten.rs`，7 条）：不说超多少的去掉 20%（四组去一组，六组的 1.2 向上取整去两组）；说了的去到刚好盖住（多一个去两组、正好盖住去一组、盖不住去到只剩一组）；截三次还超长这一轮出错结束（五组，还剩两组也不再截）；只剩一组截不动照失败；快照里没有截短的数的当场失败；截过的压缩最后写摘要没看到的那一段，有上一个检查点的从它后面第一条算起。
   - 组装：截过的只要截到的以后的；留下的第一条是回复的前面补一条 user，是人那句的不补，有检查点的检查点在最前、不补。
   - 快照：出厂的带着字和数（3、20），内核拿到截短的数和模板；旧快照、只有数没有字的都不截短，读进来再写出去一字不差。
   - 随机：另用一串随机数，只在捣乱的种子里、有摘要请求在路上时十回一回报超长，一半带超了多少，原来那串输入不动。看守查截过的请求只跟在报了超长的那一次后面、截到的一次比一次晚、最多 3 次、请求是截到的以后到第 N 条的清单；截过的压缩最后写着没看到的那一段，没截过的没有。三百例走到「摘要请求超长截短」「截短了再发」「截不动算失败」；「截过的压缩写明没看到的」在两万例的长跑里走到。
2. 请求形状探针、组装样本没变：没截过的请求字节不变。
3. **登记簿**：`truncated.txt` 10 个 token、`notes-uncovered.txt` 25 个（按第 1 到 5 条算），照项目主人给的端点量，进了 `26-提示词.md` 第十节，`prompts.md` 照它重新生成。
4. **变异**：手写 20 个全逮住（不看次数、盖住的边界、20% 不向上取整、不看上一次截到哪、至少留一组、没看到的那一段从哪算、不写那一段、截短时不查事实、再发时不照截的、替代到的变了也照截、不交回摘要请求、别的错也截、不记次数、不补 user、截的时候丢了检查点、驱动的三种解析、不是超长也解析、快照只有数也截）。
5. `cargo xtask check` 八项全过；三台机器的 CI 全绿。

**施工中改的**：
- **报了超长不当场重发**：原来想在「说完了」那一刻截好直接发。改成截到哪记在回合上、回到准备好，这一批落了盘照常走发请求那一步：守住先落盘后请求，环境、权限两块事实照查（随机测试的种子 8 撞到：这一轮里切过权限，截过的请求前面没查事实）。重读因此照常再做一次，不另记第一次的结果。蓝图第三条第 10 条第 4 条照改。
- **随机测试的超长另用一串随机数**：一开始混进原来那串的出错里，原来那串的走向变了，老的几条路走不到（「改回文件时来的命令被拒」「压缩了」）；改成另一串、只在捣乱的种子里插，老路全走得到。
- `random.rs` 过了 500 行，模型怎么收场挪到 `random/endings.rs`。
