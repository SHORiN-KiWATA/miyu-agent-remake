## 施工单 V-2（三补）：重开大会话只读一遍日志

状态：在做（2026-10-11）。V-3（量尺进 CI）第一次在 GitHub 的机器上量出来：4 个逻辑核的机器上，重启后打开一万条事件的大会话 p95 128.8 ms，超了 60 ms 的预算；本机绑到 4 个核上量也是 62.6 ms。本机 16 个核时 46.8 ms，看不出来。

### 查清楚的

重开一个会话，整份日志读了三遍，都在等的路上：

1. 会话表在载入之前另读一遍，只为认出最后一次记下的工作目录、加进来的目录（`sessions/found.rs` 的 `remembered`）。
2. 载入自己读一遍（`SessionLog::open`，V-2 下补起分块多线程解）。
3. 载入以后、放进表之前，拿着表的锁再读一遍，认派到一半的空子会话（`sessions/orphans.rs`）。

4 个核上读、解一遍约 14 ms，核少的机器上三遍叠起来就超了。

### 这一步做什么

1. 载入的格 `environment` 换成 `place: Workplace`：`Given(环境)` 照旧给定；`Remembered { offset, pick }` 由载入读日志时顺手认出最后一次记下的工作目录、加进来的目录（认法照旧，挪进 `miyu-session` 的 `open/load.rs`），工作目录交给会话表给的挑法定。开会话的配置要工作目录，挪到读完以后。载入另交回定下的环境（`load_placed`），会话表照它记进表里：不拿着表的锁去问 actor，它头一批要做的事可能也要表的锁（CI 第一趟时想到的，那一趟的偶发红另查，见下）。
2. 收空子会话挪到后台：放进表以后起一个任务，在阻塞线程里认、不拿表的锁，认出来有的才拿锁收。
3. 图纸：`protocol.md`「会话表」第 5、8 条，`session/actor.md` 第 2 条和 `Load` 的格，`agents.md` 第一条第 8 条。

### 量到的

照出厂参数（一万条事件），全核的存在 `docs/perf/2026-10-10-linux-x86_64-v2三补.{json,md}`；绑 4 个核的照同样的参数、不等闲够了退下（`--idle-wait 0`）：

| 项目 | V-2 再补 | V-2 三补 | 预算 |
|---|---|---|---|
| 重启后打开大会话 p95，本机 16 核 | 46.8 ms | 25.7 ms | 60 ms，过 |
| 重启后打开大会话 p95，本机绑 4 核 | 62.6 ms | 28.0 ms | 60 ms，过 |
| 重启后打开大会话 p95，GitHub 的机器（4 核） | 128.8 ms | 合了以后 V-3 量 | 60 ms |
| 从头投影 p95，本机 16 核 | 3.6 ms | 5.5 ms | 60 ms，过 |
| 重启、打开大会话、说一句以后的核心 PSS | 48.6 MB | 46.9 MB | 无 |

- 从头投影多了两三毫秒：收空子会话那一遍读挪到了后台，和头一次说的那一轮挤在同一时候；离预算远。
- 23 第二节的几行这一份全过。
- 第一趟 CI（run 1736）Linux 上 `preset_background::interrupting_the_parent_stops_its_foreground_subagent` 等子代理报回来超了六十秒；这条测试不载入会话，不走这一步改的路，本机单跑五遍都过，当偶发红记下，再红就专门查。
