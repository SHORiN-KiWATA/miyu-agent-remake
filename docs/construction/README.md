### 一、施工的规矩

1. **一步一张施工单。** 动手之前先写：这一步做什么、不做什么、要拍板的、怎么验收。商量定了再动手。
   - **只有技术细节的步，直接做**（2026-09-26 项目主人定）：施工单照写，留底；不等拍板，三台机器的 CI 全绿、测试全过，就算验收通过，照第 2 条整理、合进 main、推送，接着做下一步。
   - **停下来找项目主人的**：有要他拍板的、有不清楚的、要他真人实测的。前端、交互这类，照旧先出详细的施工方案商量。
2. **一步一个工作树，推倒重来只要删掉它。** 每一步从 main 开一个分支 `step/<编号>-<名字>`，检出到单独的目录 `.worktrees/<编号>-<名字>/`，施工和验收都在那里。分支上的提交是草稿，推到 GitHub 上跑三平台 CI，三个平台全绿是验收的一部分。CI 还有一项长跑：随机测试放大到两万例，只在 Linux 上、release 模式跑，它也要绿（照 niri，2026-09-26 项目主人提，施工 2-10）。验收通过了才整理成正式的提交：这一步的改动合成一个提交，说明写 `施工 <编号>：<名字>`。开工前，施工单和它补的图纸先提交进 main，标题写改了哪份图纸、改了什么，不写「施工单」（2026-09-26 项目主人）；顺手做的无关改动（例如改规矩）单独成提交。每个提交都能编译、门禁全过，一起快进合进 main、推送。不满意就删掉那个目录和分支，本地的和 GitHub 上的都删，main 一个字节都不动。
3. **每一步做完，仓库都是绿的**：能编译，测试和门禁全过。
4. **一步的大小，一次坐下来看得完。** 只做一件事，新代码一般在几百行以内。
5. **验收落在测试上。** 每一步先写证明它做对了的测试；要人眼看的东西（例如事件写成 JSON 是什么样子）存成样本文件，验收时直接看。
6. **分工照旧**：技术细节按推荐定，写进施工单留痕；产品、体验、署名这类问题问项目主人，附推荐。
7. **照图纸施工。** 每一张施工单写明照的是哪几张图纸（`00-设计理念.md` 第四节「设计有图纸」）。图纸没画到的细节，先补进图纸，跟施工单一起拍板再动手。施工中发现设计有问题，先停下来改图纸，再接着做。代码不悄悄偏离图纸。
8. **不为以后写代码。** 这一步用不到的类型、字段、配置项都不写。以后要加，格式演进的规则允许加（`03-事件模型.md` 第八节）。
9. **施工图一步拼一块。** `施工图.html` 里每一步有一张图，画出这一步做完以后的样子，新加的标出来；最上面的「拼到哪了」是整张架构图：没拼的虚着，拼上的画实，块上标着是哪一步拼的。一步合进 main 时，它的那一块跟着定稿，标题栏写上提交号（2026-09-26 项目主人提）。
10. **两步同时做，只在它们不碰同一片代码时。** 2026-09-28 试过一次：4-7（上）自己做，4-8 交给一个分身在它自己的工作树里做，共用一把 cargo 的锁。从开工到两步都合进 main 约一小时，一步一步做估计要一个半小时以上；合并时 4 个文件冲突（依赖、模块登记、施工方案的表），都是机械的；分身继承了主会话的上下文，多花了约 62 万 token。
    - M5 起照这个做法分线（2026-09-28 项目主人同意）：Linux 这条主干主会话自己做，macOS、Windows 各交给一个分身，各在自己的工作树里（代理那一步 09-29 取消）。分身不继承主会话的上下文，交代写成自包含的。分身先写施工单和蓝图，主会话审过、先提交进 main，再施工；施工做到分支 CI 全绿、变异跑完就停，由主会话审、按顺序合进 main。施工方案、施工图、蓝图的总表只有主会话改。
    - **省额度的五条**（2026-10-01 项目主人定，这一天派了 9 个分身、花了四百多万 token，大头浪费在并行冲突上）：
      1. 改同一批文件（`protocol.md`、内核、登记簿、探针存档）的步子一张一张做；并行只留互不相干的，最多两张。
      2. 合并时的冲突主会话自己解，不把做完的分身叫回来：叫回一次要重带它几十万 token 的上下文。
      3. 派工时只列这一步要读的几节（图纸的哪几节、哪一个先例），不让分身读整页图纸。
      4. 手写变异封顶 15 个左右，挑最关键的写，照旧要全被逮住。
      5. 机械的步子（改名、加字段、搬文件、照先例抄一遍）派便宜的模型（Sonnet）做；要拿主意的步子用主会话的模型。派工前主会话判断是哪一种，写进派工单。

- 先后的理由：内核是纯逻辑，不碰 I/O（`02-内核.md` K1），所以 M1、M2 全在内存里测，不需要真模型，也不需要磁盘。M3 才第一次接上真实世界。
- **试玩**（2026-09-26 项目主人提：做到一定程度以后，想先无头试玩一下）：最早能跟真模型说话的是 3-9 的 `miyu ask`，M4 以前只能聊天，还动不了文件。也可以在 3-5 做完以后先搭一个进程内的试玩台：内核直接接真模型，跳过核心进程和协议端点，早四步，缓存命中也能早点量到。**2026-09-27 项目主人定：搭**，接 DeepSeek 官方（3-5 补）。能试玩了，停下来叫他。

### 四、施工单的格式

每一张施工单只写这几节（2026-09-28 项目主人定：有了蓝图，施工单变薄）：

| 节 | 写什么 |
|---|---|
| 目的 | 这一步做成以后，多了什么，一两句 |
| 蓝图改哪几节 | 哪几页的哪几节，改成什么样的要点；真正的改动写在蓝图里，和施工单一起提交 |
| 要拍板的 | 问项目主人的，每一条附推荐；没有就不写 |
| 不做什么 | 容易顺手做、但不属于这一步的 |
| 验收 | 能照着做的步骤，每一步写清看到什么算通过 |
| 风险 | 可能出错的地方，怎么防 |

- 以前的「图纸」「做什么」「我定的」三节不再写：照哪份设计，蓝图每页的「出处」写着；改哪些文件，蓝图每页的「在哪」写着；定下的技术细节直接写进蓝图，为什么写进设计文档。
- 一张施工单大概二三十行。4-9（补）以前的施工单是当时的记录，照旧留着，不改写。

施工单放在这个目录里，文件名是 `<编号>-<名字>.md`。一步合进 main 时，它的施工单跟着一起提交，状态改成「已完成」。

- 第五节只写做到哪了、下一张是什么；每一步做了什么、怎么验收的，写在它自己的施工单里（2026-09-28 项目主人定）。
- 不写项目主人的原话：定了什么、为什么，用平常的话写，后面注明日期、谁定的（2026-09-28 项目主人定）。
