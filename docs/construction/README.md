## 施工方案

状态：已定（2026-09-26 项目主人批准）。M4 以后到了跟前再拆。

项目主人 2026-09-26：「我希望我们能慢慢做，细细地做。如果做的不好可以 discard 推倒重来的那种细度。」「拆分后一步步我们商量着来。」

这一份是总的施工方案：施工的规矩、总工程表、近期每一步做什么。每一步动手之前，另写一张施工单（第四节的格式），商量定了再做。

### 一、施工的规矩

1. **一步一张施工单。** 动手之前先写：这一步做什么、不做什么、要拍板的、怎么验收。商量定了再动手。
2. **一步一个工作树，推倒重来只要删掉它。** 每一步从 main 开一个分支 `step/<编号>-<名字>`，检出到单独的目录 `.worktrees/<编号>-<名字>/`，施工和验收都在那里。验收通过了才提交，合成一个提交快进合进 main，提交说明写 `施工 <编号>：<名字>`。不满意就删掉那个目录和分支，main 一个字节都不动。
3. **每一步做完，仓库都是绿的**：能编译，测试和门禁全过。
4. **一步的大小，一次坐下来看得完。** 只做一件事，新代码一般在几百行以内。
5. **验收落在测试上。** 每一步先写证明它做对了的测试；要人眼看的东西（例如事件写成 JSON 是什么样子）存成样本文件，验收时直接看。
6. **分工照旧**：技术细节按推荐定，写进施工单留痕；产品、体验、署名这类问题问项目主人，附推荐。
7. **照图纸施工。** 每一张施工单写明照的是哪几张图纸（`00-设计理念.md` 第四节「设计有图纸」）。图纸没画到的细节，先补进图纸，跟施工单一起拍板再动手。施工中发现设计有问题，先停下来改图纸，再接着做。代码不悄悄偏离图纸。
8. **不为以后写代码。** 这一步用不到的类型、字段、配置项都不写。以后要加，格式演进的规则允许加（`03-事件模型.md` 第八节）。

### 四、施工单的格式

每一张施工单都写这几节：

| 节 | 写什么 |
|---|---|
| 目的 | 这一步做成以后，多了什么 |
| 图纸 | 照的是哪几张图纸；图纸没画到、这一步要先补的细节 |
| 做什么 | 新增、改动哪些文件，各自装什么 |
| 不做什么 | 容易顺手做、但不属于这一步的 |
| 要拍板的 | 问项目主人的，每一条附推荐 |
| 我定的 | 技术细节，定了什么、为什么 |
| 验收 | 能照着做的步骤，每一步写清看到什么算通过 |
| 风险 | 可能出错的地方，怎么防 |

施工单放在这个目录里，文件名是 `<编号>-<名字>.md`。一步合进 main 时，它的施工单跟着一起提交，状态改成「已完成」。
